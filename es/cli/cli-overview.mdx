## Para qué sirve el CLI

El CLI es el camino más corto entre un proyecto limpio y un bot ejecutable. Gestiona el scaffolding, la generación de archivos, el arranque en desarrollo, los builds de producción, la ejecución en runtime, la integración de base de datos y los diagnósticos desde una única interfaz coherente. Esa coherencia importa porque la línea de comandos es donde los equipos suelen perder tiempo en pasos de configuración repetidos, deriva de nombres o flujos medio manuales.

En la práctica, el CLI es más útil cuando dejas que cada comando haga un trabajo claro. _new_ crea el workspace, _generate_ agrega archivos alineados con el framework, _dev_ ejecuta el bot activo, _build_ valida la salida de producción y _start_ ejecuta el artefacto compilado. Los comandos restantes respaldan flujos adyacentes como la configuración de base de datos y el diagnóstico del entorno.

## Comandos disponibles

El CLI incluye siete comandos. Cada uno apunta a una fase distinta del ciclo de vida del proyecto, desde el scaffolding de un proyecto nuevo hasta la ejecución del artefacto compilado en producción.

<DropdownGroup>
<Dropdown title="spraxium new">
  Crea un nuevo proyecto de Spraxium a partir de una plantilla. El asistente interactivo solicita nombre de proyecto, plantilla, paquetes extra opcionales y si deseas inicializar un repositorio Git. Ejecútalo una vez por proyecto, fuera de cualquier workspace de Spraxium existente.
</Dropdown>

<Dropdown title="spraxium dev">
  Inicia el servidor de desarrollo usando el loader de SWC para ciclos de
  compilación rápidos. Observa los archivos fuente y reinicia automáticamente en
  cada guardado. El comportamiento del watcher, el entrypoint y el retardo de
  debounce son configurables en *spraxium.config.ts*.
</Dropdown>

<Dropdown title="spraxium generate">
  Hace scaffolding de un archivo alineado con el framework a partir de uno de
  diecinueve schematics: módulos, servicios, tareas, listeners, slash commands,
  prefix commands, guards, embeds, botones, modales y más. Registra
  automáticamente los archivos generados en el array correcto del módulo cuando
  aplica.
</Dropdown>

<Dropdown title="spraxium build">
  Ejecuta *tsc --noEmit* para type-check y luego empaqueta con *tsdown* para
  producción. Devuelve un código de salida distinto de cero en caso de fallo, lo
  que lo hace adecuado como puerta de CI. La salida del build queda en
  `.spraxium/dist`.
</Dropdown>

<Dropdown title="spraxium start">
  Ejecuta el artefacto compilado producido por *spraxium build*. Establece
  *NODE_ENV* en `production` automáticamente y envía stdio directamente a la
  terminal. Requiere que el build se haya completado antes de ejecutarse.
</Dropdown>

<Dropdown title="spraxium database">
  Genera un módulo completo de integración ORM mediante un asistente
  interactivo. Soporta Prisma, Drizzle, TypeORM, Mongoose y MikroORM. Instala
  dependencias y registra el módulo automáticamente.
</Dropdown>

<Dropdown title="spraxium info">
  Imprime un informe de diagnóstico con la versión del CLI, versión de Node, SO,
  gestor de paquetes y todas las versiones detectadas de *@spraxium/*. Acepta
  la bandera *--json* para salida legible por máquina. Es útil para reportes de
  bugs y artefactos de CI.
</Dropdown>
</DropdownGroup>

## Cómo encajan los comandos

Piensa en el CLI como un ciclo de vida, no como una bolsa de comandos sin relación:

1. _new_ crea la forma inicial del proyecto.
2. _generate_ mantiene los archivos nuevos alineados con las convenciones del framework.
3. _dev_ ofrece el ciclo de feedback más rápido durante la implementación.
4. _build_ es la puerta de calidad antes de compartir o desplegar.
5. _start_ ejecuta exactamente el artefacto de producción que acabas de compilar.
6. _database_ e _info_ apoyan la configuración y el troubleshooting alrededor de ese ciclo.

## Flujo diario recomendado

La mayoría de los equipos solo usa un subconjunto del CLI en el día a día. El ritmo habitual es hacer scaffolding una vez, generar cuando hace falta, quedarse en _dev_ durante la implementación y usar _build_ como comprobación final de confianza antes de publicar.

<Steps>
  <Step title="Haz scaffolding con new">
    Ejecuta *spraxium new* una vez para crear el proyecto. Elige tu plantilla y
    módulos opcionales durante el asistente interactivo.
  </Step>
  <Step title="Genera con generate">
    Usa *spraxium generate* para agregar módulos, servicios, listeners o
    comandos. El CLI coloca los archivos en la carpeta correcta y los registra
    automáticamente.
  </Step>
  <Step title="Itera con dev">
    Ejecuta *spraxium dev* durante la implementación. Los archivos se recargan
    automáticamente al guardar para que veas resultados al instante.
  </Step>
  <Step title="Valida con build">
    Ejecuta *spraxium build* antes de cada despliegue a un entorno compartido.
    Los errores de tipos y de bundle aparecen aquí, no en producción.
  </Step>
  <Step title="Publica con start">
    Ejecuta *spraxium start* en staging y producción después de un build exitoso.
    Lee directamente la salida compilada.
  </Step>
</Steps>

## Uso local frente a CI

El desarrollo local suele girar en torno a _generate_ y _dev_. CI normalmente se centra en _build_ y, en algunos casos de depuración, _info --json_. Mantener clara esa separación ayuda a evitar forzar comandos interactivos dentro de la automatización o depender de comportamientos solo de desarrollo en pipelines de producción.

## Elegir rápido el comando correcto

Si no tienes claro qué comando ejecutar, usa este atajo:

1. Necesitas un proyecto nuevo: ejecuta _spraxium new_.
2. Necesitas un nuevo archivo del framework: ejecuta _spraxium generate_.
3. Necesitas recarga en caliente mientras codificas: ejecuta _spraxium dev_.
4. Necesitas un artefacto desplegable: ejecuta _spraxium build_.
5. Necesitas ejecutar el artefacto compilado: ejecuta _spraxium start_.
6. Necesitas contexto del entorno: ejecuta _spraxium info_.
