## Rol del emisor

_Signal Client_ existe para publicar eventos desde servicios externos hacia un límite de integración orientado al bot. Aunque el emisor sea un endpoint de API, un worker cron o una Server Action de Next.js, el objetivo operativo siempre es el mismo: impulsar comportamiento del bot de forma controlada y auditable. El paquete se encarga de construcción de envelope, firma HMAC, rotación de webhooks y absorción de rate-limits para que el código productor se mantenga enfocado en lógica de negocio.

Esta perspectiva evita que los equipos conviertan el cliente en una herramienta de mensajería genérica. El cliente aporta más valor cuando tus servicios necesitan una forma segura y consistente de notificar dominios del bot sobre cambios de estado sin acoplarse a internals del gateway de Discord.

## Contrato del constructor

_SignalClient_ recibe un único objeto _SignalClientConfig_ y un _FallbackStore_ personalizado opcional. El constructor crea un _SignalEnvelopeBuilder_ interno para firma HMAC, un _WebhookPool_ para entrega round-robin y, cuando está habilitado, un _FallbackWorker_ que arranca de inmediato. Cada campo, salvo `webhookUrls` y `hmacSecret`, tiene defaults razonables, así que una configuración mínima solo requiere esos dos valores.

```typescript filename="signal-client.setup.ts"
import { SignalClient } from '@spraxium/signal-client';

const client = new SignalClient({
  webhookUrls: [
    process.env.SIGNAL_WEBHOOK_URL_1!,
    process.env.SIGNAL_WEBHOOK_URL_2!,
  ],
  hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
  rateLimitStrategy: 'skip',
});
```

El secreto compartido en `hmacSecret` debe coincidir exactamente con la configuración del lado del bot. Si los valores divergen, el bot rechaza cada envelope en la verificación HMAC (regla R10) y no se ejecuta ningún listener.

## Construcción y firma del envelope

Cada llamada a _send_ delega internamente en _SignalEnvelopeBuilder_, que produce un envelope completo firmado criptográficamente. El builder genera un UUID aleatorio como nonce, captura el timestamp actual como _sentAt_ y calcula la firma HMAC-SHA256 sobre la concatenación `nonce.sentAt.JSON.stringify(payload)`. Esta fórmula es idéntica a la usada por _@spraxium/signal_ en el lado receptor, así que ambos extremos comparten el mismo contrato de firma sin negociación adicional.

El envelope resultante siempre lleva versión de protocolo `1`, nombre de evento, guild ID objetivo y payload junto a los campos criptográficos. El código productor nunca necesita interactuar directamente con el builder porque _send_ encapsula todo el flujo.

## El método send

_send_ es la API principal. Acepta nombre de evento, guild ID, payload opcional y _SendOptions_ opcional. El flujo interno construye el envelope, toma el siguiente webhook disponible del pool y entrega por HTTP POST. Si el webhook responde 429, el pool lo marca como rate-limited y prueba de inmediato el siguiente candidato. Cuando se agotan todos los webhooks, el comportamiento depende de _rateLimitStrategy_.

```typescript filename="emit-event.ts"
await client.send('billing.status.changed', guildId, {
  plan: 'premium',
  expiresAt: '2025-12-31',
});
```

La interfaz _SendOptions_ expone dos campos opcionales. El campo _webhookIndex_ fuerza entrega por un webhook específico, omitiendo la rotación round-robin. El campo _skipFallback_ se usa internamente por _FallbackWorker_ para evitar loops de reencolado durante reintentos.

## Rotación del pool de webhooks

_WebhookPool_ distribuye envíos entre webhooks configurados usando un cursor round-robin. Cuando un webhook devuelve HTTP 429, se marca como rate-limited por la duración indicada en el header `Retry-After`, y el pool lo omite automáticamente hasta que expire ese cooldown. Agregar múltiples URLs de webhook mejora mucho la resiliencia en ráfagas porque el cliente siempre tiene endpoints alternativos para probar.

El pool expone varios métodos de inspección útiles para monitoreo y debugging. Puedes acceder al pool en cualquier momento mediante la propiedad _pool_ de la instancia del cliente.

## Estrategias de rate-limit

Cuando todos los webhooks del pool están rate-limited al mismo tiempo, el cliente debe decidir qué hacer. El campo _rateLimitStrategy_ controla ese comportamiento. Ambas estrategias son válidas según tu arquitectura de servicio.

<Table>
  <TableHead>
    <TableRow>
      <TableCell header>Estrategia</TableCell>
      <TableCell header>Comportamiento</TableCell>
      <TableCell header>Mejor ajuste</TableCell>
    </TableRow>
  </TableHead>
  <TableBody>
    <TableRow>
      <TableCell>skip</TableCell>
      <TableCell>
        Lanza *AllWebhooksRateLimitedError* inmediatamente. El error incluye el
        estado completo del pool con timestamps de cooldown para que el caller
        decida cuándo reintentar.
      </TableCell>
      <TableCell>
        Servicios que ya tienen su propia orquestación de reintentos o
        infraestructura de colas.
      </TableCell>
    </TableRow>
    <TableRow>
      <TableCell>wait</TableCell>
      <TableCell>
        Espera hasta que el webhook más próximo salga de cooldown (vía
        *msUntilAvailable*) y luego reintenta entrega exactamente una vez. Si
        también falla, lanza error.
      </TableCell>
      <TableCell>
        Absorción de ráfagas cortas dentro del cliente sin lógica externa de
        reintentos.
      </TableCell>
    </TableRow>
  </TableBody>
</Table>

El default es `'skip'` porque mantiene al cliente no bloqueante. Para la mayoría de contextos de Server Actions o handlers de API donde una latencia breve es aceptable, `'wait'` ofrece mejor ergonomía al absorber picos transitorios de rate-limit de forma transparente.

## Tipos de error

El cliente expone dos clases de error que entregan información estructurada de fallas. Ambas extienden `Error` y cargan campos legibles por máquina para manejo programático.

_SignalClientError_ se lanza ante respuestas HTTP no 2xx y no 429. Expone _statusCode_ y _body_ de respuesta como propiedades, lo que facilita registrar fallas de transporte con contexto completo. Este error indica que el endpoint webhook tuvo un problema, no una situación de rate-limit.

_AllWebhooksRateLimitedError_ extiende _SignalClientError_ con `statusCode` `429` y expone un array _poolStatus_. Cada entrada es un snapshot _WebhookStatus_ con _index_, _url_, flag _available_ y timestamp _rateLimitedUntil_. Este error solo se lanza bajo estrategia `'skip'` o cuando `'wait'` agota su único reintento.

## Emisor práctico: Next.js Server Actions

Un patrón de producción común es un panel admin construido con Next.js donde una Server Action actualiza datos de negocio y emite un evento Signal para el bot. Este enfoque mantiene desacopladas las mutaciones de UI y las reacciones del bot, conservando un flujo único para operadores. La Server Action maneja autorización y persistencia dentro de tu aplicación web, y _Signal Client_ maneja la entrega asíncrona hacia el runtime del bot.

<CodeTabs>
  <Tab label="Server Action">
    ```typescript filename="app/actions/update-prefix.ts"
    'use server';

    import { SignalClient } from '@spraxium/signal-client';

    const client = new SignalClient({
      webhookUrls: [process.env.SIGNAL_WEBHOOK_URL_1!],
      hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
      rateLimitStrategy: 'wait',
    });

    export async function updatePrefix(guildId: string, prefix: string) {
      // persist in your database first
      await db.guilds.update(guildId, { prefix });

      // then emit the event for the bot
      await client.send('config.update', guildId, {
        prefix,
        source: 'admin-panel',
      });
    }
    ```

  </Tab>
  <Tab label="API Route Handler">
    ```typescript filename="app/api/signal/route.ts"
    import { SignalClient } from '@spraxium/signal-client';
    import { NextResponse } from 'next/server';

    const client = new SignalClient({
      webhookUrls: [
        process.env.SIGNAL_WEBHOOK_URL_1!,
        process.env.SIGNAL_WEBHOOK_URL_2!,
      ],
      hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
      rateLimitStrategy: 'skip',
    });

    export async function POST(req: Request) {
      const { event, guildId, payload } = await req.json();
      await client.send(event, guildId, payload);
      return NextResponse.json({ ok: true });
    }
    ```

## Guías de modelado de eventos

Prefiere nombres orientados a dominio que describan hechos de negocio en lugar de acciones de transporte. Un nombre como _billing.status.changed_ es más fácil de versionar y razonar que etiquetas orientadas a acciones que filtran detalles de implementación interna. Mantén los nombres de evento en minúsculas y formato dot-separated para seguir las convenciones usadas en todo el sistema Signal.

Los payloads deberían ser intencionalmente pequeños y estables. Incluye solo los campos que el bot realmente necesita para decidir y evoluciona el schema con cambios aditivos siempre que sea posible. Eliminar o renombrar un campo existente es un cambio breaking que exige coordinar despliegues de emisor y listener al mismo tiempo.

Usa el filtro _events_ en _FallbackConfig_ para enfocar garantías de confiabilidad en los eventos más críticos. Los eventos que no aparecen en esa lista siguen entregándose por la ruta normal, pero no se encolan en fallback store cuando fallan.

## Recorrido del flujo de entrega

<Steps>
  <Step title="Construir el envelope firmado">
    El método *send* delega en *SignalEnvelopeBuilder*. El builder genera un
    nonce vía `crypto.randomUUID()`, captura `Date.now()` como *sentAt*,
    calcula la firma HMAC-SHA256 y devuelve un envelope completo con versión de
    protocolo `1`.
  </Step>
  <Step title="Elegir el siguiente webhook">
    *WebhookPool.next* devuelve el siguiente webhook disponible en orden
    round-robin. Si se proporcionó *SendOptions.webhookIndex*, el pool devuelve
    esa entrada específica vía *get*, omitiendo rotación. Si todos los
    webhooks están rate-limited y no se forzó índice, el flujo salta al paso
    cinco.
  </Step>
  <Step title="Entregar por HTTP POST">
    El cliente envía un request POST a la URL del webhook con el envelope JSON
    serializado dentro del campo content de un mensaje de Discord. Si la
    respuesta es 2xx, la entrega se completa y el método retorna exitosamente.
  </Step>
  <Step title="Manejar respuestas 429">
    Cuando el webhook devuelve HTTP 429, el pool marca ese índice como
    rate-limited por la duración parseada del header `Retry-After` (con default
    de 1000 ms). El cliente prueba inmediatamente el siguiente webhook
    disponible. Esta rotación continúa hasta que uno tenga éxito o todos se
    agoten.
  </Step>
  <Step title="Aplicar estrategia de rate-limit">
    Cuando no quedan webhooks, *rateLimitStrategy* decide el resultado. Con
    `'skip'`, se lanza *AllWebhooksRateLimitedError* de inmediato. Con `'wait'`,
    el cliente espera el cooldown más corto y reintenta una vez. Si fallback
    está habilitado y el error es capturable, el envelope se encola en fallback
    store para reintento posterior.
  </Step>
</Steps>

## Cuándo este modelo es la herramienta equivocada

Si necesitas confirmación síncrona inmediata desde la lógica del bot dentro del mismo ciclo de request, Signal generalmente no es el contrato adecuado. Las llamadas directas a servicios siguen siendo más simples y trazables para comunicación in-process dentro de un mismo límite de servicio. Signal está diseñado para entrega de eventos asíncrona fire-and-forget donde el productor no necesita respuesta del consumidor.

Del mismo modo, si tus eventos requieren garantías de orden estricto, una cola dedicada como RabbitMQ o Redis Streams encaja mejor. Signal entrega mensajes tan rápido como lo permita el pool de webhooks, y el orden tras reintentos por fallas es best-effort, no estrictamente secuencial.
