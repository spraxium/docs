## Por qué Zod pertenece al borde de Signal

Los listeners del bot son el punto donde eventos externos se convierten en efectos internos. Cambios de roles, actualizaciones de configuración, acciones de moderación y mutaciones de facturación parten de un payload entrante. Usar Zod en este borde te permite rechazar datos mal formados antes de que lleguen a servicios de negocio. No es opcional para bots de producción, porque el payload proviene de sistemas externos que pueden evolucionar de forma independiente, enviar estructuras inesperadas o contener valores inválidos por bugs en el código emisor.

El decorator _@OnSignal_ acepta una opción `schema` que puede ser cualquier schema Zod. Cuando está presente, _SignalProcessor_ llama a _safeParse_ sobre el payload del envelope antes de invocar el handler. Si la validación falla, el handler nunca se llama y se emite un log de diagnóstico cuando el modo debug está habilitado. Si no hay schema configurado, el payload crudo pasa sin cambios, lo que puede servir para handlers que hacen su propia lógica de parseo.

<Callout tone="success" title="Valida en el borde, no dentro de los handlers">
  Adjuntar el schema a <code>@OnSignal</code> garantiza que cada invocación del
  handler reciba datos validados y tipados. Esto elimina checks defensivos
  dentro del código de negocio y hace confiables las firmas de handlers.
</Callout>

## Diseño de schemas y setup del listener

El patrón recomendado es definir schemas en archivos dedicados e importarlos en tus clases listener. Esta separación mantiene los schemas reutilizables entre handlers y permite probarlos de forma independiente. Cada archivo de schema exporta tanto la constante Zod como el tipo TypeScript inferido.

<CodeTabs>
  <Tab label="Schema" language="typescript">
```typescript filename="src/modules/signal/schemas/config-update.schema.ts"
import { z } from 'zod';

export const ConfigUpdateSchema = z.object({
  prefix: z.string().min(1).max(5),
  language: z.enum(['en', 'pt', 'es']).optional(),
  updatedBy: z.string().min(17).max(20),
});

export type ConfigUpdatePayload = z.infer<typeof ConfigUpdateSchema>;
```
  </Tab>
  <Tab label="Listener" language="typescript">
```typescript filename="src/modules/signal/listeners/guild-config.signal.ts"
import { SignalListener, OnSignal } from '@spraxium/signal';
import type { SignalEnvelope } from '@spraxium/signal';
import {
  ConfigUpdateSchema,
  type ConfigUpdatePayload,
} from '../schemas/config-update.schema';

@SignalListener()
export class GuildConfigSignal {
  @OnSignal('config.update', { schema: ConfigUpdateSchema })
  async onConfigUpdate(
    payload: ConfigUpdatePayload,
    envelope: SignalEnvelope,
  ): Promise<void> {
    // payload is validated and strongly typed
    // envelope.guildId provides tenant context
  }
}

````

## Flujo de validación en el processor

Cuando *SignalProcessor* recibe un envelope validado, comprueba si el handler resuelto tiene un schema adjunto. Si existe, el processor llama a *schema.safeParse(envelope.payload)* e inspecciona el resultado. Si es exitoso, *result.data* reemplaza al payload crudo y se pasa al handler. Si falla, el handler se omite por completo y se emite una entrada de diagnóstico con los detalles de issues de Zod.

Este flujo significa que tu handler siempre recibe datos que coinciden con el schema. No necesitas bloques try-catch para acceder al payload, no necesitas aserciones manuales de tipo y no hay riesgo de propiedades undefined causando errores de runtime. El schema actúa al mismo tiempo como contrato de compilación y de ejecución.

<Steps>
  <Step title="Chequeo de presencia de schema">
    El processor verifica si el handler tiene un schema Zod. Si no hay schema
    adjunto, *envelope.payload* se pasa al handler sin cambios. Esto permite
    que handlers sin necesidad de validación eviten por completo ese overhead.
  </Step>
  <Step title="Ejecución de safeParse">
    El processor llama a *schema.safeParse(envelope.payload)*, que nunca lanza
    excepción. Devuelve una unión discriminada: `{ success: true, data: T }`
    con payload parseado y tipado, o `{ success: false, error: ZodError }` con
    los issues de validación.
  </Step>
  <Step title="Ruta de éxito">
    En validación exitosa, *result.data* reemplaza al payload crudo. Esta
    versión parseada tiene defaults aplicados, transforms ejecutados y tipos
    refinados. El handler recibe este valor tipado como primer argumento.
  </Step>
  <Step title="Ruta de falla">
    En validación fallida, el handler nunca se invoca. Si debug está
    habilitado, el processor registra los issues de Zod como array JSON,
    incluyendo path, tipo esperado y valor recibido para cada campo fallido. El
    envelope se descarta en silencio para evitar que datos corruptos alcancen
    la lógica de negocio.
  </Step>
</Steps>

## Múltiples handlers con distintos schemas

Una sola clase *@SignalListener* puede contener múltiples métodos *@OnSignal* con nombres de evento y schemas diferentes. Cada handler se registra de forma independiente en *SignalRouter*, y cada schema se valida de forma independiente durante el despacho. Esto te permite agrupar handlers de un dominio relacionado en una sola clase mientras mantienes contratos estrictos de payload por evento.

```typescript filename="src/modules/signal/listeners/guild-config.signal.ts"
import { SignalListener, OnSignal } from '@spraxium/signal';
import type { SignalEnvelope } from '@spraxium/signal';
import { z } from 'zod';

const PrefixSchema = z.object({
  prefix: z.string().min(1).max(5),
});

const LanguageSchema = z.object({
  language:  z.enum(['en', 'pt', 'es']),
  updatedBy: z.string(),
});

@SignalListener()
export class GuildConfigSignal {
  @OnSignal('config.prefix.update', { schema: PrefixSchema })
  async onPrefixUpdate(
    payload: z.infer<typeof PrefixSchema>,
    envelope: SignalEnvelope,
  ): Promise<void> {
    // Handle prefix changes
  }

  @OnSignal('config.language.update', { schema: LanguageSchema })
  async onLanguageUpdate(
    payload: z.infer<typeof LanguageSchema>,
    envelope: SignalEnvelope,
  ): Promise<void> {
    // Handle language changes
  }
}
````

Los schemas durables siguen un conjunto de principios que minimizan cambios breaking entre despliegues de productor y consumidor. Como el emisor y el bot pueden desplegarse de manera independiente, la evolución del schema debe manejarse con cuidado.

## Patrones avanzados de schema

Para eventos de dominio complejos, Zod soporta patrones de composición potentes que mantienen schemas DRY y expresivos. Las discriminated unions permiten validar distintas formas de payload según un campo discriminador compartido. Las intersecciones permiten combinar campos base con extensiones específicas del evento.

<CodeTabs>
  <Tab label="Discriminated union" language="typescript">
```typescript filename="src/modules/signal/schemas/billing.schema.ts"
import { z } from 'zod';

const ActivatedSchema = z.object({
action: z.literal('activated'),
planId: z.string(),
userId: z.string(),
expiresAt: z.number(),
});

const CancelledSchema = z.object({
action: z.literal('cancelled'),
userId: z.string(),
reason: z.string().optional(),
});

export const BillingEventSchema = z.discriminatedUnion('action', [
  ActivatedSchema,
  CancelledSchema,
]);

export type BillingEventPayload = z.infer<typeof BillingEventSchema>;
```
  </Tab>
  <Tab label="Base + extension" language="typescript">
```typescript filename="src/modules/signal/schemas/moderation.schema.ts"
import { z } from 'zod';

const BaseModerationSchema = z.object({
moderatorId: z.string(),
targetUserId: z.string(),
reason: z.string().min(1),
});

export const BanSchema = BaseModerationSchema.extend({
  duration: z.number().positive().optional(),
});

export const MuteSchema = BaseModerationSchema.extend({
  duration:   z.number().positive(),
  channelIds: z.array(z.string()).optional(),
});
```
  </Tab>
</CodeTabs>

## Responsabilidades de reintento

El paquete _@spraxium/signal_ del lado del bot no incluye cola interna de reintentos ni worker. Si una validación Zod falla, el envelope se descarta y no se intenta reintento automático. Esto es intencional porque el bot debe mantenerse como consumidor determinista de eventos. La lógica de reintentos pertenece al lado emisor, donde _@spraxium/signal-client_ provee persistencia de fallback con backoff exponencial.

Esta separación mantiene cada lado enfocado en su responsabilidad. El bot valida y despacha envelopes confiables. El emisor maneja confiabilidad de entrega, programación de reintentos y monitoreo de dead-letter. Si necesitas reprocesar un envelope fallido, el emisor debe corregir la forma del payload y reenviarlo en lugar de que el bot tolere datos inválidos.

<Callout tone="warning" title="La propiedad de reintentos está del lado productor">
  Bot-side <code>@spraxium/signal</code> no reintenta payloads fallidos por
  diseño. Si necesitas reintentos de entrega, configúralos del lado emisor con
  ajustes de fallback de <code>@spraxium/signal-client</code> usando store de
  archivo o Redis.
</Callout>

## Testing con createSignalPayload

El paquete `@spraxium/signal` exporta un helper _createSignalPayload_ que construye envelopes sin firmar para testing. Este helper genera un UUID nonce y un timestamp actual, devolviendo un _UnsignedEnvelope_ utilizable en pruebas unitarias para verificar comportamiento del handler sin levantar todo el pipeline de Signal.

```typescript filename="test/guild-config.signal.test.ts"
import { createSignalPayload } from '@spraxium/signal';

const testEnvelope = createSignalPayload(
  'config.update',
  '123456789012345678',
  {
    prefix: '!',
    language: 'en',
  },
);

// testEnvelope has: v, event, guildId, nonce, sentAt, payload
// No signature field (unsigned, for testing only)
```
