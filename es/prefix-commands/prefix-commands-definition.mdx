## Separar estructura de ejecución

En Spraxium, los comandos con prefijo usan un patrón de dos clases. El decorador _@PrefixCommand_ marca una clase como definición de comando que describe el nombre, los alias, el esquema de argumentos y los metadatos. El decorador _@PrefixCommandHandler_ marca una clase separada que contiene el método _handle_ con la lógica real de ejecución. Esta separación mantiene estable el contrato del comando mientras te permite evolucionar el comportamiento del handler de forma independiente.

La clase de comando actúa como contenedor de metadatos. Declara cómo se llama el comando, qué argumentos espera y cómo aparece en la salida de ayuda. La clase handler es donde inyectas servicios, interactúas con Discord y generas respuestas. Esta división también habilita múltiples handlers para el mismo comando mediante el mecanismo de enrutamiento de subcomandos, donde cada subcomando obtiene su propio handler enfocado.

Ambas clases deben registrarse en el mismo módulo. Las clases de comando van en el arreglo _commands_ y las clases handler van en el arreglo _handlers_. Si solo se registran comandos, nada se ejecuta porque no hay handler que llamar. Si solo se registran handlers, no hay esquema de comando para que el registro lo indexe, así que el parser no puede resolver el nombre del comando.

## Un comando simple

El comando con prefijo más simple necesita una clase de comando con esquema de argumentos y una clase handler con un método _handle_. La clase de comando usa decoradores de método _@PrefixArg_ sobre un método _build_ para declarar argumentos posicionales. La clase handler usa decoradores de parámetro _@PrefixArg_ sobre el método _handle_ para recibir los valores parseados.

<CodeTabs>
  <Tab label="Command" language="typescript">
```typescript filename="src/modules/fun/commands/roll.command.ts"
import { PrefixArg, PrefixCommand } from '@spraxium/common';

@PrefixCommand({
  name: 'roll',
  aliases: ['r', 'dice'],
  description: 'Roll one or more dice.',
  category: 'Fun',
  usage: '!roll [sides] [count]',
  cooldown: 3,
})
export class RollCommand {
  @PrefixArg.Integer('sides', { required: false, min: 2, max: 1000 })
  @PrefixArg.Integer('count', { required: false, min: 1, max: 25 })
  build() {}
}

````
  </Tab>
  <Tab label="Handler" language="typescript">
```typescript filename="src/modules/fun/handlers/roll-command.handler.ts"
import { Ctx, PrefixArg, PrefixCommandHandler } from '@spraxium/common';
import type { Message } from 'discord.js';
import { RollCommand } from '../commands/roll.command';

@PrefixCommandHandler(RollCommand)
export class RollHandler {
  async handle(
    @Ctx() message: Message,
    @PrefixArg('sides') sides: number | undefined,
    @PrefixArg('count') count: number | undefined,
  ): Promise<void> {
    const faces = sides ?? 6;
    const rolls = count ?? 1;
    const results = Array.from({ length: rolls }, () =>
      Math.floor(Math.random() * faces) + 1, );
    const total = results.reduce((a, b) => a + b, 0);
    await message.reply(`Rolled ${rolls}d${faces}: [${results.join(', ')}] = ${total}`);
  }
}
````

  </Tab>
</CodeTabs>

Los decoradores de método _@PrefixArg_ en la clase de comando definen el esquema de argumentos. Se apilan de arriba hacia abajo para determinar el orden posicional: el primer decorador se convierte en la posición 0, el segundo en la posición 1, y así sucesivamente. En el handler, los decoradores de parámetro _@PrefixArg('name')_ inyectan el valor parseado por nombre. El decorador _@Ctx_ inyecta el objeto _Message_ sin procesar.

## Enrutamiento de subcomandos

Para familias de comandos como `!mod warn`, `!mod kick` y `!mod ban`, usa _@PrefixSubcommand_ para definir cada ruta en la clase de comando y conecta cada ruta con un handler dedicado mediante _@PrefixCommandHandler_ con una opción _subcommand_. El primer token de argv después del nombre del comando se compara con los nombres de subcomandos registrados, y el framework enruta automáticamente.

<CodeTabs>
  <Tab label="Command" language="typescript">
```typescript filename="src/modules/moderation/commands/mod.command.ts"
import { PrefixArg, PrefixCommand, PrefixSubcommand } from '@spraxium/common';

@PrefixCommand({
  name: 'mod',
  aliases: ['m'],
  description: 'Moderation commands.',
  category: 'Moderation',
  usage: '!mod <warn|kick|ban> <user> [reason]',
})
export class ModCommand {
  @PrefixSubcommand({ name: 'warn', description: 'Warn a user' })
  @PrefixArg.User('target')
  @PrefixArg.Rest('reason', { required: false })
  warn() {}

  @PrefixSubcommand({ name: 'kick', description: 'Kick a user' })
  @PrefixArg.User('target')
  @PrefixArg.Rest('reason', { required: false })
  kick() {}

  @PrefixSubcommand({ name: 'ban', description: 'Ban a user' })
  @PrefixArg.User('target')
  @PrefixArg.Rest('reason', { required: false })
  ban() {}
}

````
  </Tab>
  <Tab label="Warn Handler" language="typescript">
```typescript filename="src/modules/moderation/handlers/mod-warn-command.handler.ts"
import { Ctx, PrefixArg, PrefixCommandHandler, UseGuards } from '@spraxium/common';
import type { Message } from 'discord.js';
import { ModCommand } from '../commands/mod.command';
import { ModeratorGuard } from '../guards/moderator.guard';

@UseGuards(ModeratorGuard)
@PrefixCommandHandler(ModCommand, { subcommand: 'warn' })
export class ModWarnHandler {
  async handle(
    @Ctx() message: Message,
    @PrefixArg('target') userId: string,
    @PrefixArg('reason') reason: string | undefined,
  ): Promise<void> {
    const text = reason ?? 'No reason provided';
    await message.reply(`Warning <@${userId}>. Reason: ${text}`);
  }
}
````

  </Tab>
</CodeTabs>

Cada método de subcomando en la clase de comando define su propio esquema de argumentos. El subcomando _warn_ espera una mención de usuario seguida de texto libre opcional, mientras que _kick_ y _ban_ siguen la misma forma. Cada subcomando obtiene su propia clase handler, lo que significa que puedes aplicar guards distintos, inyectar servicios distintos y manejar errores de forma independiente por subcomando.

## Configuración de @PrefixCommand

El decorador _@PrefixCommand_ acepta un objeto de configuración que controla cómo aparece el comando en la salida de ayuda, cómo se activa y qué límites operativos tiene. Todos los campos excepto _name_ son opcionales, pero proporcionar _description_, _usage_ y _category_ mejora notablemente la salida de cualquier implementación de comando de ayuda.

<DropdownGroup>
  <Dropdown title="name (string, required)">
    El disparador principal del comando que los usuarios escriben después del prefijo. Cuando un usuario envía `!ping`, el parser elimina el prefijo, lee `ping` y busca un comando registrado con ese nombre. Cada comando debe tener un nombre único; si dos comandos comparten el mismo nombre, el último registrado ocultará al primero.
  </Dropdown>
  <Dropdown title="aliases (string[])">
    Nombres de activación alternativos que resuelven al mismo comando y handler. Definir `aliases: ['p', 'latency']` significa que `!p` y `!latency` funcionan igual que `!ping`. Los alias comparten el mismo pool de cooldown que el nombre principal, así que si un usuario está en cooldown por `!ping` también queda bloqueado para usar `!p`.
  </Dropdown>
  <Dropdown title="description (string)">
    Una línea breve que describe qué hace el comando, usada en la salida del comando de ayuda. El framework no la muestra automáticamente; está disponible mediante el método *getCommandInfo* del dispatcher para que tu propio handler de ayuda le dé formato. Mantener descripciones concisas y consistentes entre comandos mejora la calidad de los embeds de ayuda del bot.
  </Dropdown>
  <Dropdown title="usage (string)">
    Un string legible para humanos que muestra el formato de invocación esperado, como `!ban <user> [reason]`. El framework lo guarda en los metadatos del comando y lo devuelve como parte de *getCommandInfo*, pero no lo parsea ni valida automáticamente. Úsalo en embeds de ayuda y en mensajes de *ArgumentException* para que los usuarios conozcan la sintaxis correcta cuando falle el parsing.
  </Dropdown>
  <Dropdown title="category (string)">
    Una etiqueta de agrupación para organizar comandos en la salida de ayuda. Los comandos de la misma categoría suelen mostrarse juntos en embeds de ayuda. El framework no aplica categorías ni asigna comportamiento especial a partir de ellas; son metadatos puros que tu handler de ayuda lee desde *getCommandInfo*.
  </Dropdown>
  <Dropdown title="cooldown (number)">
    Un cooldown por comando en segundos que sobrescribe el *defaultCooldown* global de *PrefixConfig*. Cuando un usuario ejecuta el comando, el framework registra la marca de tiempo y bloquea ejecuciones posteriores hasta que expire el cooldown. Definir `cooldown: 0` desactiva el cooldown para ese comando sin importar el valor global.
  </Dropdown>
</DropdownGroup>

## Registro en módulo

Tanto las clases de comando como las clases handler deben registrarse en un módulo para que el framework las descubra durante el bootstrap. La clase de comando va en el arreglo _commands_ y la clase handler va en el arreglo _handlers_. El framework procesa ambos arreglos durante la carga del módulo, registra los metadatos de comando en el _PrefixRegistry_ y conecta las instancias handler mediante el contenedor DI.

```typescript filename="src/modules/moderation/moderation.module.ts"
import { Module } from '@spraxium/common';
import { ModCommand } from './commands/mod.command';
import { RollCommand } from '../fun/commands/roll.command';
import { ModWarnHandler } from './handlers/mod-warn.handler';
import { ModKickHandler } from './handlers/mod-kick.handler';
import { ModBanHandler } from './handlers/mod-ban.handler';
import { RollHandler } from '../fun/handlers/roll.handler';

@Module({
  commands: [ModCommand, RollCommand],
  handlers: [ModWarnHandler, ModKickHandler, ModBanHandler, RollHandler],
})
export class ModerationModule {}
```
