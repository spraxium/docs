## Hacer configurables los guards con @GuardOption

Algunos guards necesitan parámetros para funcionar. Un role guard necesita saber qué roles revisar, un cooldown guard necesita la ventana de tiempo y un permission guard necesita qué permisos exigir. En lugar de hardcodear estos valores dentro de la clase guard, declaras propiedades configurables con el decorador _@GuardOption_ y pasas valores cuando adjuntas el guard.

El decorador _@GuardOption_ acepta un objeto de configuración con dos campos opcionales. El campo _required_ vuelve obligatoria la opción, lo que significa que el framework lanza un error de configuración en runtime si no se proporciona. El campo _default_ define un valor de respaldo que se aplica cuando no se pasa uno explícitamente. Si no defines ni _required_ ni _default_, la opción simplemente es opcional y será undefined si no se proporciona.

```typescript filename="min-roles.guard.ts"
import { Guard, GuardOption } from '@spraxium/common';
import type { ExecutionContext, SpraxiumGuard } from '@spraxium/common';

@Guard()
export class MinRolesGuard implements SpraxiumGuard {
  @GuardOption({ default: 1 })
  minRoles!: number;

  canActivate(ctx: ExecutionContext): boolean {
    const member = ctx.getMember();
    if (!member || !('roles' in member)) return false;
    return member.roles.cache.size >= this.minRoles;
  }
}
```

En el ejemplo anterior, la propiedad _minRoles_ tiene valor por defecto 1, así que si adjuntas este guard sin especificar valor, exigirá al menos un rol. Si quieres un umbral distinto, lo pasas mediante _withOptions_ al adjuntar el guard.

## El helper withOptions

La función _withOptions_ es la forma de pasar opciones tipadas a un guard al adjuntarlo con _@UseGuards_. Recibe la clase guard como primer argumento y un objeto de opciones como segundo. El sistema de tipos de TypeScript infiere la forma de las opciones a partir de las propiedades _@GuardOption_ del guard, así que obtienes autocompletado y errores de tipo si pasas una forma incorrecta.

```typescript filename="moderation.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { PermissionGuard, RoleGuard } from '@spraxium/core';
import { MinRolesGuard } from '../guards/min-roles.guard';

@UseGuards(
  withOptions(RoleGuard, { roles: ['Moderator'] }),
  withOptions(PermissionGuard, { permissions: ['BanMembers'] }),
  withOptions(MinRolesGuard, { minRoles: 3 }),
)
export class ModerationHandler {
  async handle() {
    // all three guards must pass before this runs
  }
}
```

Si no necesitas pasar opciones porque el guard no tiene opciones obligatorias o sus valores por defecto son suficientes, puedes pasar la clase guard directamente sin _withOptions_. Ambos estilos funcionan dentro de la misma llamada a _@UseGuards_, así que puedes mezclar guards que requieren opciones con guards que no.

```typescript filename="mixed-guards.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly, RoleGuard } from '@spraxium/core';

@UseGuards(GuildOnly, withOptions(RoleGuard, { roles: ['Admin'] }))
export class MixedHandler {
  async handle() {
    // GuildOnly needs no options, RoleGuard needs roles
  }
}
```

## Guards integrados

Spraxium incluye diez guards integrados en el paquete core que cubren los patrones de acceso más comunes en Discord. Cada guard ya está decorado con _@Guard()_ y listo para usar con _@UseGuards_ o _useGlobalGuards_. El bloque siguiente muestra cada guard integrado, qué comprueba y qué opciones espera.

<DropdownGroup>
<Dropdown title="GuildOnly">
  Deniega la ejecución cuando el comando se invoca desde un canal de mensaje directo. Este es el guard más usado para asegurar que comandos exclusivos de servidor no puedan activarse desde DMs. No requiere opciones y puede pasarse directamente a *@UseGuards* sin *withOptions*.
</Dropdown>

<Dropdown title="DMOnly">
  Deniega la ejecución cuando el comando se invoca dentro de un canal de guild.
  Es el inverso de *GuildOnly* y restringe comandos únicamente a contextos de
  mensaje directo. No requiere opciones y puede pasarse directamente a
  *@UseGuards*.
</Dropdown>

<Dropdown title="OwnerOnly">
  Deniega la ejecución cuando el ID del usuario no está presente en la lista de
  owners configurada. Este guard requiere la opción *ownerIds*, que es un
  `string[]` de IDs snowflake de usuario de Discord. Usa *withOptions* para
  pasar los owner IDs al adjuntar este guard.
</Dropdown>

<Dropdown title="PermissionGuard">
  Deniega la ejecución cuando el miembro de guild no tiene alguno de los
  permisos de Discord requeridos. Este guard requiere la opción *permissions*,
  que es un `PermissionsString[]` usando cadenas de permisos de discord.js como
  `"BanMembers"` o `"ManageGuild"`. El miembro debe tener todos los permisos
  listados para que el guard pase.
</Dropdown>

<Dropdown title="RoleGuard">
  Deniega la ejecución cuando el miembro de guild no tiene ninguno de los roles
  especificados. Este guard requiere la opción *roles*, que es un `string[]` de
  nombres de rol o IDs snowflake de rol. El miembro necesita al menos un rol
  coincidente para que el guard pase.
</Dropdown>

<Dropdown title="CooldownGuard">
  Deniega la ejecución cuando el usuario activó el mismo comando dentro de la
  ventana de cooldown. Este guard requiere la opción *cooldown*, que es un
  `number` en milisegundos. Registra el timestamp de la última ejecución por
  usuario y bloquea invocaciones repetidas hasta que la ventana expire.
</Dropdown>

<Dropdown title="NoBotGuard">
  Deniega la ejecución cuando el usuario que activa el comando es una cuenta
  bot. Este guard es útil cuando tus listeners o prefix commands deben ignorar
  mensajes de otros bots. No requiere opciones y puede pasarse directamente a
  *@UseGuards*.
</Dropdown>

<Dropdown title="NSFWGuard">
  Deniega la ejecución cuando el canal no está marcado como NSFW en la
  configuración del servidor de Discord. Usa este guard para contenido con
  restricción de edad que solo debe aparecer en canales designados. No requiere
  opciones y puede pasarse directamente a *@UseGuards*.
</Dropdown>

<Dropdown title="ThreadOnlyGuard">
  Deniega la ejecución cuando el canal no es un thread. Este guard es útil para
  comandos que solo deberían correr dentro de conversaciones en thread, como
  sistemas basados en tickets. No requiere opciones y puede pasarse directamente
  a *@UseGuards*.
</Dropdown>

<Dropdown title="VoiceChannelGuard">
  Deniega la ejecución cuando el miembro de guild no está conectado a un canal de voz. Usa este guard para comandos que requieren conexión de voz, como reproducción de música o funcionalidades basadas en voz. No requiere opciones y puede pasarse directamente a *@UseGuards*.
</Dropdown>
</DropdownGroup>

## Uso de guards integrados

Los guards integrados sin opciones pueden pasarse directamente a _@UseGuards_ o _useGlobalGuards_. Los guards con opciones obligatorias deben usar _withOptions_ o el segundo parámetro de _useGlobalGuards_. Aquí tienes ejemplos prácticos con los patrones más comunes.

<CodeTabs>
  <Tab label="Registro global" language="typescript">
```typescript filename="src/main.ts"
import { SpraxiumFactory } from '@spraxium/core';
import { NoBotGuard, OwnerOnly, CooldownGuard } from '@spraxium/core';

const app = await SpraxiumFactory.create({ token: process.env.DISCORD_TOKEN! });

app.useGlobalGuards(NoBotGuard);
app.useGlobalGuards(OwnerOnly, { ownerIds: ['123456789'] });
app.useGlobalGuards(CooldownGuard, { cooldown: 3000 });

await app.listen();

````
  </Tab>
  <Tab label="Clase y método" language="typescript">
```typescript filename="moderation.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly, PermissionGuard, RoleGuard } from '@spraxium/core';

@UseGuards(
  GuildOnly,
  withOptions(RoleGuard, { roles: ['Moderator', 'Admin'] }),
)
export class ModerationHandler {
  @UseGuards(withOptions(PermissionGuard, { permissions: ['BanMembers'] }))
  async handleBan() {
    // guild + role check on class, permission check on this method only
  }

  async handleWarn() {
    // only guild + role check from the class guard
  }
}
````

  </Tab>
</CodeTabs>

El _RoleGuard_ comprueba si el miembro tiene al menos uno de los roles listados. Puedes pasar nombres de rol como "Moderator" o IDs snowflake de rol como "1234567890". El _PermissionGuard_ comprueba si el miembro tiene todos los permisos listados, usando cadenas de permisos de Discord.js como "BanMembers", "ManageGuild" o "Administrator".

## Crear un guard personalizado con opciones

Cuando los guards integrados no cubren tu caso de uso, creas un guard personalizado que declara propiedades configurables mediante _@GuardOption_. La clase guard define qué parámetros necesita, y cada lugar donde se usa aporta valores concretos mediante _withOptions_. Este patrón es cómo funcionan internamente guards integrados como _RoleGuard_ y _CooldownGuard_, y sigues exactamente el mismo enfoque para tus propios guards.

<Steps>
  <Step title="Define la clase guard con @Guard">
    Empieza con una clase decorada con *@Guard()* que implemente
    *SpraxiumGuard*. El método *canActivate* contiene la lógica de comprobación,
    y cualquier parámetro configurable recibe el decorador *@GuardOption* en su
    propiedad. Marca opciones como *required* cuando el guard no puede funcionar
    sin ellas, o define un *default* cuando exista un valor de respaldo
    razonable. El framework lee estos decoradores en el momento de instanciación
    y rellena los valores antes de que *canActivate* llegue a ejecutarse.
  </Step>
  <Step title="Pasa opciones con withOptions en cada punto de uso">
    Al adjuntar el guard con *@UseGuards*, envuélvelo en *withOptions* y pasa
    los valores concretos que espera tu guard. TypeScript infiere la forma de
    las opciones a partir de las propiedades *@GuardOption*, así que obtienes
    autocompletado y errores en compilación si pasas un tipo incorrecto. Si
    olvidas una opción *required*, el framework lanza un error de configuración
    claro durante el bootstrap.
  </Step>
  <Step title="Reutiliza el mismo guard con valores diferentes">
    El poder de los guards configurables es que una sola clase sirve para muchos
    escenarios. Un *MinAccountAgeGuard* con *minDays: 7* en un comando general y
    *minDays: 90* en un comando de giveaway usa la misma clase con umbrales
    distintos. No necesitas clases guard separadas para cada umbral.
  </Step>
</Steps>

Aquí tienes un ejemplo completo de un guard personalizado que comprueba una edad mínima de cuenta y soporta múltiples opciones configurables. El guard tiene una opción obligatoria y otra opcional con valor por defecto.

<CodeTabs>
  <Tab label="Guard" language="typescript">
```typescript filename="min-account-age.guard.ts"
import { Guard, GuardOption } from '@spraxium/common';
import type { ExecutionContext, SpraxiumGuard } from '@spraxium/common';

@Guard()
export class MinAccountAgeGuard implements SpraxiumGuard {
  @GuardOption({ required: true })
  minDays!: number;

  @GuardOption({ default: false })
  allowBots!: boolean;

  canActivate(ctx: ExecutionContext): boolean {
    const user = ctx.getUser();
    if (user.bot && !this.allowBots) return false;

    const createdAt = user.createdAt.getTime();
    const ageInDays = (Date.now() - createdAt) / (1000 * 60 * 60 * 24);
    return ageInDays >= this.minDays;
  }
}

````
  </Tab>
  <Tab label="Uso" language="typescript">
```typescript filename="giveaway.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly } from '@spraxium/core';
import { MinAccountAgeGuard } from '../guards/min-account-age.guard';

@UseGuards(
  GuildOnly,
  withOptions(MinAccountAgeGuard, { minDays: 30 }),
)
export class GiveawayHandler {
  async handle() {
    // only human accounts older than 30 days can participate
  }
}
````

  </Tab>
  <Tab label="Umbrales diferentes" language="typescript">
```typescript filename="verification.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { MinAccountAgeGuard } from '../guards/min-account-age.guard';

@UseGuards(withOptions(MinAccountAgeGuard, { minDays: 7, allowBots: true }))
export class VerificationHandler {
  async handle() {
    // only 7 days required here, bots allowed
  }
}

```
  </Tab>
</CodeTabs>

Observa que el guard tiene dos opciones: *minDays* es obligatoria porque el guard no puede funcionar sin conocer el umbral, y *allowBots* tiene valor por defecto false porque la mayoría de los puntos de uso quieren bloquear bots. La tercera pestaña muestra cómo la misma clase guard acepta una configuración completamente distinta en otro punto de uso sin duplicar código.

<Callout tone="info" title="Empieza por los integrados">
  Antes de crear un guard personalizado, revisa si uno de los diez guards
  integrados ya cubre tu caso de uso. Los guards personalizados son potentes,
  pero innecesarios cuando un integrado ya hace exactamente lo que necesitas.
</Callout>
