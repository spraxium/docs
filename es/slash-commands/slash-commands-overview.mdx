## Qué son los slash commands

Los slash commands son el modelo de interacción nativo que Discord introdujo para reemplazar el análisis de texto no estructurado. Cuando un usuario escribe `/` en un canal de texto, Discord muestra un menú de comandos con búsqueda de los comandos que el bot registró, con parámetros tipados, descripciones y validación en línea. El usuario selecciona un comando, completa las opciones y Discord entrega un _ChatInputCommandInteraction_ estructurado al proceso del bot. El framework nunca tiene que analizar texto de mensajes en bruto, adivinar límites de argumentos ni manejar errores tipográficos en nombres de comandos porque Discord mismo aplica el esquema antes de que la interacción llegue al bot.

Spraxium implementa los slash commands como un subsistema impulsado por decoradores y metadatos con una separación estricta entre _definición_ y _ejecución_. Una clase de definición decorada con _@SlashCommand_ declara el esquema del comando, su nombre, descripción, opciones, permisos y jerarquía de subcomandos. Una clase handler separada, decorada con _@SlashCommandHandler_, implementa la lógica de negocio y recibe valores de parámetros tipados mediante inyección de dependencias. Esta separación permite que el esquema evolucione de forma independiente de la lógica del handler, y que una sola definición de comando tenga múltiples handlers cuando hay subcomandos.

El subsistema de slash commands comparte el mismo contenedor de inyección de dependencias, pipeline de guards, exception handler y sistema de módulos que el resto del framework. Tus clases handler pueden inyectar servicios, aplicar _@UseGuards_ para comprobaciones de permisos y aprovechar respuestas de error estructuradas sin configuración especial más allá de registrar comandos y handlers en un módulo.

<Callout tone="info" title="DI, guards y excepciones funcionan de forma nativa">
  Los handlers de slash commands son ciudadanos completos del framework. Puedes
  inyectar cualquier servicio registrado mediante el constructor, encadenar
  varios guards con *@UseGuards* y lanzar excepciones tipadas que el exception
  handler integrado convierte en respuestas estructuradas de Discord. No se
  requiere cableado adicional más allá de declarar la clase handler dentro de
  un módulo.
</Callout>

## Separación comando-handler

La decisión arquitectónica central del subsistema de slash commands es que el _esquema_ del comando y la _lógica_ del comando viven en clases separadas. No es un patrón opcional; el framework lo aplica mediante claves de metadatos. El decorador _@SlashCommand_ escribe metadatos de esquema en la clase, y el decorador _@SlashCommandHandler_ escribe metadatos de ejecución en otra clase que referencia la clase de comando. El runtime lee ambos conjuntos de metadatos al cargar el módulo y los conecta en el registro.

Esta separación aporta tres beneficios prácticos. Primero, la clase de esquema se convierte en una declaración pura que puede importarse en handlers de autocomplete, fixtures de pruebas y generadores de documentación sin arrastrar lógica de negocio ni dependencias de servicios. Segundo, la clase handler tiene acceso al contenedor completo de inyección de dependencias, por lo que puede declarar parámetros de constructor para servicios, repositorios y otros providers que el contenedor DI resuelve automáticamente. Tercero, cuando un comando usa subcomandos, cada subcomando recibe su propia clase handler, manteniendo archivos pequeños y enfocados.

<CodeTabs defaultIndex={0}>
  <Tab label="Command" language="typescript">
```typescript filename="commands/ping.command.ts"
import { SlashCommand, SlashOption } from '@spraxium/common';

@SlashCommand({
  name: 'ping',
  description: 'Check bot latency or ping a specific service.'
})
export class PingCommand {
  @SlashOption.String('service', {
    description: 'Service to check latency for',
    required: false,
    autocomplete: true
  })
  build() {}
}

````
  </Tab>
  <Tab label="Handler" language="typescript">
```typescript filename="handlers/ping.handler.ts"
import { Ctx, SlashCommandHandler, SlashOpt } from '@spraxium/common';
import type { ChatInputCommandInteraction } from 'discord.js';
import { PingCommand } from '../commands/ping.command';

@SlashCommandHandler(PingCommand)
export class PingHandler {
  async handle(
    @Ctx() interaction: ChatInputCommandInteraction,
    @SlashOpt('service') service: string | null,
  ): Promise<void> {
    const ws = interaction.client.ws.ping;
    if (service) {
      await interaction.reply(`Service: ${service}, Latency: ${ws}ms`);
    } else {
      await interaction.reply(`Pong! ${ws}ms`);
    }
  }
}
````

  </Tab>
</CodeTabs>

## Registro en módulos

Los comandos y handlers se registran mediante el decorador _@Module_, usando el arreglo _commands_ para clases de definición y el arreglo _handlers_ para clases handler. El cargador de módulos lee estos arreglos durante el bootstrap, instancia clases handler mediante el contenedor DI y las conecta con sus definiciones de comando automáticamente.

```typescript filename="modules/slash/slash.module.ts"
import { Module } from '@spraxium/common';
import { PingCommand } from './commands/ping.command';
import { BanCommand } from './commands/ban.command';
import { PingHandler } from './handlers/ping.handler';
import { PingServiceAutocomplete } from './handlers/ping-service.autocomplete';
import { BanHandler } from './handlers/ban.handler';

@Module({
  commands: [PingCommand, BanCommand],
  handlers: [PingHandler, PingServiceAutocomplete, BanHandler],
})
export class SlashModule {}
```

El orden de las entradas en los arreglos no importa. El framework usa reflexión de metadatos para asociar handlers con sus definiciones de comando después de procesar todos los registros. Si un handler referencia un comando que no está en el arreglo _commands_ de ningún módulo cargado, el handler se ignora silenciosamente durante el enlace.

## Forzar el registro manual de comandos

Durante la secuencia de arranque normal, el framework registra slash commands automáticamente después de que el cliente se conecta. En modo desarrollo omite la llamada REST cuando los comandos no cambiaron desde la ejecución anterior, evitando llamadas innecesarias a la API de Discord. Si alguna vez necesitas forzar un registro fresco sin reiniciar todo el bot, la aplicación expone _forceRegisterSlashCommands_ exactamente para ese propósito.

Este método envía todos los payloads de comandos actuales a la API REST de Discord sin condiciones. No hace nada si la aplicación aún no terminó de arrancar o si no hay slash commands registrados. Puedes llamarlo desde un script de CLI, un handler de comando de administración o cualquier servicio que tenga acceso a la instancia de la aplicación.

```typescript filename="src/main.ts"
import { SpraxiumFactory } from '@spraxium/core';

const app = await SpraxiumFactory.create();
await app.listen();

// Force re-registration from an admin command or script
await app.forceRegisterSlashCommands();
```

Coloca los archivos de definición de comandos en una subcarpeta `commands/` y los archivos handler en una subcarpeta `handlers/` dentro del directorio del módulo. Nombra los archivos handler según el comando o subcomando que gestionan con el sufijo `.handler.ts`, y los handlers de autocomplete con el sufijo `.autocomplete.ts`. El archivo del módulo registra ambos arreglos y actúa como punto único de importación para el módulo principal de la aplicación.
