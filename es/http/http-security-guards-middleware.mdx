## La seguridad empieza antes de los controladores

_HttpServer_ aplica middleware de seguridad antes de invocar cualquier handler de controlador. Este cableado en tiempo de startup da a cada endpoint la misma política base desde la primera request, sin requerir decoraciones explícitas en cada ruta. El stack de seguridad corre en un orden fijo que el código de usuario no puede reordenar, asegurando que el hardening de headers y los límites de body sean siempre la primera línea de defensa.

Cuando HTTP está habilitado, el runtime conecta estas protecciones en esta secuencia exacta:

1. Remoción opcional de headers `X-Powered-By` y `Server` (_hidePoweredBy_, por defecto `true`).
2. _SecurityHeadersMiddleware_ envolviendo _secureHeaders_ de Hono (a menos que `headers` sea `false`).
3. _CorsMiddleware_ envolviendo _cors_ de Hono (solo cuando `security.cors` está configurado).
4. _BodyLimitMiddleware_ envolviendo _bodyLimit_ de Hono (a menos que `bodyLimit` sea `false`).
5. Instancias globales de middleware desde _@HttpClientModule({ middleware })_.
6. Guards globales desde _@HttpClientModule({ guards })_ a través de _GuardExecutor_.
7. Guards por controlador y por ruta desde _@HttpGuards_ a través de _GuardExecutor_.

Después de este stack, se ejecuta el middleware de nivel ruta desde decoradores _@HttpUseMiddleware_ y finalmente se ejecuta el propio handler. Este modelo por capas implica que las decisiones de guard suceden después del hardening base y que tus decisiones de middleware ocurren cuando los headers de seguridad ya están establecidos.

## Valores de seguridad por defecto

Cada header y cada límite de seguridad tiene un valor seguro por defecto desde _SECURITY_DEFAULTS_. Solo necesitas sobrescribir valores cuando tu despliegue requiera otro comportamiento. Cuando se omite un subcampo, se aplica el valor por defecto. Cuando se establece en `false`, esa capa se desactiva por completo.

<DropdownGroup>
<Dropdown title="hidePoweredBy: true">
  Elimina los headers `X-Powered-By` y `Server` de cada respuesta. Esto evita el fingerprinting de framework y runtime que atacantes usan para identificar vulnerabilidades conocidas en versiones específicas de software. Mantén esto habilitado salvo que tengas un motivo concreto para exponer tu stack de servidor.
</Dropdown>

<Dropdown title="X-Frame-Options: DENY">
  Evita que la página de respuesta se incruste en un iframe desde cualquier
  dominio. Esto bloquea ataques de clickjacking donde un sitio malicioso
  superpone frames transparentes para engañar a usuarios y hacer clic en
  elementos ocultos. Establécelo en `SAMEORIGIN` si tus propias páginas deben
  incrustarse entre sí.
</Dropdown>

<Dropdown title="X-Content-Type-Options: nosniff">
  Evita que navegadores hagan MIME-sniffing y cambien la interpretación del
  header `Content-Type` declarado. Sin este header, navegadores podrían
  interpretar una respuesta JSON como HTML, abriendo la puerta a XSS por
  confusión de tipo de contenido. Este header no tiene variantes de
  configuración y debería estar siempre habilitado.
</Dropdown>

<Dropdown title="Strict-Transport-Security: max-age=31536000; includeSubDomains">
  Fuerza HTTPS a nivel de user-agent por un año con cobertura de subdominios.
  Después de la primera respuesta HTTPS, los navegadores rechazan conexiones por
  HTTP plano hasta que expire el max-age. Ajusta *hstsMaxAge* y
  *hstsIncludeSubDomains* en la configuración de seguridad si tu despliegue
  requiere valores distintos.
</Dropdown>

<Dropdown title="Content-Security-Policy: default-src 'none'">
  Aplica una política de confianza cero para carga de contenido, bloqueando
  scripts, estilos, imágenes y medios salvo que se permitan explícitamente. Esta
  es la CSP más estricta posible y es adecuada para servidores solo API que no
  sirven páginas HTML. Sobrescribe *contentSecurityPolicy* con una cadena de
  directivas personalizada si tus endpoints sirven contenido renderizado en
  navegador.
</Dropdown>

<Dropdown title="Referrer-Policy: no-referrer">
  Suprime el header `Referer` en todas las solicitudes salientes originadas por
  la página de respuesta. Esto evita filtrar rutas URL y parámetros query a
  servicios de terceros. Usa `strict-origin-when-cross-origin` si tu analítica o
  CDN requiere información de referrer.
</Dropdown>

<Dropdown title="X-XSS-Protection: 1; mode=block">
  Habilita filtros XSS heredados de navegador en modo bloqueo, instruyendo al
  navegador a detener el renderizado de la página si detecta un ataque XSS
  reflejado. Navegadores modernos dependen de CSP, pero este header aporta una
  capa adicional de defensa para user agents antiguos. No hay desventaja en
  mantenerlo habilitado.
</Dropdown>

<Dropdown title="Permissions-Policy: camera=(), microphone=(), geolocation=()">
  Deniega por defecto acceso a APIs sensibles del navegador como cámara,
  micrófono y geolocalización. Esto impide que scripts maliciosos accedan al
  hardware del dispositivo incluso si burlan restricciones de CSP. Amplía la
  lista de políticas si tus respuestas API se consumen desde páginas de
  navegador que necesitan permisos específicos.
</Dropdown>

<Dropdown title="Cross-Origin-Opener-Policy: same-origin">
  Aísla el contexto de navegación para prevenir ataques cross-origin como
  Spectre que explotan memoria de proceso compartida. Cuando se establece en
  `same-origin`, la página no puede compartir grupo de contexto de navegación
  con documentos cross-origin. Este es el valor por defecto recomendado para
  cualquier servidor que maneje datos sensibles.
</Dropdown>

<Dropdown title="Body limit: 102400 bytes (100 KB)">
  Rechaza payloads de request que exceden el tamaño máximo configurado con estado 413 y una respuesta de error estructurada. El valor por defecto de 100 KB es adecuado para la mayoría de endpoints API que aceptan JSON. Sobrescribe *bodyLimit.maxSize* en la configuración de seguridad para endpoints que manejan cargas de archivos o payloads grandes.
</Dropdown>
</DropdownGroup>

## Pipeline de guards y la interfaz HttpGuard

Los guards son el límite de autenticación y autorización. Cada guard implementa la interfaz _HttpGuard_, que define un único método: `canActivate(ctx: Context): Promise<boolean>`. Los guards declarados en _@HttpClientModule({ guards })_ se instancian mediante el sistema de inyección de dependencias en startup y se ejecutan secuencialmente a través de _GuardExecutor_ en cada request, después del stack de middleware de seguridad. No se requiere ninguna llamada manual a `new` al declarar guards en el módulo.

Cuando _GuardExecutor_ encuentra un guard que retorna `false`, corta la ejecución inmediatamente y define la respuesta como `{ ok: false, error: 'Unauthorized' }` con estado 401. No se ejecutan más guards, middleware ni handlers. Este comportamiento de short-circuit implica que el orden de guards importa: coloca primero el caso de rechazo más común para evitar ejecutar verificaciones costosas en requests no autenticadas.

La respuesta 401 por rechazo de guard se inyecta directamente, no a través del handler _onError_. Esto significa que los fallos de guard son finales y no pueden ser capturados ni modificados por middleware posterior. La forma de respuesta coincide con el mismo envelope usado por el resto de respuestas de error, así que los clientes no necesitan manejo especial para rechazos por guard.

## @HttpGuards para protección por controlador y por ruta

_@HttpGuards_ es un decorador de clase o método que acota el alcance de guards a un controlador específico o a una ruta individual. A diferencia de los guards globales que protegen todos los endpoints, _@HttpGuards_ apunta a un punto concreto de la superficie de routing. El decorador acepta una o más clases guard cuyas instancias se resuelven mediante el mismo sistema DI que servicios y controladores.

_@HttpGuards_ a nivel de clase se ejecuta en todas las rutas del controlador. _@HttpGuards_ a nivel de método se ejecuta solo en ese handler específico. Cuando existen ambos niveles, primero se ejecutan guards de clase y luego guards de método. Esta superposición te permite proteger todo un controlador con una política común y agregar validación extra por ruta sin repetir el guard compartido.

<CodeTabs defaultIndex={0}>

## ApiKeyGuard en detalle

*ApiKeyGuard* es el guard integrado que trae el paquete. Lee el header `x-api-key` de la request y lo compara con el valor provisto al construirse. La comparación usa `timingSafeEqual` del módulo `crypto` de Node para prevenir ataques de timing que podrían filtrar información sobre longitud o prefijo de la clave.

El guard rechaza requests en tres escenarios: header faltante (retorna `false` de inmediato), longitud de buffer distinta (retorna `false` sin comparar para evitar el requisito de igual longitud de `timingSafeEqual`) y valores que no coinciden (retorna `false` tras comparación de tiempo constante). Esta estrategia de rechazo por capas evita exponer la longitud de la clave por diferencias de tiempo de respuesta.

*ApiKeyGuard* se activa automáticamente cuando `apiKey` tiene valor en *defineHttp*. El runtime crea y registra internamente la instancia del guard, por lo que no necesitas declararlo en *@HttpClientModule({ guards })*. El arreglo `guards` queda reservado para guards personalizados que requieren tus propias dependencias resueltas por DI.

## Modelo de ejecución de middleware

El paquete soporta dos puntos de entrada de middleware con distintos alcances y mecanismos de registro.

Las instancias globales de middleware se declaran en *@HttpClientModule({ middleware })* como un arreglo de objetos *HttpMiddleware*. Se registran sobre el path Hono `'*'`, lo que significa que se ejecutan en cada request después del stack de seguridad y antes de la ejecución de guards. Usa middleware global para preocupaciones transversales que aplican sin condición, como request logging vía *LoggerMiddleware*.

El middleware de nivel ruta usa tokens de clase y el decorador *@HttpUseMiddleware*. El token de clase debe mapearse a una instancia concreta en *@HttpClientModule({ middlewareProviders })*. *RouteBuilder* resuelve el token durante el binding de rutas e inserta el handler middleware antes del handler de ruta en la cadena Hono. *@HttpUseMiddleware* de nivel clase se ejecuta antes de *@HttpUseMiddleware* de nivel método, y ambos se ejecutan después de middleware global y guards.

Todo middleware implementa la interfaz *HttpMiddleware*: `handle(ctx: Context, next: Next): Promise<undefined | Response>`. Llamar `await next()` transfiere el control al siguiente middleware o handler. No llamar `next()` termina la request en ese middleware, que es cómo *RateLimitMiddleware* rechaza requests que superan el límite.

## Referencia de middleware integrado

<DropdownGroup>
<Dropdown title="SecurityHeadersMiddleware: Automático">
  Envuelve *secureHeaders* de Hono y aplica todos los valores por defecto de headers desde *SECURITY_DEFAULTS.headers*. Este middleware forma parte del stack automático de seguridad y se ejecuta en cada request antes de cualquier handler de controlador. Configura headers individuales mediante *SecurityHeadersConfig* en el bloque *security.headers*.
</Dropdown>

<Dropdown title="CorsMiddleware: Automático">
  Envuelve *cors* de Hono y maneja requests preflight `OPTIONS` junto con headers `Access-Control-*`. Este middleware solo se activa cuando `security.cors` está configurado en la definición del plugin HTTP. Soporta arreglos de origen, wildcard, credenciales y max-age para cacheo de preflight.
</Dropdown>

<Dropdown title="BodyLimitMiddleware: Automático">
  Envuelve *bodyLimit* de Hono y rechaza payloads que exceden *maxSize* con estado 413 y una respuesta de error estructurada. El body de respuesta sigue el mismo envelope `{ ok: false, error: 'Payload too large', maxSize }` que el resto de respuestas de error. Desactívalo estableciendo `bodyLimit` en `false` dentro de la configuración de seguridad.
</Dropdown>

<Dropdown title="RateLimitMiddleware: Manual (global o por ruta)">
  Implementa un rate limiter de ventana deslizante en memoria que acepta configuración `{ windowMs, max }`. La identificación de cliente usa el header `x-forwarded-for`, con fallback a `'unknown'` cuando falta el header. Requests que exceden el límite reciben estado 429, y las entradas antiguas se eliminan de forma periódica.
</Dropdown>

<Dropdown title="LoggerMiddleware: Manual (global o por ruta)">
  Registra `METHOD path status durationMs` para cada request que lo atraviesa. Requests con status code 400 o superior se registran con nivel `warn` para facilitar filtrado en pipelines de observabilidad. No requiere configuración: solo instancia y registra en *HttpClientModule({ middleware })*.
</Dropdown>
</DropdownGroup>

## Estrategia de rate limiting

*RateLimitMiddleware* implementa un rate limiter de ventana deslizante en memoria. Cada cliente se identifica por el valor del header `x-forwarded-for`, o `'unknown'` cuando falta ese header. El middleware mantiene un `Map<string, WindowEntry>` donde cada entrada registra el conteo de requests y la marca de tiempo de inicio de ventana.

Cuando llega una request, el middleware verifica si la ventana actual expiró. Si expiró, reinicia la entrada. Si la ventana sigue activa y el conteo supera *max*, el middleware responde `{ ok: false, error: 'Too many requests' }` con estado 429 sin llamar `next()`. Un intervalo periódico de limpieza elimina entradas de clientes que no enviaron requests dentro de la duración de la ventana.

Para usar rate limiting por ruta, extiende *RateLimitMiddleware* con tu propia configuración y regístralo en *middlewareProviders*. Este patrón mantiene visible la configuración de límites en la clase middleware y evita números mágicos en argumentos de decoradores.

## Confianza de proxy e identificación IP

El middleware de rate-limit lee `x-forwarded-for` directamente sin verificar la fuente. En producción detrás de proxies reversos o balanceadores, esto significa que debes asegurar que tu infraestructura de proxy establezca correctamente ese header. Si el header falta, todas las requests se agrupan bajo la clave `'unknown'`, lo que en la práctica crea un único bucket global de rate limit. Si el header puede falsificarse porque el proxy no lo sobrescribe, atacantes pueden evadir límites enviando IPs falsas en headers.

La interfaz *SecurityConfig* incluye un campo *trustedProxies* con un arreglo *proxies* (por defecto `['127.0.0.1', '::1']`). Usa este campo para documentar tu configuración de proxies confiables y asegúrate de que tu arquitectura de despliegue solo permita a proxies confiables establecer headers de forwarding.

## Checklist de hardening operativo

<Steps>
  <Step title="Comienza con defaults seguros">
    Habilita headers base y límites de body salvo que exista un requisito claro para relajarlos. Una postura de denegación por defecto es más fácil de auditar que una postura permisiva parchada más tarde. Sobrescribe headers individuales solo cuando tu despliegue lo requiera.
  </Step>
  <Step title="Conecta guards globales en AppHttpModule">
    Declara clases guard personalizadas en *@HttpClientModule({ guards })* para proteger todos los endpoints con la misma política. El framework resuelve dependencias de guard desde el contenedor DI, por lo que los guards pueden inyectar servicios como *AppEnv* sin cableado manual. Usa `apiKey` en *defineHttp* para activar *ApiKeyGuard* automáticamente sin declararlo en el arreglo guards.
  </Step>
  <Step title="Acota protección con @HttpGuards">
    Aplica *@HttpGuards* a nivel de controlador o método en endpoints que requieran lógica de autorización distinta o adicional. Esto mantiene el guard global enfocado en la política base y mueve verificaciones específicas al punto de declaración. Los guards de clase se ejecutan antes que los de método dentro del mismo controlador.
  </Step>
  <Step title="Agrega LoggerMiddleware para observabilidad">
    Registra `new LoggerMiddleware()` en *@HttpClientModule({ middleware })* para obtener logging base de requests. El middleware registra método, path, estado y duración. Status codes 400 o superiores se registran en nivel warn para facilitar filtrado.
  </Step>
  <Step title="Acota rate limits a endpoints sensibles">
    Extiende *RateLimitMiddleware* con configuraciones por ruta y regístralo vía *middlewareProviders*. Aplícalo con *@HttpUseMiddleware* sobre endpoints que gestionen operaciones costosas o mutaciones sensibles en lugar de aplicar un único límite global.
  </Step>
  <Step title="Valida configuración de proxy y confianza IP">
    Si rate limiting o logging de auditoría dependen de IP de cliente, verifica cómo tu proxy reverso reenvía `x-forwarded-for`. Una configuración incorrecta de confianza puede agrupar usuarios no relacionados en un solo bucket o permitir suplantación de identidad por clientes maliciosos.
  </Step>
</Steps>

<Callout tone="warning" title="La postura de seguridad sigue siendo tu responsabilidad de diseño">
  El paquete entrega primitivas y defaults seguros, pero las decisiones finales de política deben ser explícitas en tu AppModule y en tu arquitectura de despliegue. Revisa headers de seguridad, orígenes CORS y configuración de guards en cada revisión de despliegue.
</Callout>
