## Por qué importan las excepciones explícitas

Los clientes HTTP dependen de códigos de estado estables y de formas de respuesta estables. Lanzar clases _HttpError_ explícitas hace que los fallos sean observables, testeables y más fáciles de monitorear en producción. Cada clase de error exportada por el paquete tiene un código de estado semántico y un mensaje por defecto, así que el servidor puede normalizar respuestas sin lógica condicional en cada handler.

Cuando los controladores devuelven errores genéricos, los clientes pierden contexto semántico y el comportamiento de reintentos se vuelve frágil. El paquete evita esto al ofrecer una clase dedicada para cada escenario de fallo, todas extendiendo la misma base, lo que garantiza serialización consistente en toda la superficie API.

## Clase base HttpError

Todos los errores de la jerarquía extienden _HttpError_, que a su vez extiende la clase nativa _Error_. Agrega una propiedad _statusCode_ de solo lectura y sobrescribe el constructor para aceptar un mensaje y un estado HTTP numérico. Esta forma es el único contrato que la capa de normalización del servidor lee, así que cualquier clase que extienda _HttpError_ participa automáticamente en el manejo centralizado de errores sin cableado adicional.

La clase base también define `this.name` con el nombre de la clase concreta, lo que hace que stack traces y dashboards de monitoreo distingan de inmediato los tipos de error. Las subclases solo deben llamar `super(message, statusCode)` con sus propios valores por defecto para mantener ese contrato.

## Jerarquía de errores desde los exports del paquete

<DropdownGroup>
<Dropdown title="BadRequestError, 400">
  Indica que la request es sintácticamente válida pero semánticamente incorrecta o contiene combinaciones de entrada malformadas. Usa esta clase cuando la lógica de dominio rechaza una request por razones fuera de la validación DTO, como referenciar una entidad en estado inválido o enviar parámetros conflictivos. El mensaje por defecto es `'Bad request'`.
</Dropdown>

<Dropdown title="ValidationError, 400">
  Es la única clase de error que incluye estructura adicional más allá de mensaje
  y código de estado. Extiende *HttpError* con un arreglo *details* donde cada
  entrada mapea un nombre de propiedad DTO a las restricciones que fallaron.
  *ValidationPipe* lanza esta clase automáticamente cuando falla la validación
  de *@HttpBody*, por lo que rara vez necesitas construirla manualmente.
</Dropdown>

<Dropdown title="UnauthorizedError, 401">
  Indica que la request no incluye credenciales de autenticación válidas. Úsala
  cuando quien solicita no haya aportado prueba de identidad, a diferencia de
  *ForbiddenError*, que aplica cuando una identidad autenticada no tiene
  permisos. El mensaje por defecto es `'Unauthorized'`.
</Dropdown>

<Dropdown title="ForbiddenError, 403">
  Indica que una request autenticada no tiene permisos para realizar la acción
  solicitada. Úsala cuando la identidad está establecida pero el chequeo de
  autorización falla, por ejemplo cuando un usuario regular intenta una
  operación de administrador. El mensaje por defecto es `'Forbidden'`.
</Dropdown>

<Dropdown title="NotFoundError, 404">
  Indica que el recurso solicitado no existe o es inaccesible por contrato. Es
  la clase de error más común para endpoints GET y PATCH que buscan entidades
  por ID y no encuentran resultados. El mensaje por defecto es `'Not found'`.
</Dropdown>

<Dropdown title="MethodNotAllowedError, 405">
  Indica que el método HTTP usado en la request no está soportado para el
  endpoint objetivo. Úsala en lógica de controlador cuando un handler rechaza
  condicionalmente el método según el estado del recurso, no porque la ruta no
  esté registrada. El mensaje por defecto es `'Method not allowed'`.
</Dropdown>

<Dropdown title="ConflictError, 409">
  Indica que la request no puede completarse por un conflicto de estado en el
  recurso objetivo. Escenarios comunes incluyen crear un registro duplicado,
  asignar un valor ya asignado o ejecutar una operación que requiere un estado
  distinto del recurso. El mensaje por defecto es `'Conflict'`.
</Dropdown>

<Dropdown title="UnprocessableEntityError, 422">
  Indica que el servidor entendió el contenido de la request pero no puede
  procesarlo por restricciones semánticas. Úsala cuando una request parseada
  cumple requisitos estructurales pero viola reglas de negocio que la validación
  DTO no puede imponer. El mensaje por defecto es `'Unprocessable entity'`.
</Dropdown>

<Dropdown title="TooManyRequestsError, 429">
  Indica que el cliente excedió una política de rate limit o cuota.
  *RateLimitMiddleware* devuelve una respuesta 429 directamente sin lanzar esta
  clase, pero puedes lanzarla manualmente en lógica de handler cuando fallen
  verificaciones de cuota personalizadas. El mensaje por defecto es `'Too many
  requests'`.
</Dropdown>

<Dropdown title="InternalServerError, 500">
  Indica un fallo interno inesperado donde aún se requiere una respuesta JSON
  controlada. Úsala cuando captures errores no recuperables que quieras exponer
  con código predecible en lugar de dejar que el fallback genérico 500 lo
  maneje. El mensaje por defecto es `'Internal server error'`.
</Dropdown>

<Dropdown title="NotImplementedError, 501">
  Indica que una operación reconocida todavía no está implementada en la versión
  actual. Úsala como placeholder durante desarrollo cuando una ruta está
  registrada pero su handler aún no se completó, entregando una señal semántica
  a clientes en lugar de una respuesta 500 ambigua. El mensaje por defecto es
  `'Not implemented'`.
</Dropdown>

<Dropdown title="ServiceUnavailableError, 503">
  Indica una caída temporal de infraestructura o indisponibilidad de una dependencia. Úsala cuando el servidor está activo pero una dependencia downstream como base de datos o API externa no responde, estableciendo la expectativa de que un reintento puede funcionar más adelante. El mensaje por defecto es `'Service unavailable'`.
</Dropdown>
</DropdownGroup>

## ValidationError y detalles estructurados

_ValidationError_ es la única clase de error que transporta más que un mensaje. Incluye un arreglo _details_ donde cada entrada mapea una propiedad a las restricciones que fallaron. Esta estructura se produce automáticamente por _ValidationPipe_ cuando la validación de payloads de body pasa por reglas de _class-validator_.

La interfaz _ValidationDetail_ expone dos campos: _property_ (nombre del campo DTO) y _constraints_ (un registro de nombres de regla fallidos a mensajes legibles para humanos). Como el pipeline usa `whitelist: true` y `forbidNonWhitelisted: true`, cualquier campo inesperado en el body también dispara error de validación, evitando que contaminación de payload llegue a lógica de negocio.

Los clientes reciben una forma predecible donde `details` siempre es un arreglo, incluso para un solo campo inválido. Esto permite iterar el arreglo y mapear cada entrada a errores inline de formularios o resúmenes de error sin bifurcar por forma de respuesta.

import {
  HttpBody,
  HttpController,
  HttpGet,
  HttpParam,
  HttpPatch,
  HttpStatus,
} from '@spraxium/http';
import {
  NotFoundError,
  ForbiddenError,
  ConflictError,
  ServiceUnavailableError,
} from '@spraxium/http';
import { UpdateGuildConfigDto } from '../dto/update-guild-config.dto';

@HttpController('/guilds')
export class GuildHttpController {
  @HttpGet('/:guildId')
  async getGuild(@HttpParam('guildId') guildId: string) {
    const guild = await this.findGuild(guildId);

    if (!guild) {
      throw new NotFoundError('Guild not found');
    }

    if (!guild.available) {
      throw new ServiceUnavailableError('Guild is temporarily unavailable');
    }

    return { ok: true, guildId: guild.id, name: guild.name };

  }

  @HttpPatch('/:guildId/config')
  @HttpStatus(200)
  async updateConfig(
    @HttpParam('guildId') guildId: string,
    @HttpBody(UpdateGuildConfigDto) body: UpdateGuildConfigDto,
  ) {
    const guild = await this.findGuild(guildId);
    if (!guild) throw new NotFoundError('Guild not found');

    if (guild.locked) {
      throw new ForbiddenError('Guild configuration is locked by an admin');
    }

    if (guild.prefix === body.prefix) {
      throw new ConflictError('Prefix is already set to that value');
    }

    return { ok: true, guildId, applied: body };

  }

  }
}

## Comportamiento de normalización a nivel servidor

*HttpServer* registra dos handlers terminales al final del pipeline Hono: *notFound* y *onError*. Juntos garantizan que cada ruta posible de salida produzca una respuesta JSON con la misma forma.

El handler *notFound* se dispara para cualquier request que no coincida con una ruta registrada y devuelve `{ ok: false, error: 'Not Found' }` con estado 404. El handler *onError* cubre excepciones lanzadas con esta precedencia:

1. *ValidationError* devuelve estado 400 con `{ ok: false, error: 'Validation failed', details: [...] }`;
2. cualquier otra subclase *HttpError* devuelve su propio status code con `{ ok: false, error: message }`;
3. excepciones desconocidas se registran en logs y devuelven `{ ok: false, error: 'Internal server error' }` con estado 500.

Como este mapeo está centralizado, los controladores deberían lanzar la clase de error más específica posible y nunca construir payloads JSON de error ad-hoc en código de handler. La capa de normalización se encarga del resto.

## Contrato de forma de respuesta

Toda respuesta de error sigue el mismo envelope sin importar el código de estado. El campo `ok` siempre es `false`, el campo `error` lleva el string de mensaje y `details` aparece solo en respuestas de *ValidationError*. Esto permite que consumidores API verifiquen primero `ok` y luego bifurquen sobre `error` o `details` sin casos especiales por endpoint.

## Clases de error personalizadas

Puedes crear tus propias clases de error extendiendo *HttpError* o cualquier subclase existente. El único requisito es llamar `super` con mensaje y código de estado. Cualquier clase personalizada que extienda *HttpError* es capturada y serializada automáticamente por la capa de normalización del servidor sin cambios en middleware ni configuración.

## Rechazo de guard como frontera de error

*GuardExecutor* ejecuta guards globales secuencialmente antes de cualquier handler de controlador. Cuando un guard retorna `false`, el ejecutor corta la ejecución y devuelve `{ ok: false, error: 'Unauthorized' }` con estado 401. Esta respuesta se inyecta directamente, no a través de *onError*, lo que significa que los rechazos de guard son finales y no pueden capturarse ni modificarse con middleware posterior.

Como el comportamiento de guard está fuera del camino de normalización de *HttpError*, las implementaciones de guard deberían mantener semánticas de rechazo simples. La forma 401 coincide con el mismo envelope que todos los demás errores, por lo que los clientes no necesitan tratamiento especial para fallos de guard.

## Checklist de diseño de excepciones

<Steps>
  <Step title="Lanza errores semánticos cerca de reglas de negocio">
    Lanza clases *HttpError* específicas donde se toman decisiones de dominio, no solo en el borde del controlador. Lanzar *ConflictError* dentro de lógica de servicio es más claro que retornar un flag y convertirlo en error más tarde en el handler.
  </Step>
  <Step title="Mantén mensajes accionables y estables">
    Los mensajes de error deberían ayudar a clientes y operadores a entender siguientes pasos sin filtrar detalles internos sensibles. Un wording estable también mejora deduplicación de alertas y calidad de dashboards con el tiempo.
  </Step>
  <Step title="Usa validación DTO para corrección de forma">
    Deja que *ValidationPipe* y *class-validator* impongan garantías estructurales antes de ejecutar lógica de dominio. El pipeline usa `whitelist: true` y `forbidNonWhitelisted: true` por defecto, lo que significa que propiedades inesperadas se rechazan automáticamente.
  </Step>
  <Step title="Prefiere subclases personalizadas sobre HttpError crudo">
    Crea subclases con nombres descriptivos como *GuildLockedError* o *BridgeUnavailableError* en lugar de lanzar *ForbiddenError* crudo con un string. Las clases con nombre son más fáciles de buscar en logs, testear en aserciones y filtrar en dashboards de monitoreo.
  </Step>
  <Step title="Apóyate en mapeo centralizado de respuestas">
    Permite que *HttpServer* normalice errores a JSON de forma consistente en lugar de construir payloads ad-hoc en cada handler. Un mapeo unificado es más fácil de testear y razonar entre equipos, y reduce superficie para desalineaciones accidentales en forma de respuesta.
  </Step>
</Steps>

<Callout tone="warning" title="Nunca expongas detalles internos de error a clientes">
  Excepciones desconocidas son capturadas por la capa de normalización y devueltas como respuesta genérica 500. El mensaje original del error solo se registra del lado servidor. No sobrescribas este comportamiento para reenviar stack traces crudos o mensajes internos, porque eso filtra detalles de implementación a consumidores externos.
</Callout>
