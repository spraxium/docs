description: "Narrow the problem to the connection, service access, or work inside the bot."

When a route breaks, try a small call from the same host as the gateway. `bot.health` works well because it needs no guild data. If that fails, check the address in the bot's startup log, the client URL, and the credentials. If it works, repeat the exact guild ID and method used by the route.

## Did the gateway see the call?

A refused connection usually points to the address or a process that has not started. If there is a proxy, check that it supports the transport the client uses and that Node trusts its certificate. Use a request ID and approximate time to correlate gateway and application logs. Leave tokens, authorization headers, and private request data out of tickets.

`Unauthenticated` means you should compare the credential the client loaded with the one configured on the bot. `PermissionDenied` points to method permissions or a handler that remains closed. A 403 generated by the web route may happen before the bot receives any call, so check which layer produced it.

## Does the bot know what to run?

`InvalidArgument` often means that the payload failed validation or that `guildId` was missing, nested, or sent as a number. For `NotFound`, confirm the method name and provider registration and check that the bot knows the guild. If only a few guilds fail with sharding, check the logs of the parent and the child that owns them.

If the bot reports a missing framework capability, update `@spraxium/common`, `@spraxium/core`, and `@spraxium/logger` as a matching set. Check the versions your application actually resolves, since the adapter needs the module lifecycle and parent shutdown hooks.

## What if the call was slow?

For `DeadlineExceeded`, check how much time the handler spends in Discord, a database, or a second network call. Use a deadline that fits inside the HTTP request budget. For `ResourceExhausted`, check payload size, concurrency, and the credential's rate limit. For `Unavailable`, see whether the gateway or the target shard is still starting.

A read can often be tried again according to your application's needs. A write may already have succeeded when its reply is lost. Look up your operation key before trying it again. [Handlers, deadlines, and cancellation](./rpc-handlers)

## Compare the health check with the real route

When the bot's health check works but the dashboard fails, use the same service configuration as the dashboard and try the method using an ID you control. Match timings from the web route, gateway and bot logs. The HTTP route might have rejected a session, a credential might be allowed to run health checks without reading guilds, or a service inside the bot might have failed. Narrow the error to one point before changing settings.

Check whether the caller stopped waiting first or the gateway rejected the work. A 504 from your web proxy can happen before the SDK's timeout, and the original Discord operation may still finish. Set explicit client and server budgets and observe them on a known slow operation. Keep an operation ID on writes and check the current state before giving a user a retry button. If only larger replies fail, inspect the number of fields and both sides' payload limits before raising the maximum. [Gateway settings](./rpc-configuration)
