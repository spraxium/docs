## What V2 containers are

Discord's Components V2 API replaces the traditional message layout model with a composable block
system. Instead of a message being a flat combination of text content, embeds, and component rows, V2 lets you combine text blocks, sections, media galleries, separators, and action rows inside a
single container element. The container becomes the top-level layout unit for the message.

Spraxium's V2 system wraps this API with the same decorator-handler architecture used across the
rest of _@spraxium/components_. You declare a container schema as a decorated class, annotate each
structural element with a property decorator, and render the whole container through _V2Service_ by
passing runtime data. The result is a strongly-typed, composable layout that separates structure
from the data flowing through it at render time.

The package provides two authoring styles for V2. The class-based schema pattern uses
_@V2Container_ plus property decorators and is best for reusable, data-driven layouts. The fluent
API is an imperative builder that chains calls on a _V2ContainerFluentBuilder_ instance and is best
for one-off or dynamically assembled messages. Both styles produce the same wire-format and can be
mixed within the same bot.

## When to use V2 containers

V2 containers are appropriate whenever the message needs structured layout that a plain embed cannot
express. Common use cases include leaderboards with variable-length entry lists, server dashboard
panels with an icon thumbnail and stat grid, profiles with an avatar alongside multiple fields, and
image galleries embedded in command responses. Any message that benefits from visual separation
between sections, or that would require multiple embeds to approximate, is a good candidate for a
V2 container.

<Callout tone="warning">
  V2 containers require the MessageFlags.IsComponentsV2 flag when sending
  messages. Setting this flag means the message cannot simultaneously carry
  traditional embeds or a plain content string alongside the containers, design
  V2 messages as self-contained layouts, not as enhancements to existing
  content.
</Callout>

## Setting up V2Service

_V2Service_ is the rendering and construction service for all V2 work. It is automatically
available via injection once _ComponentsModule_ is registered in your module graph. No additional
configuration is needed beyond the standard _defineComponents_ plugin setup.

Inject _V2Service_ into any handler or service that needs to render V2 containers.

```typescript filename="src/handlers/my.handler.ts"
import { V2Service } from '@spraxium/components';

@SlashCommandHandler(MyCommand)
export class MyHandler {
  constructor(private readonly v2: V2Service) {}

  async handle(@Ctx() interaction: ChatInputCommandInteraction): Promise<void> {
    // ...
  }
}
```

## Class-based container schemas

The class-based pattern declares a container as an annotated class. Apply _@V2Container_ to the
class to mark it as a container and configure the accent color and spoiler options. Apply property
decorators to each field to register child components in declaration order. At render time, _V2Service.build_ reads the metadata, evaluates all factory functions with your runtime data, and
assembles the container.

The property names in the schema class do not matter at runtime. Only the metadata registered by
the decorators is read. Declare the property type as `never` to signal that the field only exists
as a metadata slot.

```typescript filename="src/schemas/user-profile.container.ts"
import {

export interface UserProfileData {

  avatarUrl: string;
  bio: string;
````

## The fluent API

The fluent API is a chainable builder attached to _V2Service_. Call _v2.container()_ to open a
builder, chain child component calls, and call _.toReply()_ at the end to produce the payload
ready for _interaction.reply()_. Each chain method returns the same builder, so every operation
can be inlined.

The fluent API does not support property-level decorators or _@V2When_ conditions because there is
no class-level metadata to annotate. Use the class-based pattern when you need conditional
rendering or when you want to reuse the same layout in multiple handlers.

```typescript filename="src/handlers/greet.handler.ts"
import { Ctx, SlashCommandHandler } from '@spraxium/common';
import { V2Service, desc } from '@spraxium/components';
import { MessageFlags, type ChatInputCommandInteraction } from 'discord.js';
import { GreetCommand } from '../commands/greet.command';

@SlashCommandHandler(GreetCommand)
export class GreetHandler {
  constructor(private readonly v2: V2Service) {}

  async handle(@Ctx() interaction: ChatInputCommandInteraction): Promise<void> {
    const user = interaction.user;

    const payload = this.v2
      .container({ accentColor: 0x57f287 })
      .text(desc().h2(`ðŸ‘‹ Hello, ${user.username}!`))
      .sep()
      .section(
        [
          `**ID:** \`${user.id}\``,
          `**Account age:** <t:${Math.floor(user.createdTimestamp / 1000)}:R>`,
        ].join("\n"),
        this.v2.thumbnail(user.displayAvatarURL({ size: 128 }), {
          description: `${user.username} avatar`,
        }),
      )
      .sep({ divider: false })
      .text(desc().subtext('Powered by Spraxium V2'))
      .toReply();

    await interaction.reply({
      ...payload,
      flags: payload.flags | MessageFlags.Ephemeral,
    });
  }
}
```

## Dynamic children with @V2Dynamic

_@V2Dynamic_ is the solution when the number of child components depends on runtime data. Instead
of a static configuration, you provide a factory function that receives the data object and returns
an array of child specs created with the helper functions _v2text_, _v2sep_, _v2section_, _v2gallery_, and _v2row_. The engine walks this array and renders each spec in sequence.

A common pattern is to generate one or more text lines per data entry and insert separators between
them, stopping one separator short so the last entry isn't followed by a divider.

```typescript filename="src/schemas/leaderboard.container.ts"
import {
  V2Container,
  V2Dynamic,
  V2Separator,
  V2Text,
  desc,
  v2sep,
  v2text,
} from '@spraxium/components';

export interface LeaderboardEntry {
  username: string;
  score: number;
  rank: number;
}

export interface LeaderboardData {
  title: string;
  entries: Array<LeaderboardEntry>;
}

const MEDALS = ['ðŸ¥‡', 'ðŸ¥ˆ', 'ðŸ¥‰'];

@V2Container({ accentColor: 0xf1c40f })
export class LeaderboardContainer {
  @V2Text((data: LeaderboardData) => desc().h2(`ðŸ† ${data.title}`))
  title!: never;

  @V2Separator()
  divider!: never;

  @V2Dynamic((data: LeaderboardData) => {
    if (data.entries.length === 0) {
      return [v2text(desc().subtext('No entries yet.'))];
    }

    return data.entries.flatMap((entry, index) => {
      const medal = MEDALS[index] ?? `**${entry.rank}.**`;
      return [
        v2text(
          `${medal} **${entry.username}**, ${entry.score.toLocaleString()} pts`,
        ),
        ...(index < data.entries.length - 1 ? [v2sep({ divider: false })] : []),
      ];
    });
  })
  entries!: never;

  @V2Separator({ divider: false })
  footer!: never;

  @V2Text((data: LeaderboardData) =>
    desc().subtext(`${data.entries.length} players ranked`),
  )
  summary!: never;
}
```

The handler passes the entry list as data and calls _buildReply_ without knowing how many rows will
be generated.

```typescript filename="src/handlers/leaderboard.handler.ts"
@SlashCommandHandler(LeaderboardCommand)
export class LeaderboardHandler {
  constructor(private readonly v2: V2Service) {}

  async handle(@Ctx() interaction: ChatInputCommandInteraction): Promise<void> {
    const entries: Array<LeaderboardEntry> = await fetchTopPlayers(10);

    const payload = await this.v2.buildReply(LeaderboardContainer, {
      title: 'Weekly Top Players',
      entries,
    });

    await interaction.reply(payload);
  }
}
```

## Conditional rendering with @V2When

_@V2When_ conditionally includes a child based on runtime data. It is applied as an additional
decorator _below_ the child decorator, which means it runs last and patches the existing child
definition with a guard predicate. If the predicate returns `false` for the given data, the child
is excluded from the container entirely, not rendered as empty.

_@V2When_ is stackable: multiple children in the same container can each carry independent
conditions. The order property assigned at registration time is preserved regardless of which
children are filtered out.

```typescript filename="src/schemas/member-card.container.ts"
import {
  V2Container,
  V2Separator,
  V2Text,
  V2When,
  desc,
} from '@spraxium/components';

export interface MemberCardData {
  username: string;
  boostLevel: number;
  isAdmin: boolean;
  bio: string;
}

@V2Container({ accentColor: 0x5865f2 })
export class MemberCardContainer {
  @V2Text((data: MemberCardData) => desc().h2(data.username))
  title!: never;

  @V2Separator()
  divider!: never;

  @V2When((data: MemberCardData) => data.isAdmin)
  @V2Text('âš™ï¸ **Server Administrator**')
  adminBadge!: never;

  @V2When((data: MemberCardData) => data.boostLevel > 0)
  @V2Text(
    (data: MemberCardData) => `â­ **Server Booster**, Level ${data.boostLevel}`,
  )
  boostBadge!: never;

  @V2Text((data: MemberCardData) => data.bio)
  bio!: never;
}
```

When `isAdmin` is `false`, the admin badge row is not rendered at all. The remaining children close
up naturally without any gap.

## Embedding action rows with @V2Row

_@V2Row_ places a button row or select menu row directly inside a V2 container. Pass your component
classes in the `components` array the same way you would pass them to _ButtonService_ or
_SelectService_. The service auto-detects whether the first class is a select menu and routes to
the correct builder automatically.

## @V2DynamicRow

_@V2DynamicRow_ auto-chunks a runtime list of items or button classes into rows of up to five inside a container. It is the V2 equivalent of calling `ButtonService.build` multiple times, but driven by data rather than a static class list.

Two modes are available:

**Dynamic mode:** pair a `@DynamicButton` class with a data accessor that produces the item list. Spraxium calls the button's `render(item)` static method for each item, stores each item as a payload, and groups the resulting buttons into rows of five. This is the main use case: one button class, N items, N handled buttons per interaction.

```typescript filename="src/modules/leaderboard/components/leaderboard.container.ts"
import { V2Container, V2Separator, V2Text, V2DynamicRow, desc } from '@spraxium/components';
import type { LeaderboardData } from '../leaderboard.data';
import { PlayerButton } from './player-button.component';

@V2Container({ accentColor: 0x5865f2 })
export class LeaderboardContainer {
  @V2Text((data: LeaderboardData) => desc().h2(`ðŸ† ${data.title}`))
  title!: never;

  @V2Separator()
  divider!: never;

  @V2DynamicRow({ dynamic: PlayerButton, items: (data: LeaderboardData) => data.players })
  playerButtons!: never;
}
```

**Components mode:** provide a factory function that returns an array of static button classes. Spraxium builds all returned classes into rows of five, with no payloads involved. Use this when the set of buttons is variable but each button has a fixed `customId`.

```typescript filename="src/modules/quick-actions/components/quick-actions.container.ts"
import { V2Container, V2DynamicRow, V2Row, V2Text, desc } from '@spraxium/components';
import type { QuickActionsData } from '../quick-actions.data';
import {
  ArchiveButton,
  DeleteButton,
  ExportButton,
  MuteButton,
  PinButton,
  RefreshButton,
  ShareButton,
} from './quick-actions.components';
import { ModeSelect } from './quick-actions.components';

@V2Container({ accentColor: 0x57f287 })
export class QuickActionsContainer {
  @V2Text((data: QuickActionsData) => desc().h2(`âš¡ Quick actions for ${data.resource}`))
  title!: never;

  @V2DynamicRow({
    components: () => [
      RefreshButton,
      ExportButton,
      ShareButton,
      ArchiveButton,
      DeleteButton,
      PinButton,
      MuteButton,
    ],
  })
  actions!: never;

  @V2Row({ components: [ModeSelect] })
  mode!: never;
}
```

<Callout tone="info">
  _@V2DynamicRow_ with dynamic: only works with @DynamicButton classes (not static buttons). For static button chunking, use the components: factory form.
</Callout>

## Building the reply payload

Both _buildReply_ and the fluent _.toReply()_ method return a `{ components, flags }` object.
Spreading this into _interaction.reply()_ sets `IsComponentsV2` automatically. You can merge
additional flags using bitwise OR.

```typescript filename="sending a V2 reply"
const payload = await this.v2.buildReply(MyContainer, data);

await interaction.reply({
  ...payload,
  flags: payload.flags | MessageFlags.Ephemeral,
});
```

If you need to update an existing V2 message, use _interaction.editReply()_ or pass the payload
to _message.edit()_ directly. The flag is required on both the initial send and subsequent edits, because Discord identifies a message as a V2 message by the presence of that flag.

## dynamic component system and migration notes

Spraxium now expands the V2 story beyond layout composition and introduces a complete dynamic
interaction model for buttons and selects. The core idea is simple: render-time data now travels
with each interactive element through a payload reference, so handlers can receive typed domain
objects directly instead of re-querying state from scratch or encoding large values manually into
custom IDs.

This model is especially useful for catalog UIs, dashboards, moderation queues, and any flow where
you render a variable list of actions and need each action to carry rich context.

### Dynamic buttons and typed payload injection

Use `@DynamicButton` to declare how each runtime item should be rendered into a button and
`@DynamicButtonHandler` to process interactions. Inject the original payload via `@ButtonPayload()`
and, when needed, inject a payload handle via `@PayloadRef()` to consume one-shot actions.

```typescript filename="src/modules/shop/buttons/buy-button.component.ts"
import {
  ButtonPayload,
  DynamicButton,
  DynamicButtonHandler,
  PayloadRef,
  type PayloadHandle,
} from '@spraxium/components';
import { Ctx } from '@spraxium/common';
import type { ButtonInteraction } from 'discord.js';

interface Product {
  id: string;
  name: string;
  price: number;
}

@DynamicButton({ baseId: 'shop-buy', payloadTtl: 300 })
export class BuyButton {
  static render(product: Product) {
    return {
      label: `Buy ${product.name}`,
      style: 'success' as const,
      emoji: 'ðŸ›’',
    };
  }
}

@DynamicButtonHandler(BuyButton)
export class BuyButtonHandler {
  async handle(
    @Ctx() interaction: ButtonInteraction,
    @ButtonPayload() product: Product,
    @PayloadRef() payload: PayloadHandle,
  ): Promise<void> {
    // One-shot purchase flow: prevent the same payload from being reused.
    await payload.consume();

    await interaction.reply({
      content: `Purchase confirmed: ${product.name} ($${product.price}).`,
      flags: 'Ephemeral',
    });
  }
}
```

### Dynamic selects with data-bound option sets

For dynamic selects, pair `@DynamicStringSelect` with `@DynamicSelectHandler`. The select can be
rendered from runtime data, while the handler receives both selected values (`@SelectedValues()`) and
the original payload (`@SelectPayload()`). This keeps presentation and domain data strongly aligned.

```typescript filename="src/modules/tickets/selects/category-select.component.ts"
import {
  DynamicStringSelect,
  DynamicSelectHandler,
  SelectPayload,
  SelectedValues,
} from '@spraxium/components';
import { Ctx } from '@spraxium/common';
import type { StringSelectMenuInteraction } from 'discord.js';

interface TicketCategory {
  id: string;
  name: string;
}

@DynamicStringSelect({ baseId: 'ticket-category', placeholder: 'Choose a category', payloadTtl: 300 })
export class TicketCategorySelect {
  static render(categories: TicketCategory[]) {
    return {
      options: categories.map((category) => ({
        label: category.name,
        value: category.id,
      })),
      minValues: 1,
      maxValues: 1,
    };
  }
}

@DynamicSelectHandler(TicketCategorySelect)
export class TicketCategorySelectHandler {
  async handle(
    @Ctx() interaction: StringSelectMenuInteraction,
    @SelectedValues() values: string[],
    @SelectPayload() categories: TicketCategory[],
  ): Promise<void> {
    const selected = categories.find((category) => category.id === values[0]);

    await interaction.update({
      content: `Ticket category selected: ${selected?.name ?? 'Unknown'}`,
      components: [],
    });
  }
}
```

### What payload and payload reference actually mean

In the dynamic interaction model, the **payload** is the original domain data used to render
the interactive element. Instead of serializing full data into `customId`, Spraxium stores that
data in its context-backed payload store and embeds only a short reference in the form `~p:<id>`.

Practically:

1. You render dynamic buttons/selects from real runtime objects (product, ticket, user, etc.).
2. The framework stores each payload with TTL and appends `~p:<id>` to the final `customId`.
3. At interaction time, the dispatcher resolves that ID and injects the typed object into the handler.

This removes brittle string parsing and keeps `customId` compact.

### @ButtonPayload vs @SelectPayload vs @PayloadRef

`@ButtonPayload()` and `@SelectPayload()` inject **the domain object** bound to the interaction.
`@PayloadRef()` injects a lifecycle handle (`PayloadHandle`) with:

- `id`: the raw payload identifier.
- `consume()`: deletes that payload from storage to prevent reuse.

Use `@PayloadRef()` for **one-shot** actions (purchase, irreversible confirmation, coupon redemption, etc.).

```typescript filename="src/modules/shop/buttons/buy-button.handler.ts"
import { ButtonPayload, DynamicButtonHandler, PayloadRef, type PayloadHandle } from '@spraxium/components';
import { Ctx } from '@spraxium/common';
import type { ButtonInteraction } from 'discord.js';
import { BuyButton } from './buy-button.component';

interface Product {
  id: string;
  name: string;
}

@DynamicButtonHandler(BuyButton)
export class BuyButtonHandler {
  async handle(
    @Ctx() interaction: ButtonInteraction,
    @ButtonPayload() product: Product,
    @PayloadRef() ref: PayloadHandle,
  ): Promise<void> {
    await this.auditPurchaseAttempt(ref.id, product.id);

    // One-shot: future clicks with this payload return as expired.
    await ref.consume();

    await interaction.reply({
      content: `Purchase confirmed: ${product.name}`,
      flags: 'Ephemeral',
    });
  }

  private async auditPurchaseAttempt(payloadId: string, productId: string): Promise<void> {
    void payloadId;
    void productId;
  }
}
```

### TTL, expiration, and when handlers stop running

Each dynamic payload has a TTL. You can set it with `payloadTtl` on the dynamic component class.
If omitted, the payload service uses a default TTL of **600 seconds**.

When a payload expires (or after you call `consume()`), later interactions carrying the same
`customId` do not reach your handler. The user receives an expired-action response, which you can
customize via component error message configuration.

### Payload reference (~p) versus flow context (~ctx)

Both tags can coexist on the same `customId`, but they serve different jobs:

- `~p:<id>`: points to dynamic component domain payload.
- `~ctx:<id>`: points to flow state (wizard progress, user restriction, step context).

Rule of thumb: payload identifies **which item** the action is about; flow context identifies
**which conversation state** the interaction belongs to.

### Async versus sync render path in modelo atual

In the current feature set, `build()` and `buildReply()` are asynchronous by design because V2 schemas can now include
children that require async resolution, such as:

- `@V2DynamicRow` using `dynamic:` item expansion.
- `@V2Row` with dynamic selects that resolve options asynchronously.
- Any child that delegates to async component factories.

Use `buildSync()` or `buildReplySync()` only when your container is fully synchronous. If a schema
contains async-only children, the sync path throws intentionally to prevent silently incorrect layouts.

### Practical migration checklist

When upgrading legacy V2 handlers, this quick checklist covers almost all breakages:

1. Add `await` before `this.v2.build(...)` and `this.v2.buildReply(...)`.
2. Keep using `buildReplySync()` only for static containers without dynamic rows/selects.
3. For list-like action UIs, migrate manual row chunking to `@V2DynamicRow`.
4. For data-rich interaction handlers, replace custom ID parsing with `@ButtonPayload()` / `@SelectPayload()`.
5. For one-shot actions (purchase, confirm, consume), inject `@PayloadRef()` and call `consume()`.
