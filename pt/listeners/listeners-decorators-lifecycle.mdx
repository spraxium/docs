## O decorator de classe @Listener

O decorator _@Listener_ é o que transforma uma classe comum em um listener. Ele recebe um único argumento: o nome do evento do Discord a partir do enum _Events_ do Discord.js. Internamente, esse decorator faz duas coisas. Primeiro, salva o nome do evento como metadado da classe. Depois, marca a classe como injetável para que o container de DI consiga resolver dependências do construtor durante o bootstrap.

Cada classe de listener fica vinculada a exatamente um evento. Se você precisar reagir a _GuildMemberAdd_ e _GuildMemberRemove_, crie duas classes separadas. Isso mantém cada classe focada em um único evento e evita confusão sobre qual método trata o quê. Você até pode declarar várias classes no mesmo arquivo quando elas forem muito relacionadas, como _MemberJoinListener_ e _MemberLeaveListener_, mas cada classe ainda precisa do seu próprio _@Listener_ com o evento correto.

<CodeTabs>
  <Tab label="Classe única" language="typescript">
```typescript filename="member-join.listener.ts"
import { Events, Listener, On } from '@spraxium/common';
import type { GuildMember } from 'discord.js';

@Listener(Events.GuildMemberAdd)
export class MemberJoinListener {
  @On()
  async onJoin(member: GuildMember): Promise<void> {
    const channel = await member.guild.channels.fetch('1234567890');
    if (channel?.isTextBased()) {
      await channel.send(`Welcome, ${member}!`);
    }
  }
}

````
  </Tab>
  <Tab label="Múltiplas classes" language="typescript">
```typescript filename="member.listener.ts"
import { Events, Listener, On } from '@spraxium/common';
import { Logger } from '@spraxium/core';
import type { GuildMember, PartialGuildMember } from 'discord.js';

@Listener(Events.GuildMemberAdd)
export class MemberJoinListener {
  private readonly logger = new Logger(MemberJoinListener.name);

  @On()
  async onJoin(member: GuildMember): Promise<void> {
    this.logger.info(`${member.user.username} joined ${member.guild.name}`);
  }
}

@Listener(Events.GuildMemberRemove)
export class MemberLeaveListener {
  private readonly logger = new Logger(MemberLeaveListener.name);

  @On()
  async onLeave(member: GuildMember | PartialGuildMember): Promise<void> {
    const name = member.partial ? `User ${member.id}` : member.user.username;
    this.logger.info(`${name} left guild ${member.guild.id}`);
  }
}
````

## @On versus @Once

O decorator _@On_ cria um binding persistente de evento. Toda vez que o evento do Discord dispara, o método decorado roda. É isso que você vai querer na maioria dos eventos, como _MessageCreate_, _InteractionCreate_ e _GuildMemberAdd_, ou qualquer outro que possa acontecer várias vezes. O binding continua ativo durante toda a vida do processo do bot.

O decorator _@Once_ cria um binding de uso único. Ele dispara só na primeira vez que o evento acontece depois que o bot sobe, e então o binding é removido automaticamente. O caso clássico é _ClientReady_, que geralmente só precisa ser tratado uma vez quando a conexão termina de subir. Também pode servir para qualquer lógica de inicialização que precise rodar exatamente uma vez em resposta a um evento específico.

```typescript filename="ready.listener.ts"
import { Events, Listener, Once } from '@spraxium/common';
import type { Client } from 'discord.js';

@Listener(Events.ClientReady)
export class ReadyListener {
  @Once()
  onReady(client: Client<true>): void {
    console.log(`Logged in as ${client.user.tag}`);
  }
}
```

Um detalhe importante: _@Once_ fala de semântica de binding de evento, não de semântica da instância da classe. Em outras palavras, significa “registre este handler com `client.once()` em vez de `client.on()`”. O próprio cliente do Discord.js remove o listener depois da primeira invocação. Essa diferença é sutil, mas importante, porque o comportamento é controlado pelo sistema de eventos do Discord.js, e não por algum contador de chamadas do framework.

## O decorator de parâmetro @Ctx

_@Ctx_ é um decorator de parâmetro que injeta os argumentos brutos do evento do Discord dentro de um parâmetro do método. Na maior parte do tempo, você nem precisa dele, porque o payload já pode ser recebido como parâmetro normal do método. Ainda assim, _@Ctx_ é útil quando você quer deixar explícita a intenção de injeção no código ou quando o evento fornece vários argumentos e você quer destacar qual deles interessa.

```typescript filename="interaction.listener.ts"
import { Ctx, Events, Listener, On } from '@spraxium/common';
import type { Interaction } from 'discord.js';

@Listener(Events.InteractionCreate)
export class InteractionListener {
  @On()
  async onInteraction(@Ctx() interaction: Interaction): Promise<void> {
    if (!interaction.isChatInputCommand()) return;
    console.log(`Received command: ${interaction.commandName}`);
  }
}
```

## Injeção de dependência em listeners

Como _@Listener_ marca a classe como injetável automaticamente, o listener pode receber dependências de construtor do mesmo jeito que qualquer outra classe injetável do Spraxium. É assim que você conecta listeners a serviços, repositórios e outras partes da aplicação sem acoplamento desnecessário nem wiring manual.

```typescript filename="message-create.listener.ts"
import { Events, Listener, On } from '@spraxium/common';
import { Logger } from '@spraxium/core';
import type { Message } from 'discord.js';
import { LeaderboardService } from '../../services/leaderboard.service';

@Listener(Events.MessageCreate)
export class MessageCreateListener {
  private readonly logger = new Logger(MessageCreateListener.name);

  constructor(private readonly leaderboard: LeaderboardService) {}

  @On()
  async onMessage(message: Message): Promise<void> {
    if (message.author.bot) return;
    this.logger.debug(`Message from ${message.author.id}`);
    await this.leaderboard.trackMessage(message.author.id, message.guildId);
  }
}
```

_LeaderboardService_ precisa estar registrado como provider no mesmo módulo ou exportado por algum módulo importado. O container de DI resolve isso no momento da instanciação, antes de qualquer evento começar a disparar. Se a dependência não puder ser resolvida, o framework lança um erro claro durante o bootstrap dizendo qual token faltou e sugerindo onde fazer o registro.

Mantenha os métodos do listener enxutos. O listener recebe o evento, faz filtros básicos, como ignorar mensagens de bot, e delega o trabalho real para um serviço injetado. Esse padrão deixa a lógica de negócio testável sem depender do sistema de eventos e evita que listeners virem classes grandes, cheias de regra de domínio.

<Callout tone="warning" title="Gateway intents importam">
  Se o listener está registrado corretamente, mas nunca dispara, a causa mais
  comum é a falta de gateway intents na configuração do bot. Por exemplo,
  MessageCreate exige GuildMessages ou DirectMessages, e GuildMemberAdd exige
  GuildMembers.
</Callout>
