## Configurando o logger

Mantenha a configuração do logger em um arquivo dedicado, como _config/logger.config.ts_, e referencie esse arquivo a partir de _spraxium.config.ts_. Isso deixa a configuração raiz legível e deixa claro onde níveis, masking, timestamps e encaminhamento para o Discord estão definidos.

O framework aplica essa configuração durante o bootstrap, antes de qualquer provider começar a emitir logs. Na prática, isso significa que a primeira linha escrita pelo seu bot já sai com o formato de timestamp, os níveis customizados e os transports corretos.

```typescript filename="config/logger.config.ts"
import type { SpraxiumLoggerConfig } from '@spraxium/logger';

export const loggerConfig: SpraxiumLoggerConfig = {
  levels: [
    { name: 'audit', color: 'blueBright' },
    { name: 'payment', color: 'greenBright' },
  ],
  maskTokens: true,
  discord: {
    type: 'channel',
    channelId: '1234567890',
    levels: ['error', 'warn', 'command'],
  },
};
```

```typescript filename="spraxium.config.ts"
import { defineConfig } from '@spraxium/core';
import { loggerConfig } from './config/logger.config';

export default defineConfig((_env) => ({
  logger: loggerConfig,
}));
```

O array _levels_ registra níveis de log customizados com suas cores no console. Esses níveis passam a ficar disponíveis via _Logger.extend_ e são entendidos pelos dois transports nativos. Já o _maskTokens_ controla o _TokenMasker_, que vem ligado por padrão. Só faz sentido desligá-lo em sessões locais muito controladas.

## O transport do Discord

O transport do Discord encaminha entradas de log selecionadas como embeds para o Discord. Ele só envia os níveis listados no próprio array _levels_, então você pode manter logs operacionais de alto volume no terminal e encaminhar apenas alertas, erros ou auditoria de comando para um canal compartilhado.

Existem dois modos de entrega. No modo _channel_, o transport usa o próprio client do bot para localizar o canal e enviar embeds. No modo _webhook_, ele faz requisições HTTP para uma URL de webhook, o que é útil quando o destino operacional fica separado do runtime do bot.

No modo channel, o transport enfileira mensagens que chegam antes de o client ficar pronto. Assim que o client emite _ready_, a fila é drenada automaticamente. O tamanho máximo é 100 entradas para evitar crescimento de memória durante sequências longas de startup.

O transport também faz deduplicação. Se o mesmo nível, contexto e mensagem forem enviados dentro de um segundo, o segundo envio é suprimido. Isso protege canais operacionais contra rajadas duplicadas causadas por retries ou handlers sobrepostos.

## Templates de embed customizados

Por padrão, os embeds do Discord usam o nível como título, a mensagem como descrição, uma cor correspondente e timestamp em formato ISO. Você pode sobrescrever isso com um template customizado em _embed_ quando quiser uma apresentação mais operacional, por exemplo exibindo shard, guild ou campos de metadata em posições previsíveis.

````typescript filename="config/logger.config.ts"
import type { SpraxiumLoggerConfig } from '@spraxium/logger';

export const loggerConfig: SpraxiumLoggerConfig = {
  discord: {
    type: 'channel',
    channelId: '1234567890123456789',
    levels: ['error', 'warn', 'command'],
    embed: {
      title: '{{level}} Log',
      description: "```\n{{message}}\n```",
      color: 0xff6b6b,
      timestamp: true,
      footer: { text: "Shard {{shard}} \u00b7 {{date}} {{time}}" },
      fields: [
        { name: 'Context', value: '{{context}}', inline: true },
        { name: 'Level', value: '{{level}}', inline: true },
      ],
    },
  },
};
````

Os placeholders disponíveis são resolvidos a partir da entrada de log no momento do envio. A variável _shard_ mostra o ID do shard quando o bot está sharded ou `N/A` em processo único. Metadata passada por _log_ também vira placeholder, o que torna logs de comando e auditoria especialmente úteis no Discord.

## Command logging

O serviço _CommandLogger_ registra automaticamente toda execução de slash command. Ele se conecta ao evento _interactionCreate_ do client e captura nome do comando, tag do usuário, ID do usuário, nome da guild, ID da guild e ID do canal. Cada execução gera uma entrada de log no nível _command_ com metadata estruturada, pronta para reaproveitamento em templates de embed.

A forma padrão de ativar isso é em _spraxium.config.ts_. Defina _commandLogging_ como _true_ dentro do bloco do logger, e o framework chama _CommandLogger.bind_ automaticamente durante o wiring do client. Esse é o setup mais indicado para a maioria dos bots porque permanece dentro do lifecycle normal do framework.

```typescript filename="config/logger.config.ts"
import type { SpraxiumLoggerConfig } from '@spraxium/logger';

export const loggerConfig: SpraxiumLoggerConfig = {
  maskTokens: true,
  commandLogging: true,
  discord: {
    type: 'channel',
    channelId: '1234567890123456789',
    levels: ['command'],
    embed: {
      title: 'Command Executed',
      description: '`/{{command}}` by **{{user}}**',
      timestamp: true,
      footer: { text: '{{guild}} ({{guildId}})' },
    },
  },
};
```

Se você estiver usando o logger fora do framework, ou precisar ligar o command logging manualmente, chame _CommandLogger.bind_ diretamente com o client do Discord depois de ele ficar pronto. A partir daí, metadata de comando, usuário, guild e canal também passa a ficar disponível no template.

```typescript filename="src/main.ts"
import { CommandLogger } from '@spraxium/logger';

// Call after the client is ready
CommandLogger.bind(client);
```

## Transportes customizados

Crie um transport customizado quando console e Discord não forem suficientes, por exemplo para escrever em arquivo, integrar com uma stack de observabilidade ou publicar em barramentos internos. Um transport implementa _LogTransport_, expõe um _name_ e fornece um método _log_ que recebe uma _LogEntry_.

Falhas do transport são isoladas do restante da aplicação. Se um transport lançar exceção ou rejeitar promessa, o logger engole essa falha para garantir que logging nunca vire ponto único de falha do runtime do bot.

```typescript filename="src/transports/file.transport.ts"
import { appendFileSync } from 'node:fs';
import type { LogEntry, LogTransport } from '@spraxium/logger';

export class FileTransport implements LogTransport {
  readonly name = 'file';

  constructor(private readonly path: string) {}

  log(entry: LogEntry): void {
    const line = `[${entry.timestamp.toISOString()}] ${entry.level.toUpperCase()} ${entry.context ?? ''} ${entry.message}\n`;
    appendFileSync(this.path, line);
  }
}
```

Registre o transport com _Logger.addTransport_. Se já existir outro com o mesmo nome, ele é substituído. Você pode remover um transport pelo nome com _Logger.removeTransport_. O _ConsoleTransport_ sempre fica registrado por padrão e usa o nome `"console"`.

```typescript filename="src/main.ts"
import { Logger } from '@spraxium/logger';
import { FileTransport } from './transports/file.transport';

Logger.addTransport(new FileTransport('./logs/bot.log'));
```

Se o seu transport precisar da instância do client do Discord, por exemplo para resolver nome de canal ou dados de guild, implemente a interface _ClientAwareTransport_ no lugar de um transport simples. Ela adiciona o método _setClient_, chamado automaticamente pelo framework quando o client fica pronto. O _DiscordTransport_ nativo usa essa interface internamente.
