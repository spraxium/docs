## Tornando guards configuráveis com @GuardOption

Alguns guards precisam de parâmetros para funcionar. Um guard de cargos precisa saber quais cargos verificar, um guard de cooldown precisa conhecer a janela de tempo e um guard de permissões precisa saber quais permissões exigir. Em vez de fixar esses valores dentro da classe do guard, você declara propriedades configuráveis com o decorator _@GuardOption_ e passa os valores quando anexa o guard.

O decorator _@GuardOption_ aceita um objeto de configuração com dois campos opcionais. O campo _required_ torna a opção obrigatória, o que significa que o framework lança um erro de configuração em runtime se ela não for fornecida. O campo _default_ define um valor de fallback aplicado quando nenhum valor é passado explicitamente. Se nem _required_ nem _default_ forem definidos, a opção será apenas opcional e ficará como undefined quando não for informada.

```typescript filename="min-roles.guard.ts"
import { Guard, GuardOption } from '@spraxium/common';
import type { ExecutionContext, SpraxiumGuard } from '@spraxium/common';

@Guard()
export class MinRolesGuard implements SpraxiumGuard {
  @GuardOption({ default: 1 })
  minRoles!: number;

  canActivate(ctx: ExecutionContext): boolean {
    const member = ctx.getMember();
    if (!member || !('roles' in member)) return false;
    return member.roles.cache.size >= this.minRoles;
  }
}
```

No exemplo acima, a propriedade _minRoles_ tem valor padrão 1, então, se você anexar esse guard sem especificar um valor, ele exigirá pelo menos um cargo. Se quiser um limite diferente, basta passá-lo por _withOptions_ ao anexar o guard.

## O helper withOptions

A função _withOptions_ é a forma de passar opções tipadas para um guard ao anexá-lo com _@UseGuards_. Ela recebe a classe do guard como primeiro argumento e um objeto de opções como segundo. O sistema de tipos do TypeScript infere o formato dessas opções a partir das propriedades com _@GuardOption_ do guard, então você ganha autocomplete e erros de tipo se passar um formato incorreto.

```typescript filename="moderation.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { PermissionGuard, RoleGuard } from '@spraxium/core';
import { MinRolesGuard } from '../guards/min-roles.guard';

@UseGuards(
  withOptions(RoleGuard, { roles: ['Moderator'] }),
  withOptions(PermissionGuard, { permissions: ['BanMembers'] }),
  withOptions(MinRolesGuard, { minRoles: 3 }),
)
export class ModerationHandler {
  async handle() {
    // all three guards must pass before this runs
  }
}
```

Se você não precisar passar opções porque o guard não tem opções obrigatórias ou porque os valores padrão já bastam, pode passar a classe do guard diretamente, sem _withOptions_. Os dois estilos funcionam na mesma chamada de _@UseGuards_, então você pode misturar guards que precisam de opções com guards que não precisam.

```typescript filename="mixed-guards.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly, RoleGuard } from '@spraxium/core';

@UseGuards(GuildOnly, withOptions(RoleGuard, { roles: ['Admin'] }))
export class MixedHandler {
  async handle() {
    // GuildOnly needs no options, RoleGuard needs roles
  }
}
```

## Guards embutidos

O Spraxium traz dez guards embutidos no pacote core que cobrem os padrões de acesso mais comuns no Discord. Cada guard já vem decorado com _@Guard()_ e pronto para uso com _@UseGuards_ ou _useGlobalGuards_. A lista abaixo mostra cada guard embutido, o que ele verifica e quais opções espera.

<DropdownGroup>
<Dropdown title="GuildOnly">
  Nega a execução quando o comando é invocado a partir de um canal de mensagem direta. Esse é o guard mais comum para garantir que comandos exclusivos de servidor não possam ser disparados por DMs. Ele não exige opções e pode ser passado diretamente para *@UseGuards* sem *withOptions*.
</Dropdown>

<Dropdown title="DMOnly">
  Nega a execução quando o comando é invocado dentro de um canal de guild. É o
  inverso de *GuildOnly* e restringe comandos apenas a contextos de mensagem
  direta. Não exige opções e pode ser passado diretamente para *@UseGuards*.
</Dropdown>

<Dropdown title="OwnerOnly">
  Nega a execução quando o ID do usuário não está presente na lista configurada
  de owners. Esse guard exige a opção *ownerIds*, que é um `string[]` de IDs
  snowflake de usuários do Discord. Use *withOptions* para passar os IDs de
  owner ao anexar esse guard.
</Dropdown>

<Dropdown title="PermissionGuard">
  Nega a execução quando o membro da guild não tem alguma das permissões do
  Discord exigidas. Esse guard exige a opção *permissions*, que é um
  `PermissionsString[]` usando strings de permissão do discord.js, como
  `"BanMembers"` ou `"ManageGuild"`. O membro precisa ter todas as permissões
  listadas para o guard passar.
</Dropdown>

<Dropdown title="RoleGuard">
  Nega a execução quando o membro da guild não tem nenhum dos cargos
  especificados. Esse guard exige a opção *roles*, que é um `string[]` com
  nomes de cargos ou IDs snowflake de cargo. O membro precisa ter pelo menos um
  cargo correspondente para o guard passar.
</Dropdown>

<Dropdown title="CooldownGuard">
  Nega a execução quando a pessoa usuária disparou o mesmo comando dentro da
  janela de cooldown. Esse guard exige a opção *cooldown*, que é um `number` em
  milissegundos. Ele rastreia o timestamp da última execução por usuário e
  bloqueia novas invocações até a janela expirar.
</Dropdown>

<Dropdown title="NoBotGuard">
  Nega a execução quando a pessoa que disparou a ação é uma conta de bot. Esse
  guard é útil quando seus listeners ou comandos de prefixo devem ignorar
  mensagens de outros bots. Ele não exige opções e pode ser passado diretamente
  para *@UseGuards*.
</Dropdown>

<Dropdown title="NSFWGuard">
  Nega a execução quando o canal não está marcado como NSFW nas configurações do
  servidor do Discord. Use esse guard para conteúdo com restrição etária que só
  deve aparecer em canais designados. Ele não exige opções e pode ser passado
  diretamente para *@UseGuards*.
</Dropdown>

<Dropdown title="ThreadOnlyGuard">
  Nega a execução quando o canal não é uma thread. Esse guard é útil para
  comandos que só devem rodar dentro de conversas em thread, como sistemas de
  tickets. Ele não exige opções e pode ser passado diretamente para
  *@UseGuards*.
</Dropdown>

<Dropdown title="VoiceChannelGuard">
  Nega a execução quando o membro da guild não está conectado a um canal de voz.
  Use esse guard para comandos que exigem conexão de voz, como reprodução de
  música ou recursos baseados em voz. Ele não exige opções e pode ser passado
  diretamente para *@UseGuards*.
</Dropdown>
</DropdownGroup>

## Usando guards embutidos

Guards embutidos sem opções podem ser passados diretamente para _@UseGuards_ ou _useGlobalGuards_. Guards com opções obrigatórias precisam usar _withOptions_ ou o segundo parâmetro de _useGlobalGuards_. Aqui estão exemplos práticos com os padrões mais comuns.

<CodeTabs>
  <Tab label="Registro global" language="typescript">
```typescript filename="src/main.ts"
import { SpraxiumFactory } from '@spraxium/core';
import { NoBotGuard, OwnerOnly, CooldownGuard } from '@spraxium/core';

const app = await SpraxiumFactory.create({ token: process.env.DISCORD_TOKEN! });

app.useGlobalGuards(NoBotGuard);
app.useGlobalGuards(OwnerOnly, { ownerIds: ['123456789'] });
app.useGlobalGuards(CooldownGuard, { cooldown: 3000 });

await app.listen();

````
  </Tab>
  <Tab label="Classe e método" language="typescript">
```typescript filename="moderation.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly, PermissionGuard, RoleGuard } from '@spraxium/core';

@UseGuards(
  GuildOnly,
  withOptions(RoleGuard, { roles: ['Moderator', 'Admin'] }),
)
export class ModerationHandler {
  @UseGuards(withOptions(PermissionGuard, { permissions: ['BanMembers'] }))
  async handleBan() {
    // guild + role check on class, permission check on this method only
  }

  async handleWarn() {
    // only guild + role check from the class guard
  }
}
````

  </Tab>
</CodeTabs>

O _RoleGuard_ verifica se o membro tem pelo menos um dos cargos listados. Você pode passar nomes de cargos como "Moderator" ou IDs snowflake de cargo como "1234567890". O _PermissionGuard_ verifica se o membro tem todas as permissões listadas, usando strings de permissão do Discord.js como "BanMembers", "ManageGuild" ou "Administrator".

## Criando um guard personalizado com opções

Quando os guards embutidos não cobrem seu caso de uso, você cria um guard personalizado que declara propriedades configuráveis por meio de _@GuardOption_. A classe do guard define quais parâmetros precisa, e cada ponto que a utiliza fornece os valores concretos por meio de _withOptions_. É assim que guards embutidos como _RoleGuard_ e _CooldownGuard_ funcionam internamente, e você segue exatamente a mesma abordagem nos seus próprios guards.

<Steps>
  <Step title="Defina a classe do guard com @Guard">
    Comece com uma classe decorada com *@Guard()* que implemente
    *SpraxiumGuard*. O método *canActivate* contém a lógica de verificação, e
    qualquer parâmetro configurável recebe o decorator *@GuardOption* em sua
    propriedade. Marque opções como *required* quando o guard não puder
    funcionar sem elas, ou defina um *default* quando existir um fallback
    sensato. O framework lê esses decorators no momento da instanciação e
    preenche os valores antes mesmo de *canActivate* ser executado.
  </Step>
  <Step title="Passe opções com withOptions em cada uso">
    Ao anexar o guard com *@UseGuards*, envolva-o com *withOptions* e passe os
    valores concretos que ele espera. O TypeScript infere o formato das opções
    a partir das propriedades com *@GuardOption*, então você recebe
    autocomplete e erros em tempo de compilação se passar o tipo errado. Se
    esquecer uma opção *required*, o framework lança um erro de configuração
    claro durante o bootstrap.
  </Step>
  <Step title="Reutilize o mesmo guard com valores diferentes">
    O poder dos guards configuráveis está em uma única classe servir a muitos
    cenários. Um *MinAccountAgeGuard* com *minDays: 7* em um comando geral e
    *minDays: 90* em um comando de giveaway usa a mesma classe com limites
    diferentes. Você não precisa criar classes separadas de guard para cada
    limite.
  </Step>
</Steps>

Aqui está um exemplo completo de um guard personalizado que verifica a idade mínima da conta e suporta várias opções configuráveis. O guard tem uma opção obrigatória e uma opção opcional com valor padrão.

<CodeTabs>
  <Tab label="Guard" language="typescript">
```typescript filename="min-account-age.guard.ts"
import { Guard, GuardOption } from '@spraxium/common';
import type { ExecutionContext, SpraxiumGuard } from '@spraxium/common';

@Guard()
export class MinAccountAgeGuard implements SpraxiumGuard {
  @GuardOption({ required: true })
  minDays!: number;

  @GuardOption({ default: false })
  allowBots!: boolean;

  canActivate(ctx: ExecutionContext): boolean {
    const user = ctx.getUser();
    if (user.bot && !this.allowBots) return false;

    const createdAt = user.createdAt.getTime();
    const ageInDays = (Date.now() - createdAt) / (1000 * 60 * 60 * 24);
    return ageInDays >= this.minDays;
  }
}

````
  </Tab>
  <Tab label="Uso" language="typescript">
```typescript filename="giveaway.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { GuildOnly } from '@spraxium/core';
import { MinAccountAgeGuard } from '../guards/min-account-age.guard';

@UseGuards(
  GuildOnly,
  withOptions(MinAccountAgeGuard, { minDays: 30 }),
)
export class GiveawayHandler {
  async handle() {
    // only human accounts older than 30 days can participate
  }
}
````

  </Tab>
  <Tab label="Limites diferentes" language="typescript">
```typescript filename="verification.handler.ts"
import { UseGuards, withOptions } from '@spraxium/common';
import { MinAccountAgeGuard } from '../guards/min-account-age.guard';

@UseGuards(withOptions(MinAccountAgeGuard, { minDays: 7, allowBots: true }))
export class VerificationHandler {
  async handle() {
    // only 7 days required here, bots allowed
  }
}

```
  </Tab>
</CodeTabs>

Repare que o guard tem duas opções: *minDays* é obrigatória porque o guard não consegue funcionar sem saber o limite, e *allowBots* tem padrão false porque a maioria dos pontos de uso quer bloquear bots. A terceira aba mostra como a mesma classe de guard aceita uma configuração completamente diferente em outro ponto de uso, sem nenhuma duplicação de código.

<Callout tone="info" title="Comece pelos embutidos">
  Antes de criar um guard personalizado, verifique se um dos dez guards
  embutidos já cobre o seu caso de uso. Guards personalizados são poderosos,
  mas desnecessários quando um embutido já faz exatamente o que você precisa.
</Callout>
