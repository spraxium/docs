## Por que exceções explícitas importam

Clientes HTTP dependem de status codes estáveis e formatos de resposta estáveis. Lançar classes explícitas de _HttpError_ torna falhas observáveis, testáveis e mais fáceis de monitorar em produção. Toda classe de erro exportada pelo pacote carrega um status code semântico e uma mensagem padrão, então o servidor consegue normalizar respostas sem lógica condicional em cada handler.

Quando controllers retornam erros genéricos, clientes perdem contexto semântico e o comportamento de retry fica frágil. O pacote evita isso ao dar a cada cenário de falha uma classe dedicada que estende a mesma base, garantindo serialização consistente em toda a superfície da API.

## HttpError base class

Todo erro da hierarquia estende _HttpError_, que por sua vez estende a classe nativa _Error_. Ela adiciona uma propriedade _statusCode_ somente leitura e sobrescreve o construtor para aceitar uma mensagem e um status HTTP numérico. Esse formato é o único contrato que a camada de normalização do servidor lê, então qualquer classe que estenda _HttpError_ participa automaticamente do tratamento centralizado de erros sem wiring adicional.

A classe base também define `this.name` com o nome da classe concreta, o que torna stack traces e dashboards de monitoramento imediatamente distinguíveis entre tipos de erro. Subclasses só precisam chamar `super(message, statusCode)` com seus próprios padrões para manter esse contrato.

## Hierarquia de erros exportada pelo pacote

<DropdownGroup>
<Dropdown title="BadRequestError, 400">
  Indica que a requisição é sintaticamente válida, mas semanticamente incorreta
  ou contém combinações de entrada malformadas. Use essa classe quando a lógica
  de domínio rejeitar uma requisição por motivos fora da validação de DTO, como
  referenciar uma entidade em estado inválido ou fornecer parâmetros
  conflitantes. A mensagem padrão é `'Bad request'`.
</Dropdown>

<Dropdown title="ValidationError, 400">
  A única classe de erro que carrega estrutura adicional além de mensagem e
  status code. Ela estende *HttpError* com um array *details* no qual cada
  entrada mapeia o nome de uma propriedade do DTO para as constraints que
  falharam. *ValidationPipe* lança essa classe automaticamente quando a
  validação de *@HttpBody* falha, então você raramente precisa construí-la
  manualmente.
</Dropdown>

<Dropdown title="UnauthorizedError, 401">
  Indica que a requisição não traz credenciais de autenticação válidas. Use essa
  classe quando quem faz a requisição não forneceu nenhuma prova de identidade,
  ao contrário de *ForbiddenError*, que se aplica quando uma identidade já
  autenticada não tem permissão. A mensagem padrão é `'Unauthorized'`.
</Dropdown>

<Dropdown title="ForbiddenError, 403">
  Indica que uma requisição autenticada não tem permissão para executar a ação
  pedida. Use essa classe quando a identidade já estiver estabelecida, mas a
  checagem de autorização falhar, por exemplo quando uma operação de admin é
  tentada por um usuário comum. A mensagem padrão é `'Forbidden'`.
</Dropdown>

<Dropdown title="NotFoundError, 404">
  Indica que o recurso solicitado não existe ou está inacessível pelo contrato.
  Essa é a classe de erro mais comum para endpoints GET e PATCH que buscam
  entidades por ID e não encontram nada. A mensagem padrão é `'Not found'`.
</Dropdown>

<Dropdown title="MethodNotAllowedError, 405">
  Indica que o método HTTP usado na requisição não é suportado pelo endpoint de
  destino. Use essa classe na lógica do controller quando um handler rejeita o
  método de forma condicional por causa do estado do recurso, e não porque a
  rota não está registrada. A mensagem padrão é `'Method not allowed'`.
</Dropdown>

<Dropdown title="ConflictError, 409">
  Indica que a requisição não pode ser concluída por causa de um conflito de
  estado no recurso de destino. Cenários comuns incluem criar um registro
  duplicado, atribuir um valor já atribuído ou executar uma operação que exige
  um estado diferente do recurso. A mensagem padrão é `'Conflict'`.
</Dropdown>

<Dropdown title="UnprocessableEntityError, 422">
  Indica que o servidor entendeu o conteúdo da requisição, mas não consegue
  processá-lo por causa de constraints semânticas. Use essa classe quando uma
  requisição já parseada atende aos requisitos estruturais, mas viola regras de
  negócio que a validação de DTO não consegue impor. A mensagem padrão é
  `'Unprocessable entity'`.
</Dropdown>

<Dropdown title="TooManyRequestsError, 429">
  Indica que o cliente excedeu uma política de rate limit ou de quota.
  *RateLimitMiddleware* retorna uma resposta 429 diretamente, sem lançar essa
  classe, mas você pode lançá-la manualmente na lógica do handler quando
  checagens customizadas de quota falharem. A mensagem padrão é
  `'Too many requests'`.
</Dropdown>

<Dropdown title="InternalServerError, 500">
  Indica uma falha interna inesperada em que ainda se deseja uma resposta JSON
  controlada. Use essa classe ao capturar erros irrecuperáveis que você quer
  expor com um status code previsível, em vez de deixar o fallback genérico 500
  tratá-los. A mensagem padrão é `'Internal server error'`.
</Dropdown>

<Dropdown title="NotImplementedError, 501">
  Indica que uma operação reconhecida ainda não foi implementada na versão
  atual. Use essa classe como placeholder durante o desenvolvimento quando uma
  rota já está registrada, mas seu handler ainda não foi concluído, dando aos
  clientes um sinal semântico em vez de uma resposta 500 vaga. A mensagem padrão
  é `'Not implemented'`.
</Dropdown>

<Dropdown title="ServiceUnavailableError, 503">
  Indica uma indisponibilidade temporária de infraestrutura ou dependência. Use
  essa classe quando o servidor está rodando, mas uma dependência downstream,
  como banco de dados ou API externa, está inacessível, estabelecendo a
  expectativa de que um retry pode funcionar mais tarde. A mensagem padrão é
  `'Service unavailable'`.
</Dropdown>
</DropdownGroup>

## ValidationError e detalhes estruturados

_ValidationError_ é a única classe de erro que carrega mais do que uma mensagem. Ela inclui um array _details_ em que cada entrada mapeia o nome de uma propriedade para as constraints que falharam. Essa estrutura é produzida automaticamente por _ValidationPipe_ quando a validação do payload de body roda pelas regras de _class-validator_.

A interface _ValidationDetail_ expõe dois campos: _property_, o nome do campo do DTO, e _constraints_, um registro que mapeia nomes de regras que falharam para mensagens legíveis por humanos. Como o pipeline usa `whitelist: true` e `forbidNonWhitelisted: true`, qualquer campo inesperado no body também dispara um erro de validação, impedindo que poluição de payload chegue à regra de negócio.

Clientes recebem um formato previsível em que `details` é sempre um array, mesmo quando há só um campo inválido. Isso permite que consumidores da API percorram o array e mapeiem cada entrada para erros inline de formulário ou resumos de erro sem precisar ramificar pela forma da resposta.

  HttpBody,
  HttpController,
  HttpGet,

  NotFoundError,
  ForbiddenError,
  ConflictError,
  ServiceUnavailableError,

import { UpdateGuildConfigDto } from '../dto/update-guild-config.dto';

@HttpController('/guilds')
export class GuildHttpController {
  @HttpGet('/:guildId')
  async getGuild(@HttpParam('guildId') guildId: string) {
    const guild = await this.findGuild(guildId);

    if (!guild) {
      throw new NotFoundError('Guild not found');
    }

    if (!guild.available) {
      throw new ServiceUnavailableError('Guild is temporarily unavailable');
    }

    return { ok: true, guildId: guild.id, name: guild.name };

  }

  @HttpPatch('/:guildId/config')
  @HttpStatus(200)
  async updateConfig(
    @HttpParam('guildId') guildId: string,
    @HttpBody(UpdateGuildConfigDto) body: UpdateGuildConfigDto,
  ) {
    const guild = await this.findGuild(guildId);
    if (!guild) throw new NotFoundError('Guild not found');

    if (guild.locked) {
      throw new ForbiddenError('Guild configuration is locked by an admin');
    }

    if (guild.prefix === body.prefix) {
      throw new ConflictError('Prefix is already set to that value');
    }

    return { ok: true, guildId, applied: body };

  }

## Comportamento de normalização no nível do servidor

*HttpServer* registra dois handlers terminais no fim do pipeline do Hono: *notFound* e *onError*. Juntos, eles garantem que toda saída possível produza uma resposta JSON com o mesmo formato.

O handler *notFound* dispara para qualquer requisição que não corresponda a uma rota registrada e retorna `{ ok: false, error: 'Not Found' }` com status 404. O handler *onError* cobre exceções lançadas usando esta precedência:

1. *ValidationError* retorna status 400 com `{ ok: false, error: 'Validation failed', details: [...] }`;
2. qualquer outra subclasse de *HttpError* retorna seu próprio status code com `{ ok: false, error: message }`;
3. exceções desconhecidas são registradas em log e retornadas como `{ ok: false, error: 'Internal server error' }` com status 500.

Como esse mapeamento é centralizado, controllers devem lançar a classe de erro mais específica disponível e nunca montar payloads JSON de erro ad hoc dentro do handler. A camada de normalização cuida do restante.

## Contrato do formato de resposta

Toda resposta de erro segue o mesmo envelope, independentemente do status code. O campo `ok` é sempre `false`, o campo `error` carrega a mensagem em string e `details` aparece apenas em respostas de *ValidationError*. Isso permite que consumidores da API verifiquem primeiro `ok` e depois desviem para `error` ou `details` sem tratamento especial por endpoint.

## Classes de erro customizadas

Você pode criar suas próprias classes de erro estendendo *HttpError* ou qualquer subclasse existente. A única exigência é chamar `super` com uma mensagem e um status code. Qualquer classe customizada que estenda *HttpError* é capturada e serializada automaticamente pela camada de normalização do servidor, sem mudanças em middleware ou configuração.

export class GuildLockedError extends ForbiddenError {

## Rejeição de guard como fronteira de erro

*GuardExecutor* executa guards globais em sequência antes de qualquer handler de controller. Quando um guard retorna `false`, o executor interrompe a execução e retorna `{ ok: false, error: 'Unauthorized' }` com status 401. Essa resposta é injetada diretamente, e não pelo handler *onError*, o que significa que rejeições de guard são finais e não podem ser capturadas nem modificadas por middleware posterior.

Como o comportamento de guard fica fora do caminho de normalização de *HttpError*, implementações de guard devem manter a semântica de rejeição simples. O formato da resposta 401 segue o mesmo envelope dos demais erros, então clientes não precisam de tratamento especial para falhas de guard.

## Checklist de design para exceções

<Steps>
  <Step title="Lance erros semânticos perto das regras de negócio">
    Lance classes específicas de *HttpError* onde as decisões de domínio são
    tomadas, e não apenas na borda do controller. Lançar um *ConflictError*
    dentro da lógica de service é mais claro do que retornar uma flag e
    convertê-la depois em erro no handler.
  </Step>
  <Step title="Mantenha mensagens acionáveis e estáveis">
    Mensagens de erro devem ajudar clientes e operadores a entender os próximos
    passos sem vazar detalhes internos sensíveis. Uma redação estável também
    melhora deduplicação de alertas e a qualidade dos dashboards ao longo do
    tempo.
  </Step>
  <Step title="Use validação de DTO para garantir o formato">
    Deixe *ValidationPipe* e *class-validator* impor garantias estruturais antes
    de a lógica de domínio rodar. O pipeline usa `whitelist: true` e
    `forbidNonWhitelisted: true` por padrão, o que significa que propriedades
    inesperadas são rejeitadas automaticamente.
  </Step>
  <Step title="Prefira subclasses customizadas a HttpError bruto">
    Crie subclasses com nomes descritivos como *GuildLockedError* ou
    *BridgeUnavailableError* em vez de lançar um *ForbiddenError* puro com uma
    string. Classes nomeadas são mais fáceis de buscar em logs, testar em
    assertions e filtrar em dashboards de monitoramento.
  </Step>
  <Step title="Confie no mapeamento centralizado de resposta">
    Deixe *HttpServer* normalizar erros para JSON de forma consistente, em vez
    de montar payloads de erro ad hoc em cada handler. Um mapeamento unificado é
    mais fácil de testar e raciocinar entre equipes, além de reduzir a chance
    de desvio acidental no formato da resposta.
  </Step>
</Steps>

<Callout tone="warning" title="Nunca exponha detalhes internos de erro para clientes">
  Exceções desconhecidas são capturadas pela camada de normalização e devolvidas
  como uma resposta 500 genérica. A mensagem original do erro é registrada em
  log apenas no lado do servidor. Não sobrescreva esse comportamento para
  encaminhar stack traces brutos ou mensagens internas, porque isso vaza
  detalhes de implementação para consumidores externos.
</Callout>
