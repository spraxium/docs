## A segurança começa antes dos controllers

_HttpServer_ aplica middleware de segurança antes que qualquer handler de controller seja invocado. Esse wiring na inicialização dá a todo endpoint a mesma política de base desde a primeira requisição, sem exigir decoração explícita em cada rota. A pilha de segurança roda em uma ordem fixa que o código do usuário não pode reordenar, garantindo que hardening de headers e limites de body sejam sempre a primeira linha de defesa.

Quando HTTP está habilitado, o runtime conecta essas proteções nesta sequência exata:

1. Remoção opcional dos headers `X-Powered-By` e `Server` (_hidePoweredBy_, com padrão `true`).
2. _SecurityHeadersMiddleware_ envolvendo _secureHeaders_ do Hono, a menos que `headers` esteja como `false`.
3. _CorsMiddleware_ envolvendo _cors_ do Hono, apenas quando `security.cors` estiver configurado.
4. _BodyLimitMiddleware_ envolvendo _bodyLimit_ do Hono, a menos que `bodyLimit` esteja como `false`.
5. Instâncias globais de middleware vindas de _@HttpClientModule({ middleware })_.
6. Guards globais de _@HttpClientModule({ guards })_ por meio de _GuardExecutor_.
7. Guards por controller e por rota de _@HttpGuards_ por meio de _GuardExecutor_.

Depois dessa pilha, roda o middleware em nível de rota vindo de decorators _@HttpUseMiddleware_, e por fim o próprio handler é executado. Esse modelo em camadas significa que decisões de guard acontecem depois do hardening de base, e decisões de middleware acontecem depois que os headers de segurança já foram definidos.

## Valores padrão de segurança

Todo header e limite de segurança tem um padrão seguro vindo de _SECURITY_DEFAULTS_. Você só precisa sobrescrever valores quando sua implantação exigir comportamento diferente. Quando um subcampo é omitido, o padrão se aplica. Quando é definido como `false`, aquela camada é desativada por completo.

<DropdownGroup>
<Dropdown title="hidePoweredBy: true">
  Remove os headers `X-Powered-By` e `Server` de toda resposta. Isso evita
  fingerprinting de framework e runtime, técnica usada por atacantes para
  identificar vulnerabilidades conhecidas em versões específicas de software.
  Mantenha isso habilitado, a menos que exista um motivo específico para expor a
  pilha do servidor.
</Dropdown>

<Dropdown title="X-Frame-Options: DENY">
  Impede que a página de resposta seja embutida em um iframe em qualquer domínio.
  Isso bloqueia ataques de clickjacking em que um site malicioso sobrepõe frames
  transparentes para induzir usuários a clicar em elementos escondidos. Defina
  como `SAMEORIGIN` se páginas suas precisarem se embutir mutuamente.
</Dropdown>

<Dropdown title="X-Content-Type-Options: nosniff">
  Impede que navegadores façam MIME sniffing das respostas ignorando o header
  `Content-Type` declarado. Sem esse header, navegadores podem interpretar uma
  resposta JSON como HTML, o que abre espaço para XSS por confusão de content
  type. Esse header não tem variantes de configuração e deve permanecer sempre
  habilitado.
</Dropdown>

<Dropdown title="Strict-Transport-Security: max-age=31536000; includeSubDomains">
  Força HTTPS no nível do user agent por um ano, cobrindo subdomínios. Depois da
  primeira resposta HTTPS, navegadores se recusam a conectar por HTTP puro até
  que o max-age expire. Ajuste *hstsMaxAge* e *hstsIncludeSubDomains* na
  configuração de segurança se sua implantação exigir valores diferentes.
</Dropdown>

<Dropdown title="Content-Security-Policy: default-src 'none'">
  Aplica um padrão zero trust para carregamento de conteúdo, bloqueando todos os
  scripts, estilos, imagens e mídias, a menos que sejam explicitamente
  permitidos. Esse é o CSP mais restritivo possível e faz sentido para
  servidores somente de API, que nunca entregam páginas HTML. Sobrescreva
  *contentSecurityPolicy* com uma string de diretivas customizada se seus
  endpoints servirem conteúdo renderizado no navegador.
</Dropdown>

<Dropdown title="Referrer-Policy: no-referrer">
  Suprime o header `Referer` em todas as requisições de saída originadas da
  página de resposta. Isso evita vazamento de caminhos de URL e parâmetros de
  query para serviços de terceiros. Use `strict-origin-when-cross-origin` se seu
  analytics ou CDN precisar de informação de referrer.
</Dropdown>

<Dropdown title="X-XSS-Protection: 1; mode=block">
  Habilita filtros legados de XSS do navegador em modo de bloqueio, instruindo o
  navegador a parar de renderizar a página se um ataque XSS refletido for
  detectado. Navegadores modernos dependem de CSP no lugar disso, mas esse
  header fornece defesa em profundidade para user agents mais antigos. Não há
  desvantagem prática em mantê-lo ligado.
</Dropdown>

<Dropdown title="Permissions-Policy: camera=(), microphone=(), geolocation=()">
  Nega por padrão o acesso a APIs sensíveis do navegador, como câmera,
  microfone e geolocalização. Isso impede que scripts maliciosos acessem o
  hardware do dispositivo mesmo que consigam contornar restrições de CSP.
  Expanda a lista da policy se as respostas da sua API forem consumidas por
  páginas de navegador que precisem de permissões específicas.
</Dropdown>

<Dropdown title="Cross-Origin-Opener-Policy: same-origin">
  Isola o contexto de navegação para evitar ataques cross-origin, como Spectre,
  que exploram memória compartilhada de processo. Quando definido como
  `same-origin`, a página não pode compartilhar grupo de contexto de navegação
  com documentos de outra origem. Esse é o padrão recomendado para qualquer
  servidor que lide com dados sensíveis.
</Dropdown>

<Dropdown title="Body limit: 102400 bytes (100 KB)">
  Rejeita payloads de requisição que ultrapassem o tamanho máximo configurado
  com status 413 e uma resposta de erro estruturada. O padrão de 100 KB é
  apropriado para a maioria dos endpoints de API que aceitam JSON. Sobrescreva
  *bodyLimit.maxSize* na configuração de segurança para endpoints que lidam com
  uploads de arquivos ou payloads grandes.
</Dropdown>
</DropdownGroup>

## Pipeline de guards e a interface HttpGuard

Guards são a fronteira de autenticação e autorização. Todo guard implementa a interface _HttpGuard_, que define um único método: `canActivate(ctx: Context): Promise<boolean>`. Guards declarados em _@HttpClientModule({ guards })_ são instanciados pelo sistema de injeção de dependência na inicialização e executados em sequência por _GuardExecutor_ em toda requisição depois da pilha de middleware de segurança. Nenhuma chamada manual a `new` é necessária ao declarar guards no módulo.

Quando _GuardExecutor_ encontra um guard que retorna `false`, ele interrompe a execução imediatamente e define a resposta como `{ ok: false, error: 'Unauthorized' }` com status 401. Nenhum outro guard, middleware ou handler é executado. Esse comportamento de short-circuit significa que a ordem dos guards importa: coloque primeiro o caso de rejeição mais comum para evitar checagens caras em requisições não autenticadas.

A resposta 401 da rejeição de guard é injetada diretamente, e não pelo handler _onError_. Isso significa que falhas de guard são finais e não podem ser capturadas nem modificadas por middleware downstream. O formato da resposta segue o mesmo envelope usado pelos outros erros, então clientes não precisam de tratamento especial para rejeições de guard.

## @HttpGuards para proteção por controller e por rota

_@HttpGuards_ é um decorator de classe ou método que restringe o escopo do guard a um controller específico ou a uma rota individual. Ao contrário de guards globais, que protegem todo endpoint, _@HttpGuards_ mira um ponto único da superfície de roteamento. O decorator aceita uma ou mais classes de guard cujas instâncias são resolvidas pelo mesmo sistema de DI usado por services e controllers.

_@HttpGuards_ em nível de classe roda em toda rota do controller. _@HttpGuards_ em nível de método roda apenas naquele handler específico. Quando os dois níveis estão presentes, guards de classe executam primeiro, seguidos pelos guards de método. Essa organização em camadas permite proteger um controller inteiro com uma política compartilhada e adicionar validação extra por rota sem repetir o guard comum.

## ApiKeyGuard em detalhe

*ApiKeyGuard* é o guard nativo que acompanha o pacote. Ele lê o header `x-api-key` da requisição e o compara com o valor fornecido na construção. A comparação usa `timingSafeEqual` do módulo `crypto` do Node para evitar ataques de timing que poderiam vazar informação sobre o tamanho da chave ou seu prefixo.

O guard rejeita requisições em três cenários: header ausente, retornando `false` imediatamente; buffers com tamanho diferente, retornando `false` sem comparar, para respeitar a exigência de tamanhos iguais do `timingSafeEqual`; e valores diferentes, retornando `false` depois da comparação em tempo constante. Essa estratégia de rejeição em camadas evita expor o tamanho da chave por diferenças no tempo de resposta.

*ApiKeyGuard* é ativado automaticamente quando `apiKey` é definido em *defineHttp*. O runtime cria e registra internamente a instância do guard, então você não precisa declará-la em *@HttpClientModule({ guards })*. O array `guards` fica reservado para guards customizados que exigem dependências resolvidas pela sua DI.

## Modelo de execução de middleware

O pacote oferece dois pontos de entrada para middleware, com escopos e mecanismos de registro diferentes.

Instâncias globais de middleware são declaradas em *@HttpClientModule({ middleware })* como um array de objetos *HttpMiddleware*. Elas são registradas no caminho `'*'` do Hono, o que significa que rodam em toda requisição depois da pilha de segurança, mas antes da execução dos guards. Use middleware global para preocupações transversais que se aplicam sem condição, como logging de requisição via *LoggerMiddleware*.

Middleware em nível de rota usa tokens de classe e o decorator *@HttpUseMiddleware*. O token de classe precisa ser mapeado para uma instância concreta em *@HttpClientModule({ middlewareProviders })*. *RouteBuilder* resolve o token durante o binding da rota e insere o handler de middleware antes do handler da rota na cadeia do Hono. *@HttpUseMiddleware* em nível de classe roda antes de *@HttpUseMiddleware* em nível de método, e ambos rodam depois dos guards e do middleware global.

Todo middleware implementa a interface *HttpMiddleware*: `handle(ctx: Context, next: Next): Promise<undefined | Response>`. Chamar `await next()` passa o controle ao próximo middleware ou handler. Não chamar `next()` encerra a requisição naquele middleware, que é justamente como *RateLimitMiddleware* rejeita requisições acima do limite.

## Referência de middleware embutido

<DropdownGroup>
<Dropdown title="SecurityHeadersMiddleware: Automatic">
  Envolve *secureHeaders* do Hono e aplica todos os headers padrão de
  *SECURITY_DEFAULTS.headers*. Esse middleware faz parte da pilha automática de
  segurança e roda em toda requisição antes de qualquer handler de controller.
  Configure headers individuais por *SecurityHeadersConfig* no bloco
  *security.headers*.
</Dropdown>

<Dropdown title="CorsMiddleware: Automatic">
  Envolve *cors* do Hono e trata requisições preflight `OPTIONS` junto com os
  headers `Access-Control-*`. Esse middleware só é ativado quando
  `security.cors` está configurado na definição do plugin HTTP. Ele suporta
  arrays de origens, wildcard, credentials e max-age para cache de preflight.
</Dropdown>

<Dropdown title="BodyLimitMiddleware: Automatic">
  Envolve *bodyLimit* do Hono e rejeita payloads que ultrapassam *maxSize* com
  status 413 e uma resposta de erro estruturada. O corpo da resposta segue o
  mesmo envelope `{ ok: false, error: 'Payload too large', maxSize }` usado nos
  demais erros. Desative-o definindo `bodyLimit` como `false` na configuração de
  segurança.
</Dropdown>

<Dropdown title="RateLimitMiddleware: Manual (global or route)">
  Implementa um rate limiter em memória com janela deslizante que aceita uma
  configuração `{ windowMs, max }`. A identificação do cliente usa o header
  `x-forwarded-for`, fazendo fallback para `'unknown'` quando o header está
  ausente. Requisições acima do limite recebem status 429, e entradas antigas
  são removidas periodicamente.
</Dropdown>

<Dropdown title="LoggerMiddleware: Manual (global or route)">
  Registra `METHOD path status durationMs` para cada requisição que passa por
  ele. Requisições com status code 400 ou superior são registradas em nível
  `warn` para facilitar a filtragem em pipelines de observabilidade. Nenhuma
  configuração é necessária; basta instanciar e registrar em
  *HttpClientModule({ middleware })*.
</Dropdown>
</DropdownGroup>

## Estratégia de rate limiting

*RateLimitMiddleware* implementa um rate limiter em memória com janela deslizante. Cada cliente é identificado pelo valor do header `x-forwarded-for`, ou por `'unknown'` quando o header está ausente. O middleware mantém um `Map<string, WindowEntry>` em que cada entrada rastreia a contagem de requisições e o timestamp de início da janela.

Quando uma requisição chega, o middleware verifica se a janela atual expirou. Se expirou, a entrada é reiniciada. Se a janela ainda estiver ativa e a contagem ultrapassar *max*, o middleware responde com `{ ok: false, error: 'Too many requests' }` no status 429 sem chamar `next()`. Um intervalo periódico de limpeza remove entradas de clientes que não enviaram requisições dentro da duração da janela.

Para usar rate limiting por rota, estenda *RateLimitMiddleware* com sua própria configuração e registre a instância em *middlewareProviders*. Esse padrão mantém a configuração de rate limit visível no nível da classe de middleware e evita números mágicos em argumentos de decorator.

## Confiança em proxy e identificação de IP

O middleware de rate limit lê `x-forwarded-for` diretamente, sem verificar a origem. Em produção atrás de proxies reversos ou load balancers, isso significa que você precisa garantir que sua infraestrutura de proxy defina esse header corretamente. Se o header estiver ausente, todas as requisições ficam agrupadas sob a chave `'unknown'`, o que na prática cria um único bucket global de rate limit. Se o header puder ser falsificado porque o proxy não o sobrescreve, atacantes podem contornar o rate limit enviando IPs falsos no header.

A interface *SecurityConfig* inclui um campo *trustedProxies* com um array *proxies*, cujo padrão é `['127.0.0.1', '::1']`. Use esse campo para documentar sua configuração de proxies confiáveis e garanta que sua arquitetura de implantação só permita que proxies confiáveis definam headers de encaminhamento.

## Checklist operacional de hardening

<Steps>
  <Step title="Comece com padrões seguros">
    Habilite headers de base e limites de body, a menos que exista um requisito
    claro para relaxá-los. Uma postura de negação por padrão é mais fácil de
    auditar do que uma postura permissiva remendada depois. Sobrescreva headers
    individuais apenas quando sua implantação exigir.
  </Step>
  <Step title="Registre guards globais no AppModule">
    Declare classes de guard customizadas em *@HttpClientModule({ guards })*
    para proteger todo endpoint com a mesma política. O framework resolve as
    dependências dos guards a partir do container de DI, então guards podem
    injetar services como *AppEnv* sem wiring manual. Use `apiKey` em
    *defineHttp* para ativar *ApiKeyGuard* automaticamente, sem declará-lo no
    array de guards.
  </Step>
  <Step title="Restrinja a proteção com @HttpGuards">
    Aplique *@HttpGuards* em nível de controller ou método para endpoints que
    exigem lógica de autorização diferente ou adicional. Isso mantém o guard
    global focado na política de base e leva checagens específicas de rota para
    o ponto de declaração. Guards de classe executam antes de guards de método no
    mesmo controller.
  </Step>
  <Step title="Adicione LoggerMiddleware para observabilidade">
    Registre `new LoggerMiddleware()` em *@HttpClientModule({ middleware })* para
    obter logging básico de requisições. O middleware registra método, caminho,
    status e duração. Status codes 400 ou superiores são registrados em nível
    warn para facilitar a filtragem.
  </Step>
  <Step title="Aplique rate limits a endpoints sensíveis">
    Estenda *RateLimitMiddleware* com configurações por rota e registre por meio
    de *middlewareProviders*. Aplique com *@HttpUseMiddleware* em endpoints que
    lidam com operações caras ou mutações sensíveis, em vez de impor um único
    limite global.
  </Step>
  <Step title="Valide configurações de confiança em proxy e IP">
    Se rate limiting ou logging de auditoria depende do IP do cliente, verifique
    como seu proxy reverso encaminha `x-forwarded-for`. Uma configuração de
    confiança incorreta pode agrupar usuários sem relação no mesmo bucket ou
    permitir que clientes maliciosos falsifiquem sua identidade.
  </Step>
</Steps>

<Callout tone="warning" title="A postura de segurança continua sendo responsabilidade do seu design">
  O pacote oferece primitivas e padrões seguros, mas decisões finais de política
  precisam estar explícitas no seu AppModule e na arquitetura de implantação.
  Revise headers de segurança, origens de CORS e configuração de guard em toda
  revisão de deploy.
</Callout>
