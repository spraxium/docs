## Fluxos de falha

Quando um prefix command falha em qualquer etapa, o framework gera uma exceção específica que você pode interceptar e formatar. Entender essa taxonomia de falhas ajuda a projetar respostas de erro amigáveis, em vez de deixar erros brutos vazarem para o chat. Cada tipo de falha corresponde a uma classe de exceção distinta com seu próprio hook de layout.

<DropdownGroup>
  <Dropdown title="CommandNotFoundException (comando desconhecido)">
    É lançada quando o prefixo é reconhecido, mas o nome do comando não
    corresponde a nenhuma entrada no registry. A exceção expõe o nome de
    *command* tentado e o *prefix* correspondente como propriedades. Você pode
    interceptá-la com um exception layout para enviar uma resposta útil, ou
    ativar *replyOnNotFound* em *PrefixConfig* para ter feedback automático sem
    um layout customizado.
  </Dropdown>
  <Dropdown title="ArgumentException (argumento ausente ou inválido)">
    É lançada quando um argumento obrigatório está ausente ou quando a coerção
    de tipo ou a validação falha para um valor informado. A exceção expõe o
    *name* do argumento, a restrição *expected*, a entrada bruta *received* e a
    string de *usage* definida no comando. Registre um layout para
    *ArgumentException* para exibir mensagens de erro consistentes em todos os
    comandos.
  </Dropdown>
  <Dropdown title="ForbiddenException ou custom (negação por guard)">
    É lançada quando o método *canActivate* de um guard retorna `false` ou
    lança uma exceção. Se o guard retornar `false`, o framework lança uma
    *ForbiddenException* automaticamente. Se o guard lançar sua própria
    exceção, ela se propaga sem alterações e pode ser capturada por um layout
    compatível.
  </Dropdown>
  <Dropdown title="Cooldown ativo (bloqueio silencioso)">
    Quando uma pessoa usuária aciona um comando antes de o cooldown expirar, o
    framework bloqueia a execução silenciosamente, sem lançar exceção. Você
    pode ler os segundos restantes em *PrefixCooldownManager.check* e enviar
    uma resposta customizada a partir de um cooldown guard se quiser feedback
    visível para a pessoa usuária.
  </Dropdown>
</DropdownGroup>

## Layouts de exceção

Exception layouts permitem definir respostas personalizadas para tipos específicos de exceção. Em vez de escrever blocos try-catch em todo handler, você registra um layout uma vez e o framework o aplica automaticamente sempre que aquele tipo de exceção é lançado durante a execução de um prefix command. Isso mantém os handlers limpos e padroniza a formatação de erros em todo o bot.

Um layout recebe o _Message_ original e a exceção lançada, então você pode montar embeds de erro ricos em contexto sobre o que deu errado. O helper _defineExceptionLayout_ cria uma factory de layout que o framework descobre por meio do registro do módulo.

<CodeTabs>
  <Tab label="Layout de argumento" language="typescript">
```typescript filename="src/modules/prefix/layouts/argument-exception.layout.ts"
import { defineExceptionLayout } from '@spraxium/core';
import { ArgumentException } from '@spraxium/common';

export const ArgumentExceptionLayout = defineExceptionLayout(
  ArgumentException,
  async (message, exception) => {
    await message.reply({
      content: `Invalid argument: **${exception.argName}** - ${exception.message}`,
    });
  },
);
```
  </Tab>
  <Tab label="Layout para não encontrado" language="typescript">
```typescript filename="src/modules/prefix/layouts/not-found.layout.ts"
import { defineExceptionLayout } from '@spraxium/core';
import { CommandNotFoundException } from '@spraxium/common';

export const CommandNotFoundLayout = defineExceptionLayout(
  CommandNotFoundException,
  async (message, exception) => {
    await message.reply({
      content: `Command \`${exception.commandName}\` not found. Use \`!help\` to see available commands.`,
    });
  },
);
```
  </Tab>
</CodeTabs>

Registre os layouts no módulo ao lado dos comandos e handlers. O framework os coleta durante a inicialização do módulo e os aplica automaticamente aos tipos de exceção corretos.

```typescript filename="src/modules/prefix/prefix.module.ts"
import { Module } from '@spraxium/common';
import { RollCommand } from './commands/roll.command';
import { RollHandler } from './handlers/roll.handler';
import { ArgumentExceptionLayout } from './layouts/argument-exception.layout';
import { CommandNotFoundLayout } from './layouts/not-found.layout';

@Module({
  commands: [RollCommand],
  handlers: [RollHandler],
  layouts: [ArgumentExceptionLayout, CommandNotFoundLayout],
})
export class PrefixModule {}
```

## Inspeção do dispatcher

O _PrefixDispatcher_ expõe métodos para inspecionar a árvore de comandos registrada em runtime. O método _getCommandInfo_ retorna um array de objetos _PrefixCommandInfo_ com nomes de comandos, descrições, listas de subcomandos e schemas de argumentos. Essa é a base para construir comandos de ajuda dinâmicos.

O dispatcher também expõe _getResolved_ para os vínculos comando-handler já resolvidos, _size_ para o número total de entradas registradas, _commandCount_ para comandos de nível superior distintos e _guildPrefixes_ para o gerenciador de prefixos por guild. Esses métodos de introspecção são úteis em painéis administrativos, health checks e ferramentas de depuração.

```typescript filename="src/modules/prefix/handlers/help-command.handler.ts"
import { Ctx, PrefixCommandHandler } from '@spraxium/common';
import { PrefixDispatcher } from '@spraxium/core';
import type { Message } from 'discord.js';
import { HelpCommand } from '../commands/help.command';

@PrefixCommandHandler(HelpCommand)
export class HelpHandler {
  constructor(private readonly dispatcher: PrefixDispatcher) {}

  async handle(@Ctx() message: Message): Promise<void> {
    const commands = this.dispatcher.getCommandInfo();
    const lines = commands.map((cmd) => {
      const subs = cmd.subcommands?.map((s) => s.name).join(', ');
      return subs
        ? `**${cmd.name}** - subcommands: ${subs}`
        : `**${cmd.name}**`;
    });
    await message.reply(lines.join('\n') || 'No commands registered.');
  }
}
```

## Guards com prefix commands

Prefix commands aceitam o mesmo sistema de guards usado por slash commands e listeners. Decore uma classe handler com _@UseGuards_ para anexar um ou mais guards que rodam antes da execução do handler. Se qualquer guard retornar `false` ou lançar uma exceção, o handler é ignorado. Guards são úteis para verificações de permissão, restrições por cargo e filtros por tipo de canal.

Guards recebem o contexto de execução, que para prefix commands inclui o objeto _Message_ original. Você pode reutilizar as mesmas classes de guard em prefix commands, slash commands e listeners sem modificações. Esse é um dos benefícios da arquitetura unificada de guards.

<CodeTabs>
  <Tab label="Guard" language="typescript">
```typescript filename="src/modules/moderation/guards/moderator.guard.ts"
import { CanActivate, ExecutionContext } from '@spraxium/common';

export class ModeratorGuard implements CanActivate {
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const message = context.getMessage();
    const member = message.member;
    if (!member) return false;
    return member.permissions.has('ModerateMembers');
  }
}
```
  </Tab>
  <Tab label="Handler com guard" language="typescript">
```typescript filename="src/modules/moderation/handlers/ban-command.handler.ts"
import { Ctx, PrefixArg, PrefixCommandHandler, UseGuards } from '@spraxium/common';
import type { Message } from 'discord.js';
import { ModeratorGuard } from '../guards/moderator.guard';
import { ModCommand } from '../commands/mod.command';

@UseGuards(ModeratorGuard)
@PrefixCommandHandler(ModCommand, { subcommand: 'ban' })
export class BanHandler {
  async handle(
    @Ctx() message: Message,
    @PrefixArg('target') targetId: string,
    @PrefixArg('reason') reason: string | undefined,
  ): Promise<void> {
    await message.guild?.members.ban(targetId, { reason: reason ?? 'No reason provided' });
    await message.reply(`Banned <@${targetId}>.`);
  }
}

```
