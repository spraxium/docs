## Visão geral

Três comandos cobrem todo o ciclo de desenvolvimento no Spraxium: _spraxium dev_ para a iteração local, _spraxium build_ para gerar um artefato de produção e _spraxium start_ para executar esse artefato. Esta página reúne os três para que você entenda como eles se conectam sem precisar pular entre documentos.

## spraxium dev

_spraxium dev_ inicia um servidor de desenvolvimento que observa os arquivos e reinicia a aplicação automaticamente quando o código-fonte muda. Ele usa SWC para carregar TypeScript sem uma etapa separada de compilação, mantendo os reinícios rápidos mesmo em projetos grandes. O observador reage aos padrões glob `include` e `exclude` da sua configuração e aplica um debounce configurável para agrupar salvamentos rápidos em um único reinício.

```bash filename="terminal"
spraxium dev
```

### Configuração do dev

```typescript filename="spraxium.config.ts"
export default {
  dev: {
    entrypoint: 'src/main.ts',
    include: ['src/**'],
    exclude: ['src/**/*.spec.ts'],
    debounce: 300,
  },
};
```

<DropdownGroup>
<Dropdown title="entrypoint">
  Arquivo a partir do qual o processo de dev é iniciado. O padrão é `src/main.ts`, se ele existir, e depois `main.ts`. Substitua esse valor quando o seu arquivo de bootstrap estiver fora do local convencional.
</Dropdown>

<Dropdown title="include">
  Padrões glob para arquivos que podem disparar um reinício. Reduzir essa lista
  diminui reinícios desnecessários causados por arquivos que não deveriam afetar o comportamento em execução.
</Dropdown>

<Dropdown title="exclude">
  Arquivos correspondentes aqui são ignorados pelo observador, mesmo se também
  estiverem dentro de um padrão `include`. Use isso para pular arquivos de teste,
  código gerado ou qualquer caminho que mude com frequência sem afetar o processo em execução.
</Dropdown>

<Dropdown title="debounce">
  Quantos milissegundos esperar após uma mudança em arquivo antes de reiniciar. O padrão é 300 ms. Aumente esse valor ao salvar vários arquivos ao mesmo tempo para evitar vários reinícios em sequência.
</Dropdown>
</DropdownGroup>

<Callout tone="info" title="As exclusões padrão estão sempre ativas">
  Mesmo sem um bloco de configuração, o observador ignora node_modules, .git e
  .spraxium para evitar ciclos de reinício causados por instalações de dependências ou artefatos de build.
</Callout>

### Recuperação após falhas

Se o processo do bot falhar, o servidor de dev não encerra. Ele aplica um atraso com backoff exponencial antes de iniciar de novo, calculado como `Math.min(1000 * 2 ** crashCount, maxBackoff)`. Isso evita um ciclo apertado de relançamentos quando a falha é reproduzível. Corrija o erro, salve o arquivo, e o observador fará um reinício normal.

## spraxium build

_spraxium build_ valida os tipos e produz um bundle pronto para produção. Ele roda em duas etapas sequenciais: primeiro a verificação de tipos e depois o bundler. Se a verificação falhar, o bundler nem chega a executar, então você recebe um código de saída limpo, confiável para pipelines de CI.

```bash filename="terminal"
spraxium build
```

### O que acontece

<Steps>
  <Step title="Verificação de tipos">
    Executa `tsc --noEmit` no seu projeto. Qualquer erro de tipo faz o comando
    falhar imediatamente. Corrija todos os erros de TypeScript antes que o bundler possa continuar.
  </Step>
  <Step title="Empacotamento">
    Executa `tsdown` com a configuração do seu projeto. Se existir um arquivo
    `tsdown.config.*` na raiz do projeto, a CLI o utiliza. Caso contrário, aplica estes padrões:
    pontos de entrada `src/main.ts` e `spraxium.config.ts`, diretório de saída `.spraxium/dist`,
    formato ESM, plataforma Node, `--clean` e `--no-dts`.
  </Step>
</Steps>

A saída compilada vai para `.spraxium/dist/` por padrão. Esse diretório é o artefato que _spraxium start_ procura.

<Callout tone="warning" title="O build não executa testes">
  Rodar *spraxium build* não executa sua suíte de testes. Rode os testes
  separadamente, antes ou depois, e trate o build apenas como uma etapa de validação de tipos e empacotamento.
</Callout>

## spraxium start

_spraxium start_ executa o artefato compilado produzido por _spraxium build_. Antes de iniciar, ele define `NODE_ENV=production` e herda o stdio do processo atual para que os logs da aplicação sejam exibidos diretamente no terminal.

```bash filename="terminal"
spraxium start
```

### Resolução do ponto de entrada

A CLI verifica os caminhos abaixo em ordem e executa o primeiro que encontrar:

1. `.spraxium/dist/src/main.js`
2. `.spraxium/dist/main.js`
3. `dist/src/main.js`
4. `dist/main.js`
5. `build/src/main.js`
6. `build/main.js`

<Callout tone="warning" title="Sem build, não há start">
  Se nenhum dos caminhos candidatos existir, o comando falha e mostra uma mensagem
  pedindo para você executar *spraxium build* primeiro. Garanta que variáveis de ambiente
  como DISCORD_TOKEN estejam carregadas antes de rodar este comando.
</Callout>

## Fluxo típico

Uma iteração completa, do desenvolvimento à produção, costuma seguir esta ordem: use _spraxium dev_ durante o trabalho ativo, mude para _spraxium build_ ao preparar uma release e, por fim, rode _spraxium start_ para verificar ou implantar o artefato compilado. Em CI, pule totalmente a etapa de dev e execute build seguido de start como pipeline de validação.

## Bloqueio de processo

O Spraxium grava um arquivo de lock por projeto em `.spraxium/spraxium.lock` ao iniciar e o remove em um desligamento limpo. Se uma segunda instância detectar esse lock, ela encerra com um aviso de conflito em vez de duplicar listeners e registros de comandos silenciosamente.

### Flags

Tanto _spraxium dev_ quanto _spraxium start_ oferecem duas flags relacionadas ao lock:

<Table>
  <TableHead>
    <TableRow>
      <TableCell header>Flag</TableCell>
      <TableCell header>Variável de ambiente</TableCell>
      <TableCell header>Descrição</TableCell>
    </TableRow>
  </TableHead>
  <TableBody>
    <TableRow>
      <TableCell>*--force-unlock*</TableCell>
      <TableCell>*SPRAXIUM_FORCE_UNLOCK=1*</TableCell>
      <TableCell>Encerra o processo do bot existente, junto com o launcher do observador de dev para impedir um retorno automático, e então assume o controle. O terminal é liberado logo após o encerramento.</TableCell>
    </TableRow>
    <TableRow>
      <TableCell>*--no-lock*</TableCell>
      <TableCell>*SPRAXIUM_NO_LOCK=1*</TableCell>
      <TableCell>Pula totalmente a verificação de lock. Use isso apenas em cenários que executam instâncias concorrentes de propósito, como um ambiente de testes rodando ao lado da produção.</TableCell>
    </TableRow>
  </TableBody>
</Table>

```bash filename="terminal"
# Kill the running instance and take over
spraxium dev --force-unlock

# Skip the lock check (concurrent instances allowed)
spraxium dev --no-lock
```

Locks obsoletos deixados por processos que falharam são detectados automaticamente com `process.kill(pid, 0)` e removidos antes da inicialização, então você só verá avisos de conflito quando a outra instância realmente estiver em execução.

## Notificador de atualização

Na inicialização, o Spraxium examina `node_modules/@spraxium/*` para encontrar todos os pacotes do framework instalados no projeto, consulta o registro do npm pelas versões mais recentes e mostra um aviso se algum pacote estiver desatualizado. Essa verificação roda em segundo plano e nunca atrasa a inicialização.

Os resultados são armazenados em cache em `~/.spraxium/upgrade-check.json`, com TTL de 24 horas compartilhado por todos os projetos da máquina. Se um pacote tiver sido instalado recentemente e ainda não estiver no cache, apenas esse pacote será buscado, enquanto o restante usará os dados já armazenados.

Defina `SPRAXIUM_NO_UPGRADE_NOTIFIER=1`, ou a variável de ambiente com o mesmo nome, para desativar completamente essa verificação. Isso é útil em ambientes de CI, nos quais o aviso gera mais ruído do que sinal.
