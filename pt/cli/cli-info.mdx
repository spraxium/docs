## Quando usar

Use _spraxium info_ sempre que precisar de um retrato rápido de diagnóstico da máquina e do projeto atuais. Ele é especialmente útil antes de abrir issues, depois de upgrades, quando a CI se comporta de forma diferente do desenvolvimento local ou quando você precisa confirmar exatamente quais pacotes do Spraxium um projeto está usando.

```bash filename="terminal"
spraxium info
spraxium info --json
```

Se você só precisa de uma checagem rápida para leitura humana, a saída padrão no terminal já basta. Se o resultado for para um ticket, script ou artefato de CI, prefira o modo JSON, assim o relatório completo pode ser copiado e analisado sem perder detalhes.

## O que o relatório inclui

O comando monta um relatório com a versão da CLI, o nome de projeto detectado, a versão do Node, o sistema operacional e o caminho do runtime. Ele também captura o gerenciador de pacotes preferido e as versões detectadas de npm, pnpm, yarn e bun. Por fim, percorre o projeto e o workspace em busca de todos os pacotes `@spraxium/*` instalados e lista a versão de cada um.

Essa combinação importa porque a maioria das perguntas de troubleshooting começa com uma destas incertezas:

1. Qual versão da CLI está realmente em execução?
2. A máquina está usando o runtime do Node esperado?
3. O projeto está no gerenciador de pacotes que o time espera?
4. Os pacotes do framework estão alinhados ou há algum atrasado em relação aos demais?

_spraxium info_ responde a essas perguntas de uma vez, em vez de obrigar você a levantar tudo manualmente.

## Como ler o relatório

<Steps>
  <Step title="Verifique o runtime primeiro">
    Comece pela versão do Node, sistema operacional e caminho do runtime. Se uma
    máquina falha e outra funciona, este costuma ser o lugar mais rápido para
    encontrar uma diferença de ambiente.
  </Step>
  <Step title="Verifique o gerenciador de pacotes em seguida">
    Confirme se o projeto está usando pnpm, npm, yarn ou bun. Problemas de
    resolução de dependências e drift de lockfile costumam começar aqui.
  </Step>
  <Step title="Verifique o alinhamento dos pacotes Spraxium">
    Compare as versões encontradas de *@spraxium/*. Versões misturadas são uma
    fonte comum de comportamentos estranhos do framework depois de upgrades parciais.
  </Step>
</Steps>

## Modos de saída

<DropdownGroup>
<Dropdown title="Legível por humanos (spraxium info)">
  Imprime um resumo formatado diretamente no terminal. Use para uma inspeção visual rápida antes de abrir uma issue ou durante uma sessão de depuração em que você só precisa de uma visão geral do ambiente.
</Dropdown>

<Dropdown title="JSON (spraxium info --json)">
  Emite o relatório completo como `JSON.stringify(report, null, 2)`. Use em scripts de automação, pipelines de CI que armazenam o relatório como artefato de build ou quando você precisar analisar campos específicos programaticamente.
</Dropdown>
</DropdownGroup>

<Callout tone="info" title="Prefira JSON ao compartilhar diagnósticos">
  A saída padrão é mais fácil de ler no terminal. A saída JSON é melhor quando o
  relatório será colado em uma issue, armazenado em CI ou comparado entre
  máquinas.
</Callout>

## Onde e quem deve usar

- Suporte interno: pedir o contexto mínimo de quem reporta.
- Relatórios públicos de bug: anexar diagnósticos em templates de issue.
- Depuração em CI: persistir o relatório como artefato de build.

Usuários avançados também se beneficiam disso depois de upgrades de dependência. Se um workspace de repente se comportar de forma diferente depois de atualizar pacotes, _spraxium info_ é a maneira mais rápida de confirmar se as versões resolvidas correspondem ao que você pretendia instalar.

## Modelo rápido de issue

```text
Problem summary:
Reproduction steps:
Expected result:
Actual result:
Output from `spraxium info --json`:
```

## Hábito útil

Se o seu time dá suporte a múltiplos bots ou ambientes, inclua _spraxium info --json_ no template padrão de relatório de bugs. Esse pequeno hábito elimina bastante ida e volta antes mesmo de a depuração real começar.
