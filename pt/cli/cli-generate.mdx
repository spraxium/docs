## O que ele faz

_spraxium generate_ cria um novo arquivo-fonte a partir de um schematic nomeado e o conecta ao módulo correto. O comando aceita o nome do schematic e o nome do arquivo como argumentos; se um deles for omitido, aparece um seletor interativo. Todos os nomes de classe gerados são normalizados para PascalCase e os nomes de arquivo para kebab-case, então você não precisa se preocupar manualmente com convenções de nomenclatura.

```bash filename="terminal"
spraxium generate [schematic] [name]
# alias:
spraxium g [schematic] [name]
```

Esse comando é especialmente valioso quando você quer velocidade sem abrir mão da consistência do projeto. Em vez de criar um arquivo na mão, escolher uma pasta, adicionar decorators e depois lembrar de registrar a classe no módulo, você deixa a CLI gerar um ponto de partida alinhado ao framework em uma única etapa.

## Quando usar generate em vez de criar arquivos manualmente

Use _spraxium generate_ quando o arquivo de que você precisa já corresponder a um padrão conhecido do framework: serviços, listeners, handlers, guards, tarefas, comandos e scaffolds de módulo. Ele é especialmente útil no início de um projeto, quando desvios de nomenclatura e registros esquecidos são comuns.

Criar arquivos manualmente ainda faz sentido quando você está construindo algo intencionalmente customizado, refatorando pesado um módulo existente ou criando um tipo de arquivo que não se encaixa em um schematic suportado. A CLI existe para eliminar setup repetitivo, não para substituir critério técnico.

## Como a geração funciona

<Steps>
  <Step title="Identificar o schematic">
    A CLI lê o argumento do schematic ou, se ele estiver ausente, apresenta uma
    lista interativa com todos os 19 schematics disponíveis. Aliases são aceitos
    em qualquer lugar onde o nome completo é aceito, então `g sc ping` equivale
    a `g slash-command ping`.
  </Step>
  <Step title="Normalizar o nome">
    O nome fornecido é dividido em hífens e underscores, normalizado para
    PascalCase no nome da classe e para kebab-case no nome do arquivo. Um nome
    como `auction-bid` vira `AuctionBidService` na classe e
    `auction-bid.service.ts` no arquivo.
  </Step>
  <Step title="Escolher o módulo de destino">
    Para todos os schematics que vivem dentro de um módulo, a CLI percorre
    `src/modules/` e apresenta um prompt com os módulos detectados. Selecione o
    módulo que deve receber o novo arquivo. Apenas o schematic *module* pula essa etapa.
  </Step>
  <Step title="Escrever o arquivo">
    A CLI grava o arquivo gerado na subpasta correta dentro do módulo escolhido,
    seguindo o layout padrão (`services/`, `tasks/`, `listeners/` etc.).
  </Step>
  <Step title="Registrar automaticamente no módulo">
    Quando o schematic oferece suporte, a CLI injeta a importação e o nome da
    classe no array correto dentro do decorator `@Module` do módulo de destino:
    `providers`, `listeners`, `controllers` ou `imports`.
  </Step>
</Steps>

## Todos os schematics

### Estrutura principal

<DropdownGroup>
<Dropdown title="module (alias m)">
  Cria um novo módulo em `src/modules/<name>/<name>.module.ts` com um decorator *@Module* básico. Não faz registro automático em outro módulo. Use como primeiro passo ao adicionar um novo domínio à aplicação.
</Dropdown>

<Dropdown title="service (alias s)">
  Cria uma classe *@Injectable* em `services/<name>.service.ts` dentro do módulo escolhido e a adiciona a `providers[]`. Use para lógica de negócio, acesso a dados ou utilitários reutilizáveis que precisem de injeção de dependência.
</Dropdown>

<Dropdown title="boot-service (alias bs)">
  Cria um serviço que implementa *OnApplicationBoot* em `services/<name>.service.ts` e o registra em `providers[]`. O método *onBoot* roda depois que o container está totalmente inicializado. Use para tarefas de inicialização que dependem de outros serviços injetados já estarem prontos.
</Dropdown>
</DropdownGroup>

### Tratamento de eventos

<DropdownGroup>
<Dropdown title="listener (alias l)">
  Cria uma classe listener de evento do Discord em `listeners/<name>.listener.ts` e a adiciona a `listeners[]`. A classe gerada usa o decorator *@Listener* para se ligar a um evento do cliente Discord.js. Use para qualquer evento bruto do Discord, como `messageCreate` ou `guildMemberAdd`.
</Dropdown>

<Dropdown title="signal-listener (alias sl)">
  Cria um listener que se inscreve em eventos do servidor Signal em `listeners/<name>.listener.ts` e o adiciona a `listeners[]`. Requer *@spraxium/signal* ou *@spraxium/signal-client* instalados. Use quando o bot precisar reagir a eventos internos tipados vindos de um barramento Signal.
</Dropdown>
</DropdownGroup>

### Comandos slash

<DropdownGroup>
<Dropdown title="slash-command (alias sc)">
  Cria uma classe de definição de comando slash no nível do módulo em `src/modules/<module>/`, decorada com *@SlashCommand*. O arquivo gerado declara o nome do comando, a descrição e os metadados das opções. Combine-o com um schematic *slash-handler* para tratar a interação.
</Dropdown>

<Dropdown title="slash-handler (alias sh)">
  Cria o handler de interação para um comando slash. A classe gerada é decorada com *@SlashHandler* e expõe um método *execute* que recebe o contexto da interação. Combine com um arquivo *slash-command* que defina o formato do comando.
</Dropdown>
</DropdownGroup>

### Comandos prefixados

<DropdownGroup>
<Dropdown title="prefix-command (alias pc)">
  Cria uma classe de definição de comando prefixado decorada com *@PrefixCommand*. Requer *@spraxium/components* e um prefixo de comando configurado. O arquivo gerado define o gatilho do comando, aliases e expectativas de argumentos.
</Dropdown>

<Dropdown title="prefix-handler (alias ph)">
  Cria o handler de mensagem para um comando prefixado, decorado com *@PrefixHandler*. O método *execute* recebe a mensagem analisada e os argumentos. Combine com o arquivo de definição *prefix-command* correspondente.
</Dropdown>
</DropdownGroup>

### HTTP

<DropdownGroup>
  <Dropdown title="http-controller (alias hc)">
    Cria uma classe de controller REST decorada com *@Controller* e a adiciona
    ao array `controllers[]` do módulo. Requer *@spraxium/http* instalado. A
    classe gerada inclui um método de rota *@Get* de exemplo. Use para qualquer
    endpoint exposto pelo servidor HTTP embutido.
  </Dropdown>
</DropdownGroup>

### Components

<DropdownGroup>
<Dropdown title="button (alias btn)">
  Cria uma classe handler de interação de botão decorada com *@Button* e a adiciona a `providers[]`. A classe gerada identifica interações por um prefixo de custom ID. Use ao implementar fluxos de UI baseados em botões, como confirmações ou respostas paginadas.
</Dropdown>

<Dropdown title="select (alias sel)">
  Cria um handler de interação de menu de seleção decorado com *@Select* e o
  adiciona a `providers[]`. Funciona do mesmo jeito que *button*, mas corresponde
  a interações de menu de seleção. Use em fluxos de entrada baseados em listas suspensas.
</Dropdown>

<Dropdown title="modal (alias md)">
  Cria um handler de envio de modal decorado com *@Modal* e o adiciona a
  `providers[]`. A classe gerada lida com envios de formulário modal
  identificados por um custom ID. Use quando precisar coletar texto estruturado dos usuários.
</Dropdown>

<Dropdown title="embed (alias em)">
  Cria uma classe reutilizável de construção de embed como um serviço injetável
  simples em `providers[]`. A classe gerada expõe um método `build()` que retorna
  um `EmbedBuilder`. Use para centralizar a construção de embeds e manter os handlers enxutos.
</Dropdown>

<Dropdown title="v2-component (alias v2)">
  Cria um handler de componente V2 do Discord para o novo modelo de interação Components V2. A classe gerada é decorada com *@V2Component* e adicionada a `providers[]`. Use ao trabalhar com a API atualizada de componentes do Discord para mensagens interativas mais ricas.
</Dropdown>
</DropdownGroup>

### Segurança

<DropdownGroup>
  <Dropdown title="guard (alias gu)">
    Cria uma classe guard *@Injectable* que implementa *CanActivate* e a adiciona
    a `providers[]`. Guards são executados antes de handlers de comando ou
    interação e retornam um booleano ou uma promise resolvida. Use para checagens
    de permissão, validação de papéis ou aplicação de cooldown.
  </Dropdown>
</DropdownGroup>

### Agendamento

<DropdownGroup>
<Dropdown title="task (alias t)">
  Cria uma tarefa agendada genérica decorada com *@Task* e a adiciona a `providers[]`. A classe gerada é adequada para encapsular qualquer trabalho no estilo cron. Requer *@spraxium/schedule* instalado.
</Dropdown>

<Dropdown title="timeout-task (alias tt)">
  Cria uma tarefa de execução única que roda após um atraso configurado,
  decorada com *@TimeoutTask*, e a adiciona a `providers[]`. Use para operações
  adiadas que devem rodar apenas uma vez, como lembretes ou anúncios programados.
</Dropdown>

<Dropdown title="interval-task (alias it)">
  Cria uma tarefa recorrente que roda em intervalo fixo, decorada com *@IntervalTask*, e a adiciona a `providers[]`. Use para polling, heartbeats ou qualquer trabalho periódico em segundo plano que deva se repetir durante toda a vida do processo.
</Dropdown>
</DropdownGroup>

## Validação de nomes

A CLI bloqueia padrões de sufixo repetidos para evitar nomes de arquivo redundantes. Passar `invoice-service` para o schematic _service_ é rejeitado porque o sufixo já está implícito pelo tipo de schematic. Use apenas `invoice`, e a CLI acrescentará automaticamente o sufixo correto.

É um detalhe pequeno, mas que ajuda a manter projetos grandes mais limpos. Assim, você evita nomes como _invoice-service.service.ts_ e classes como _InvoiceServiceService_, que surgem com facilidade quando a geração é totalmente manual.

## Dicas práticas de escolha

Se você não tiver certeza sobre qual schematic escolher, foque no papel do arquivo em runtime:

1. Lógica de negócio reutilizada por muitos pontos de entrada: escolha *service*.
2. Um ponto de entrada de evento do Discord: escolha *listener*.
3. A definição de um comando slash ou prefixado: escolha o schematic *command* correspondente.
4. A lógica de execução de uma interação ou comando: escolha o schematic *handler* correspondente.
5. Controle de acesso ou checagens de política: escolha *guard*.
6. Execução em segundo plano baseada em tempo: escolha um schematic de agendamento.

Essa regra prática costuma ser suficiente para escolher o scaffold certo sem decorar todos os aliases.

## Exemplos práticos

```bash filename="terminal"
# create a new domain module
spraxium g module billing

# create a service inside a module (prompted)
spraxium g service invoice

# create a slash command and its handler
spraxium g slash-command ping
spraxium g slash-handler ping

# create an interval task
spraxium g interval-task presence-cycle
```

## O que generate não faz

A geração entrega o arquivo, o formato do decorator e o registro no módulo quando isso é suportado. Ela não conclui a funcionalidade por você. Ainda é necessário adicionar a lógica de negócio, preencher a configuração, conectar dependências e decidir se a estrutura gerada corresponde ao desenho final do módulo.
