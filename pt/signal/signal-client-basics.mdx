## Papel do emissor

_Signal Client_ existe para publicar eventos de serviços externos em uma fronteira de integração orientada a bots. Mesmo quando o emissor é um endpoint de API, um cron worker ou uma Server Action em Next.js, o objetivo operacional é sempre o mesmo: influenciar o comportamento do bot de forma controlada e auditável. O pacote cuida da construção do envelope, da assinatura HMAC, da rotação de webhooks e da absorção de rate limit para que o código produtor continue focado na lógica de negócio.

Essa perspectiva evita que a equipe transforme o client em uma ferramenta genérica de envio de mensagens. O client é mais valioso quando seus serviços precisam de uma forma segura e consistente de avisar domínios do bot sobre mudanças de estado sem acoplamento aos internals do gateway do Discord.

## Contrato do construtor

_SignalClient_ recebe um único objeto _SignalClientConfig_ e, opcionalmente, um _FallbackStore_ customizado. O construtor cria internamente um _SignalEnvelopeBuilder_ para assinatura HMAC, um _WebhookPool_ para entrega em round-robin e, quando habilitado, um _FallbackWorker_ que é iniciado imediatamente. Todo campo além de `webhookUrls` e `hmacSecret` possui um valor padrão sensato, então uma configuração mínima precisa apenas desses dois valores.

```typescript filename="signal-client.setup.ts"
import { SignalClient } from '@spraxium/signal-client';

const client = new SignalClient({
  webhookUrls: [
    process.env.SIGNAL_WEBHOOK_URL_1!,
    process.env.SIGNAL_WEBHOOK_URL_2!,
  ],
  hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
  rateLimitStrategy: 'skip',
});
```

O segredo compartilhado em `hmacSecret` precisa coincidir exatamente com a configuração do lado do bot. Se os valores divergirem, o bot rejeita todo envelope na verificação HMAC, regra R10, e nenhum listener será executado.

## Construção e assinatura do envelope

Toda chamada de _send_ delega internamente para _SignalEnvelopeBuilder_, que produz um envelope completo e assinado criptograficamente. O builder gera um UUID aleatório como nonce, captura o timestamp atual como _sentAt_ e calcula a assinatura HMAC-SHA256 sobre a concatenação `nonce.sentAt.JSON.stringify(payload)`. Essa fórmula é idêntica à usada por _@spraxium/signal_ no lado receptor, então as duas pontas concordam com o contrato de assinatura sem qualquer negociação adicional.

O envelope resultante sempre carrega a versão `1` do protocolo, o nome do evento, o guild ID de destino e o payload, além dos campos criptográficos. O código produtor nunca precisa interagir diretamente com o builder, porque _send_ encapsula esse fluxo inteiro.

## O método send

_send_ é a API principal. Ele recebe um nome de evento, um guild ID, um payload opcional e _SendOptions_ também opcionais. O fluxo interno monta o envelope, escolhe o próximo webhook disponível do pool e entrega via POST HTTP. Se o webhook responder com 429, o pool o marca como limitado e tenta imediatamente o próximo candidato. Quando todos os webhooks se esgotam, o comportamento passa a depender da configuração em _rateLimitStrategy_.

```typescript filename="emit-event.ts"
await client.send('billing.status.changed', guildId, {
  plan: 'premium',
  expiresAt: '2025-12-31',
});
```

A interface _SendOptions_ expõe dois campos opcionais. O campo _webhookIndex_ força a entrega por um webhook específico, ignorando a rotação round-robin. O campo _skipFallback_ é usado internamente pelo _FallbackWorker_ para evitar loops de reenfileiramento durante tentativas de retry.

## Rotação do pool de webhooks

_WebhookPool_ distribui os envios entre os webhooks configurados usando um cursor round-robin. Quando um webhook responde com HTTP 429, ele é marcado como limitado pelo período indicado no cabeçalho `Retry-After`, e o pool passa a ignorá-lo automaticamente até o fim do cooldown. Adicionar múltiplas URLs de webhook melhora bastante a resiliência em picos, porque o client sempre tem endpoints alternativos para tentar.

O pool expõe vários métodos de inspeção úteis para monitoramento e depuração. Você pode acessar o pool a qualquer momento pela propriedade _pool_ da instância do client.

## Estratégias de rate limit

Quando todos os webhooks do pool estão limitados ao mesmo tempo, o client precisa decidir o que fazer. O campo _rateLimitStrategy_ controla esse comportamento. As duas estratégias são válidas, dependendo da arquitetura do seu serviço.

<Table>
  <TableHead>
    <TableRow>
      <TableCell header>Estratégia</TableCell>
      <TableCell header>Comportamento</TableCell>
      <TableCell header>Cenário ideal</TableCell>
    </TableRow>
  </TableHead>
  <TableBody>
    <TableRow>
      <TableCell>skip</TableCell>
      <TableCell>
        Lança *AllWebhooksRateLimitedError* imediatamente. O erro inclui o status completo do pool com timestamps de cooldown para que o chamador decida quando tentar de novo.
      </TableCell>
      <TableCell>
        Serviços que já possuem orquestração própria de retry ou infraestrutura de fila.
      </TableCell>
    </TableRow>
    <TableRow>
      <TableCell>wait</TableCell>
      <TableCell>
        Aguarda até o webhook com cooldown mais curto ficar disponível, por meio de *msUntilAvailable*, e tenta a entrega exatamente uma vez de novo. Se essa nova tentativa falhar, ele lança o erro.
      </TableCell>
      <TableCell>
        Absorção de picos curtos dentro do próprio client, sem lógica externa de retry.
      </TableCell>
    </TableRow>
  </TableBody>
</Table>

O padrão é `'skip'`, porque mantém o client não bloqueante. Na maioria dos contextos de Server Action ou handlers de API, em que uma pequena latência extra é aceitável, `'wait'` oferece ergonomia melhor ao absorver picos transitórios de rate limit de forma transparente.

## Tipos de erro

O client expõe duas classes de erro que entregam informações estruturadas de falha. Ambas estendem `Error` e carregam campos legíveis por máquina para tratamento programático.

_SignalClientError_ é lançado em respostas HTTP que não são 2xx nem 429. Ele expõe _statusCode_ e o _body_ da resposta como propriedades, o que facilita registrar falhas de transporte com contexto completo. Esse erro indica que o problema está no próprio endpoint de webhook, não em uma situação de rate limit.

_AllWebhooksRateLimitedError_ estende _SignalClientError_ com `statusCode` igual a `429` e expõe um array _poolStatus_. Cada entrada desse array é um snapshot de _WebhookStatus_ com _index_, _url_, a flag _available_ e o timestamp _rateLimitedUntil_. Esse erro só é lançado sob a estratégia `'skip'` ou quando `'wait'` esgota sua única nova tentativa.

## Emissor prático: Server Actions no Next.js

Um padrão comum em produção é um painel administrativo feito em Next.js, no qual uma Server Action atualiza dados de negócio e emite um evento Signal para o bot. Essa abordagem mantém as mutações de UI e as reações do bot fracamente acopladas, preservando um único fluxo operacional para quem administra o sistema. A Server Action cuida de autorização e persistência dentro da sua aplicação web, e o _Signal Client_ cuida da entrega assíncrona para o runtime do bot.

<CodeTabs>
  <Tab label="Server Action">
    ```typescript filename="app/actions/update-prefix.ts"
    'use server';

    import { SignalClient } from '@spraxium/signal-client';

    const client = new SignalClient({
      webhookUrls: [process.env.SIGNAL_WEBHOOK_URL_1!],
      hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
      rateLimitStrategy: 'wait',
    });

    export async function updatePrefix(guildId: string, prefix: string) {
      // persist in your database first
      await db.guilds.update(guildId, { prefix });

      // then emit the event for the bot
      await client.send('config.update', guildId, {
        prefix,
        source: 'admin-panel',
      });
    }
    ```

  </Tab>
  <Tab label="API Route Handler">
    ```typescript filename="app/api/signal/route.ts"
    import { SignalClient } from '@spraxium/signal-client';
    import { NextResponse } from 'next/server';

    const client = new SignalClient({
      webhookUrls: [
        process.env.SIGNAL_WEBHOOK_URL_1!,
        process.env.SIGNAL_WEBHOOK_URL_2!,
      ],
      hmacSecret: process.env.SIGNAL_HMAC_SECRET!,
      rateLimitStrategy: 'skip',
    });

    export async function POST(req: Request) {
      const { event, guildId, payload } = await req.json();
      await client.send(event, guildId, payload);
      return NextResponse.json({ ok: true });
    }
    ```

## Diretrizes de modelagem de eventos

Prefira nomes orientados ao domínio, que descrevam fatos de negócio em vez de ações de transporte. Um nome como _billing.status.changed_ é mais fácil de versionar e de entender do que rótulos voltados à ação, que acabam vazando detalhes internos de implementação. Mantenha nomes de evento em minúsculas e separados por ponto para seguir as convenções já usadas em todo o sistema do Signal.

Os payloads devem ser intencionalmente pequenos e estáveis. Inclua apenas os campos de que o bot realmente precisa para decidir o que fazer e evolua o schema com mudanças aditivas sempre que possível. Remover ou renomear um campo existente é uma quebra de compatibilidade e exige coordenação entre as implantações do emissor e do listener.

Use o filtro _events_ em _FallbackConfig_ para concentrar as garantias de confiabilidade nos eventos mais críticos. Eventos que não aparecem nessa lista continuam sendo entregues pelo fluxo normal, mas não entram no fallback store quando ocorre falha.

## Passo a passo do fluxo de entrega

<Steps>
  <Step title="Monte o envelope assinado">
    O método *send* delega para *SignalEnvelopeBuilder*. O builder gera um
    nonce com `crypto.randomUUID()`, captura `Date.now()` como *sentAt*,
    calcula a assinatura HMAC-SHA256 e devolve um envelope completo com a
    versão `1` do protocolo.
  </Step>
  <Step title="Escolha o próximo webhook">
    *WebhookPool.next* retorna o próximo webhook disponível em ordem
    round-robin. Se *SendOptions.webhookIndex* tiver sido informado, o pool
    retorna essa entrada específica via *get*, sem passar pela rotação. Se
    todos os webhooks estiverem limitados e nenhum índice tiver sido forçado, o
    fluxo salta para a etapa cinco.
  </Step>
  <Step title="Entregue via POST HTTP">
    O client envia uma requisição POST para a URL do webhook com o envelope
    serializado em JSON dentro do campo de conteúdo de mensagem do Discord. Se
    a resposta for 2xx, a entrega termina com sucesso e o método retorna.
  </Step>
  <Step title="Trate respostas 429">
    Quando o webhook responde com HTTP 429, o pool marca aquele índice como
    limitado pela duração extraída do cabeçalho `Retry-After`, usando 1000 ms
    como padrão. O client tenta imediatamente o próximo webhook disponível. Essa
    rotação continua até que um webhook funcione ou todos se esgotem.
  </Step>
  <Step title="Aplique a estratégia de rate limit">
    Quando não resta nenhum webhook, *rateLimitStrategy* decide o resultado. Em
    `'skip'`, um *AllWebhooksRateLimitedError* é lançado na hora. Em `'wait'`,
    o client dorme até o cooldown mais curto terminar e tenta uma vez de novo.
    Se o fallback estiver habilitado e o erro puder ser capturado, o envelope é
    enfileirado no fallback store para novo processamento posterior.
  </Step>
</Steps>

## Quando esse modelo é a ferramenta errada

Se você precisa de uma confirmação síncrona imediata da lógica do bot dentro do mesmo ciclo da requisição, Signal normalmente não é o contrato certo. Chamadas diretas de serviço continuam mais simples e fáceis de rastrear para comunicação in-process dentro da mesma fronteira de serviço. O Signal foi desenhado para entrega assíncrona de eventos no estilo fire-and-forget, em que o produtor não precisa de resposta do consumidor.

Da mesma forma, se seus eventos exigem garantias rígidas de ordenação, uma fila dedicada, como RabbitMQ ou Redis Streams, é mais adequada. O Signal entrega mensagens tão rápido quanto o pool de webhooks permite, e a ordem dos retries depois de falhas é best-effort, não estritamente sequencial.
