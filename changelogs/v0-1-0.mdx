Spraxium started inside Spacelaxy. We were repeating the same setup across Discord bots and needed a place for each feature, along with a way to share services between commands. The module system, dependency injection, and guards grew out of that work.

Our bots used versions of the framework for over a year before we opened the repository. With 0.1.0, we put that code into public packages, added documentation and examples, and made it available for other people to build with.

## What's in the first release

`@spraxium/core` handles modules, shared services, commands, events, guards, and the bot's lifecycle. `@spraxium/common` provides the decorators and types those features use. Together they give a bot's code a structure that can grow as new features are added.

There are optional packages for the work around those commands. `@spraxium/env` checks environment variables at startup and reports missing or invalid values before the bot connects. `@spraxium/i18n` loads translations and resolves the language for a server, with typed keys that can be used in command handlers and embeds. `@spraxium/schedule` adds cron and interval jobs that start when the bot is ready and stop with the application.

For integrations, `@spraxium/http` provides a web server alongside the bot, with controllers, input validation, and a bridge for operations that use Discord. `@spraxium/signal` receives signed events from other services, and `@spraxium/signal-client` sends them from a Node.js backend. Both ends share the event types.

The CLI creates a project, generates modules, providers, commands, and guards, and runs the development server with hot reload. The included templates show how to put those pieces together in a working bot.

## What we're looking at next

The first public version includes the modules and services we had been using in our own bots. More people using the framework will also bring configurations we haven't worked with as often. Dynamic module setups, circular dependencies, and advanced HTTP routes are areas where reports from real projects will help us.

The next round of work focuses on clearer dependency injection errors, better CLI output during development, and more tests for Signal. If you run into a problem, an issue with the steps to reproduce it helps us check it against the same setup.
